<InBrief>

- Paginate every collection from day one, with a server-enforced maximum page size. Adding pagination later is a breaking change.
- Prefer keyset (cursor) pagination: constant cost at any depth and no duplicates or gaps under concurrent writes.
- Keep cursors opaque, bind them to the query that produced them, and order by a unique tiebreaker.
- Return a page object with a `next` link; its absence means the end. Clients shouldn't build URLs.
- Avoid exact total counts on large collections. Offer `has_more`, an estimate, or an opt-in count.

</InBrief>

Every collection starts small. Then one Black Friday `GET /orders` returns two million rows, the database spends a minute serialising them, and the mobile app gives up at thirty seconds. Pagination is cheap to add before the first release and a breaking change afterwards. The kind you choose decides whether page 5,000 costs the same as page 1.

## Prefer keyset pagination over offsets

Offset pagination ("skip 40, take 20") is everyone's first instinct: easy to explain, and clients can jump to page 37. It has two problems that grow with the data:

1. **Cost grows with depth.** `OFFSET 1000000` makes the database read and discard a million rows before returning twenty.
2. **Pages drift under writes.** An insert at the top shifts every row down one place, so the next page repeats an item. A delete shifts rows up, so an item is skipped. A sync job built on offsets silently misses records, and Larkspur Logistics finds out at quarter-end reconciliation.

Here is the drift in slow motion:

<Figure n={1} caption="Offset pagination while a new order (Z) arrives between two requests. Order C appears twice.">

```text
Request 1   ?offset=0&limit=3    [ A  B  C ]  D  E  F
            new order Z inserted at the top
Request 2   ?offset=3&limit=3      Z  A  B  [ C  D  E ]   ← C again
```

</Figure>

Both problems come from describing a page by its position. Keyset pagination, which APIs usually call cursor pagination, describes it by content instead: "the rows after this one". Watch the `WHERE` clause; it replaces `OFFSET` entirely:

```sql
-- cursor decodes to (created_at, id) of the last row on the previous page
SELECT * FROM orders
WHERE (created_at, id) < ('2026-03-14T09:26:53Z', 'ord_42')
ORDER BY created_at DESC, id DESC
LIMIT 21;  -- one extra row tells you whether there's a next page
```

With an index on `(created_at, id)`, every page is an index seek, and inserts or deletes elsewhere can't cause duplicates or gaps. Page 5,000 costs what page 1 costs. The price is that clients can't jump to an arbitrary page. Feeds, syncs, exports and infinite scroll never need to; a back-office table with page numbers might, and offset is acceptable there if depth is capped.

## Cursors fail in the details

The SQL is short. The bugs live around it, and each passes every test until production data arrives:

- **Order by a unique tiebreaker.** Sorting by `created_at` alone breaks when two orders share a timestamp, and on Black Friday hundreds do: the page boundary falls between them and one is skipped. Append the primary key.
- **Mixed sort directions need care.** Row-value comparison `(a, b) < (x, y)` only works when both columns sort in the same direction. For `ORDER BY total DESC, id ASC`, expand it: `total < x OR (total = x AND id > y)`.
- **Make cursors opaque.** Encode them (base64url of JSON, or encrypted if they reveal anything) and document them as strings with no structure. A client that can read your cursor will eventually build one, and then you can never change the format.
- **Bind the cursor to its query.** A cursor from `?status=shipped` reused with `?status=paid` produces nonsense. Embed a hash of the filter and sort parameters and reject a mismatch with `422`, or put the full query in the cursor so `next` needs nothing else.

## Return a page object with a next link

Once the server owns the cursor, it should own the URL too. A client that builds page URLs must know your parameter names and carry the filters forward. Hand it the next URL instead:

```json
{
  "items": [{ "id": "ord_42" }, { "id": "ord_41" }],
  "next": "https://api.example.com/orders?status=shipped&limit=20&cursor=eyJjIjoi…",
  "self": "https://api.example.com/orders?status=shipped&limit=20"
}
```

No `next` means the end. Notice how little the client loop has to know: no URL building, no page arithmetic, no off-by-one errors:

```ts
for (let url: string | undefined = START; url;) {
  const page = await fetch(url).then((r) => r.json());
  await process(page.items);
  url = page.next;
}
```

One case surprises people. An empty page with a `next` link is legal, for example when a filter rejected every row in a scanned batch. Clients must keep following `next` rather than stopping at the first empty page. Say so in the docs, because someone will write `if (!items.length) break`.

```python
def encode(cursor: dict) -> str:
    return base64.urlsafe_b64encode(json.dumps(cursor).encode()).decode().rstrip("=")

def decode(token: str) -> dict:
    return json.loads(base64.urlsafe_b64decode(token + "=" * (-len(token) % 4)))

@app.get("/orders")
def list_orders(request: Request, status: str | None = None, cursor: str | None = None,
                limit: int = Query(20, ge=1, le=100)) -> OrderPage:
    query_hash = hashlib.sha256(f"{status}".encode()).hexdigest()[:8]
    after = decode(cursor) if cursor else None
    if after and after["q"] != query_hash:
        raise problem(422, "cursor-query-mismatch")
    rows = orders.page(status=status, after=after and (after["c"], after["id"]), limit=limit + 1)
    page, has_more = rows[:limit], len(rows) > limit
    next_url = None
    if has_more:
        last = page[-1]
        token = encode({"c": last.created_at.isoformat(), "id": last.id, "q": query_hash})
        next_url = str(request.url.include_query_params(cursor=token))
    return OrderPage(items=page, next=next_url, self=str(request.url))
```

## Make total counts opt-in

Then someone asks for "1–20 of 1,284,302". It looks helpful. On a large, filtered table, the exact `COUNT(*)` can cost more than fetching the page, because PostgreSQL has to visit every matching row to count it. So ask what the client does with the number. Usually it needs to know whether there's more, which the `next` link already says. If a count is needed, offer it as an opt-in (`?include=total_count`), cap it ("10,000+"), or return the planner's estimate and label it as one.

You won't be the first to migrate from offsets after launch. Slack did it in public, and wrote it up.

<Note kind="practice" title="Slack's move to cursors" year="2017" source="https://slack.engineering/evolving-api-pagination-at-slack/">

Slack's Web API had grown several pagination styles, including page numbers and offsets. Then workspaces reached hundreds of thousands of channels and users, and those styles became slow and unreliable. Slack moved to one cursor scheme across methods, with `next_cursor` in `response_metadata` and an empty string meaning the end. Their write-up is a clear account of migrating a public API's pagination without breaking clients.

</Note>

<WorkedProblem kind="Review" title="A product listing cursor">

```python
@app.get("/products")
def list_products(after: str | None = None, sort: str = "price", limit: int = 1000):
    q = select(Product).order_by(getattr(Product, sort))
    if after:
        q = q.where(getattr(Product, sort) > after)
    return session.scalars(q.limit(limit)).all()
```

Find the bugs.

<Solution>

1. **No unique tiebreaker.** Many products share a price, so `price > after` skips every remaining product that shares the boundary price. Order by `(price, id)` and compare both.
2. **The cursor isn't opaque.** `after` is a raw price, so clients will construct it, and you can never change the scheme.
3. **The cursor isn't bound to the sort.** A cursor taken while sorting by `price` and replayed with `sort=name` compares a price to names.
4. **`sort` goes straight into `getattr`.** That allows sorting by any attribute, including unindexed or internal ones. Allow-list the sortable fields.
5. **No maximum page size,** and a default of 1,000. Enforce something like 100.
6. **A bare array response,** with no `next` link and no room for one.

</Solution>
</WorkedProblem>

## What to take away

Describe a page by the last row the client saw, not its position, and hand the client a `next` link. Paginate from the first release; adding it later breaks everyone. A cursor is only valid for the query that made it, which is why filters and sorting need the same care. That's [filtering and sorting](/collections/filtering/).
