<InBrief>

- Use one vocabulary across the API: `q`, `sort`, `fields`, `embed`, `limit`, `cursor`, plus filters named after the field they filter.
- Choose one multi-value format, either `?status=a,b` or `?status=a&status=b`, and use it everywhere.
- Allow-list filterable and sortable fields, back them with indexes, and append a unique tiebreaker to every sort.
- Move complex boolean queries, and any query on sensitive values, into `POST` on a search resource.
- Document implicit filtering, such as "returns only the caller's orders".

</InBrief>

Once collections are paginated, the next request is always some version of "only the shipped orders from last week, newest first, just the IDs and totals". If every endpoint answers that with its own parameter names, every client reads every page of docs. With a small shared vocabulary, clients guess, and they guess right.

## Use one small vocabulary everywhere

| Parameter                                         | Meaning                              | Example                               |
| ------------------------------------------------- | ------------------------------------ | ------------------------------------- |
| `q`                                               | Free-text search                     | `?q=linen+shirt`                      |
| `sort`                                            | Sort keys, `-` for descending        | `?sort=-created_at,id`                |
| `fields`                                          | Return only these fields             | `?fields=id,status,total`             |
| `embed`                                           | Inline related resources             | `?embed=customer,line_items`          |
| `limit`                                           | Page size                            | `?limit=50`                           |
| `cursor`                                          | Opaque position from a previous page | `?cursor=eyJj…`                       |
| _field name_                                      | Exact-match filter                   | `?status=shipped&customer_id=cus_7`   |
| _field_`_after` / `_before`, `min_`/`max_`_field_ | Ranges                               | `?created_after=2026-11-01T00:00:00Z` |

## Pick one multi-value format

For "any of these values", both forms are common:

```http
GET /orders?status=shipped,delivered            # OpenAPI style: form, explode: false
GET /orders?status=shipped&status=delivered     # OpenAPI style: form, explode: true
```

Comma-separated is shorter and easier to type. Repeated parameters need no escaping when values themselves contain commas. Either is fine. Mixing them in one API is the mistake, and so is leaving the `explode` setting unspecified in the spec, because code generators then guess.

`sort=-price,name` means price descending, then name ascending. Zalando also allows `+` for ascending, but a literal `+` in a query string decodes to a space, so clients have to send `%2B`. Leaving the prefix off for ascending avoids that.

## Allow-list fields, and index what you allow

Every filterable or sortable field is a query plan you have promised to keep fast. Allow-list them explicitly, return <code>422</code> with the allowed list for anything else, and make sure each one is covered by an index that also works with your pagination order. Append the primary key to every sort internally so [pagination](/collections/pagination/) stays stable.

_Assumes:_ SQLAlchemy 2 for FastAPI, django-filter 24 for DRF, Zod for Hono.

SORTABLE = {"created_at", "total", "id"}

@app.get("/orders")
def list_orders(
    status: Annotated[str | None, Query(description="Comma-separated: shipped,delivered")] = None,
    customer_id: str | None = None,
    created_after: AwareDatetime | None = None,
    sort: str = "-created_at",
):
    q = select(OrderRow)
    if status:
        q = q.where(OrderRow.status.in_(status.split(",")))
    if customer_id:
        q = q.where(OrderRow.customer_id == customer_id)
    if created_after:
        q = q.where(OrderRow.created_at > created_after)
    for key in [*sort.split(","), "id"]:  # unique tiebreaker last
        name = key.lstrip("-")
        if name not in SORTABLE:
            raise problem(422, "unsortable-field", field=name, sortable=sorted(SORTABLE))
        col = getattr(OrderRow, name)
        q = q.order_by(col.desc() if key.startswith("-") else col.asc())
    ...

class CharInFilter(django_filters.BaseInFilter, django_filters.CharFilter):
    pass

class OrderFilter(django_filters.FilterSet):
    status = CharInFilter(field_name="status")  # ?status=a,b
    created_after = django_filters.IsoDateTimeFilter(field_name="created_at", lookup_expr="gt")

    class Meta:
        model = Order
        fields = ["status", "customer_id", "created_after"]

class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    filter_backends = [DjangoFilterBackend, SearchFilter, OrderingFilter]
    filterset_class = OrderFilter
    search_fields = ["reference", "customer__email"]
    ordering_fields = ["created_at", "total"]  # the allow-list
    ordering = ["-created_at", "-id"]

# settings.py: conventional names instead of DRF's search= and ordering=
REST_FRAMEWORK = {"SEARCH_PARAM": "q", "ORDERING_PARAM": "sort"}

<TabItem label="Hono">

```ts
const SortKey = /^-?(created_at|total|id)$/;

const OrderQuery = z.object({
  status: z
    .string()
    .transform((s) => s.split(","))
    .pipe(z.array(z.enum(["placed", "shipped", "delivered"])))
    .optional(),
  customer_id: z.string().optional(),
  created_after: z.string().datetime({ offset: true }).optional(),
  sort: z
    .string()
    .default("-created_at")
    .refine((s) => s.split(",").every((k) => SortKey.test(k)), "unsortable field"),
});

app.get("/orders", zValidator("query", OrderQuery), async (c) => {
  const q = c.req.valid("query");
  const orderBy = [...q.sort.split(","), "id"].map((k) =>
    k.startsWith("-") ? { [k.slice(1)]: "desc" } : { [k]: "asc" },
  );
  return c.json({ items: await orders.find({ ...q, orderBy }) });
});
```

## Trim responses with fields and embed

`fields` lets a mobile client ask for three properties instead of forty, and `embed` lets it inline related resources to save round trips. Both multiply the response shapes you must test and cache, so support them where measurements show they matter: large resources and chatty mobile screens. Unknown names should produce <code>422</code>, not be silently ignored, so typos are caught. Caching implications are covered in [Caching](/collections/caching/).

## Move complex and sensitive queries into a body

When a query needs nested AND/OR, long ID lists, or many ranges, the query string becomes unreadable, and some proxies cap URLs at a few kilobytes. Model the search as a resource:

```http
POST /orders/search
Content-Type: application/json

{
  "filter": { "and": [
    { "field": "status", "in": ["shipped", "delivered"] },
    { "or": [ { "field": "total.amount", "gte": "100.00" }, { "field": "customer.tier", "eq": "gold" } ] }
  ]},
  "sort": ["-created_at"],
  "limit": 50
}
```

This gives up HTTP caching and safe-method retries, which is why simple queries stay on `GET`, and why the [`QUERY` method](/http/methods/) is worth watching. Google takes a different route with AIP-160: a single `filter` string in a small, specified expression language (`status = "shipped" AND total > 100`), which keeps `GET` at the cost of a parser on both sides.

The same move applies to sensitive filters. URLs end up in access logs, proxy logs, browser history, APM tools and `Referer` headers. An email address or a national ID used as a filter belongs in a body.

<Note kind="incident" title="HealthCare.gov" year="2015" source="https://www.eff.org/deeplinks/2015/01/healthcare.gov-sends-personal-data">

The EFF found that HealthCare.gov was passing details such as age, income, ZIP code, smoking status and pregnancy to third-party analytics and advertising services, partly because those values sat in URLs that tracking scripts and `Referer` headers carried along. Treat every query string as something that will be logged and shared, because eventually it will be.

</Note>

## Document implicit filtering

`GET /orders` returning only the caller's orders is normal. Leaving it undocumented means an admin and a customer calling the same URL see different results, and nobody can tell whether it's a bug. State the implicit scope in the endpoint description, and consider making it explicit for privileged callers (`?customer_id=…`).
