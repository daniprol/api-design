<InBrief>

- Make every change to a published API backward compatible, or treat it as a new API.
- Additive changes are compatible: new endpoints, new optional inputs, new response fields. Removing, renaming, retyping or tightening is breaking.
- Document enums as open-ended from day one. New values are the most common surprise break.
- Be strict about input from the first release (reject unknown fields); relaxing later is compatible, tightening isn't.
- Write clients as tolerant readers: ignore unknown fields, map unknown enum values to a fallback, never depend on order.

</InBrief>

Shipping an API is easy. Changing it without breaking anyone is the real craft. You often can't see your clients, can't force them to upgrade, and can't know which harmless-looking detail they depend on. Getting compatibility right is what lets an API live for ten years instead of being rewritten every two.

## Know which changes break clients

| Compatible                                             | Breaking                                                      |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| Add an endpoint or resource                            | Remove or rename an endpoint                                  |
| Add an optional request field or parameter             | Add a required request field or parameter                     |
| Add a response field                                   | Remove or rename a response field                             |
| Make a required input optional                         | Make an optional input required                               |
| Accept more input values                               | Reject input that used to be accepted                         |
| Add a problem type within an existing status class     | Change a field's type (`"42"` → `42`) or format               |
| Add an enum value, _if_ clients were told to expect it | Make a response field nullable or optional when it wasn't     |
|                                                        | Change a field's meaning, units or default                    |
|                                                        | Change the status code or problem type of an existing failure |

Two rows deserve emphasis. A rename is a removal plus an addition, so it's breaking even when it feels like tidying. And changing what a field means without changing its shape is the most dangerous break of all, because no schema diff or contract test catches it. Prices that silently switch from gross to net will be wrong in every client until someone notices the money.

## Design so that growth stays additive

The cheapest compatibility problem is the one the first version doesn't create:

- **Return objects, not primitives, where growth is likely.** `"price": {"amount": "19.99", "currency": "EUR"}` can gain `tax_included`. `"price": 19.99` can't.
- **Return an object at the top level** so a list can gain pagination (see [JSON conventions](/representations/json/)).
- **Be strict about input from the start.** Reject unknown fields (`extra="forbid"`). A typo like `quantitty` is caught at once, and accepting more later is compatible. Starting lenient and tightening later breaks everyone who relied on leniency.
- **Don't return fields "just in case".** Each field is a promise you'll have to keep.
- **Document enums as open-ended.** Say in the spec that new values may appear and what clients should do with unknown ones.

## Write clients as tolerant readers

Postel's robustness principle ("be conservative in what you send, liberal in what you accept") applied to APIs means: servers are strict with input and careful with output, and clients tolerate additions. A tolerant reader ignores fields it doesn't know, maps unknown enum values to a sensible fallback, and never depends on field order or on the exact text of messages.

_Assumes:_ these are client-side models consuming the shop API.

```python
    model_config = ConfigDict(extra="ignore")  # unknown fields are fine
    id: str
    status: str  # not Literal[...]: new statuses must not crash the client

    @property
    def is_final(self) -> bool:
        return self.status in {"delivered", "cancelled"}  # unknown → not final

class OrderIn(BaseModel):  # the server's input model: strict
    model_config = ConfigDict(extra="forbid")
```

<Note kind="history" title="Postel's Law, revisited" year="2023" source="https://www.rfc-editor.org/rfc/rfc9413">

Jon Postel wrote the robustness principle into the TCP specification in 1980. It helped the early internet interoperate, but decades of being liberal in what you accept meant protocols accumulated everyone's bugs as de facto features, and some of them became security holes. RFC 9413 revisits it and recommends active maintenance and strictness over indefinite tolerance. For APIs: tolerant readers, yes; lenient servers, no.

</Note>

## Accept that everything observable becomes contract

Hyrum's Law says that with enough users, every observable behaviour will be depended on by someone, whatever the documentation promises. Field order, the wording of `detail`, how long a slow endpoint takes, the order of an unsorted list. You can't prevent this, but you can limit the surface. Expose less, sort lists explicitly, keep error `type` values stable and treat `detail` text as free to change, and say all of this in the docs, so that when a client's assumption breaks, you know who was wrong.

<Note kind="curiosity" title="Spacebar heating" source="https://xkcd.com/1172/">

XKCD 1172 shows a user complaining that an update fixed a bug where holding the spacebar made the CPU overheat, because their workflow used the heat as a signal. It's the clearest illustration of Hyrum's Law, and most API maintainers can name a real equivalent from their own changelog.

</Note>

<WorkedProblem kind="Review" title="A release note">

The next release of the orders API lists these changes. Which are breaking?

1. New endpoint `GET /orders/{id}/invoice`.
2. `shipping_address.zip` renamed to `shipping_address.postal_code`.
3. New optional query parameter `?include_cancelled=true`. The default behaviour changes from including cancelled orders to excluding them.
4. New enum value `partially_shipped` for `status`, documented as open-ended since v1.
5. `total.amount` now excludes tax. A new field `total_with_tax` was added.
6. `email` is now validated with a stricter regex.

<Solution>

- **Compatible:** 1 (additive), and 4 (additive, because clients were told to expect new values).
- **Breaking:** 2 (rename); 3 (the parameter is additive, but the default behaviour changed, so old clients silently lose cancelled orders); 5 (same shape, new meaning, the most dangerous kind); 6 (input that used to be accepted is now rejected).

For 3, keep the old default and add `?exclude_cancelled=true`, or make the new behaviour opt-in. For 5, add `subtotal` and leave `total` alone.

</Solution>
</WorkedProblem>
