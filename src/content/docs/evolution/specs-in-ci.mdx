<InBrief>

- Check the spec into the repository and generate or validate it on every build. A spec that drifts from the code is worse than none.
- Give every spec an owner, a stable API ID, an audience and a semantic version.
- Lint against your style guide (Spectral or Zally) so reviews can focus on the domain.
- Fail the build on breaking changes with a spec diff (oasdiff), and require an explicit override.
- Test the running implementation against the spec (Schemathesis), and use consumer contracts (Pact) where you know your consumers.

</InBrief>

Thursday afternoon. A Fernhill pull request makes `warehouse_id` required on `POST /shipments`. Two reviewers approve it: the code is tidy and the tests pass. On Friday every Larkspur Logistics shipment comes back <code>422</code>, and Priya spends the weekend reading a diff nobody compared. With five APIs, people catch this; with five hundred, the style guide becomes a document everyone agrees with and nobody follows. So hand the checking to the build: validate, lint, diff and publish the spec on every change, the way code is compiled and tested.

## Make every spec say who owns it and who it's for

During an incident, Priya's first question is whose API this is and who depends on it. The `info` block should answer that. Notice the two `x-` fields: an identity that survives renames, and an audience that sets the stakes.

```yaml
openapi: 3.1.0
info:
  title: Order Management API
  version: 1.14.2 # semantic version of the contract
  description: Place, track and cancel customer orders.
  contact: { name: Team Checkout, url: https://wiki.example.com/teams/checkout }
  x-api-id: 0f3c1e2d-7a0e-4b8e-9d2b-1f2a3b4c5d6e # stable forever, survives renames
  x-audience: external-partner
servers:
  - url: https://order-management.api.example.com
```

Version the contract with SemVer, even if the API is never versioned on the wire. Major means breaking (rare), minor means additive, and patch means documentation only.

Declare the audience, which tells reviewers how careful to be: component-internal, business-unit-internal, company-internal, external-partner or external-public. Your own frontend's API can move fast; one with three thousand external integrators can't.

And name by function, not by team or technology: `order-management.api.example.com`, not `team-falcon-svc-2`. Teams reorganise; functions stay.

## Let a linter argue about casing

Human reviewers are expensive; spend them on the domain model, not on whether a path is kebab-case. A linter turns guideline rules into failing builds. Spectral is the generic engine, with rulesets for OpenAPI and several public style guides; Zally is Zalando's linter for its own guidelines. Here are two house rules in Spectral. Each is a JSONPath (`given`) and a check (`then`):

```yaml title=".spectral.yaml"
extends: ["spectral:oas"]
rules:
  paths-kebab-case:
    description: Path segments are kebab-case.
    given: "$.paths[*]~"
    then: { function: pattern, functionOptions: { match: "^(/([a-z0-9-]+|\\{[a-z_]+\\}))+$" } }
    severity: error
  problem-json-errors:
    description: 4xx and 5xx responses use application/problem+json.
    given: "$.paths.*.*.responses[?(@property >= '400')].content"
    then: { field: "application/problem+json", function: truthy }
    severity: error
```

Start with a small set at `error` severity, keep the rest as warnings, and promote rules as the existing APIs comply. A linter that fails every build on day one gets disabled on day two.

## Fail the build when a change breaks clients

This check would have saved Priya's weekend. Compare the spec on the branch with the one on `main`, and fail if anything breaks existing clients: a removed path, a new required parameter, a narrowed enum, a changed type. oasdiff checks a long catalogue of such changes. In the workflow, watch the last step: it diffs against `main`'s spec.

```yaml title=".github/workflows/api.yml (excerpt)"
- name: Export spec
  run: python -m app.export_openapi > openapi.json
- name: Lint
  run: npx @stoplight/spectral-cli lint openapi.json --fail-severity error
- name: Breaking changes
  run: |
    git show origin/main:openapi.json > base.json
    docker run --rm -v "$PWD:/w" tufin/oasdiff breaking /w/base.json /w/openapi.json --fail-on ERR
```

When a break is intended, the override should be explicit and reviewed, such as a pull-request label plus a major version bump, not a flag someone quietly sets at 6 p.m. Diffs see shape, not meaning. A field that changes from gross to net price passes every tool (see [Compatibility](/evolution/compatibility/)).

## Check that the code keeps the spec's promises

A linted, diffed spec can still describe an API that doesn't exist. Two complementary techniques close the gap.

Property-based testing works from the spec. Schemathesis generates requests from the schema, including edge cases you didn't think of, and checks the responses: undocumented status codes, wrong content types, 500s on unusual input, bodies that don't match. It's the cheapest way to find the stack trace you promised never to leak.

Consumer-driven contracts start from the consumer. With Pact, each consumer records the interactions it relies on and the provider's CI replays them, so you learn which consumers a change breaks before you deploy. It needs known consumers willing to take part, so it suits internal ecosystems better than public APIs; Larkspur will not be writing Pact files.

All of this needs CI to get the spec out of the app cheaply. Here's the export step; notice the metadata is stamped on at export time.

_Assumes:_ the app can export its spec without starting a server.

## Publish the spec, then watch who actually calls

A spec that lives only in a repository is a secret. Publish it to an API catalogue or developer portal, so teams find an API before building a duplicate, and render reference docs from the same file so they can't drift.

Then measure how the API is actually used. Per endpoint and per client, track rate, errors split into 4xx and 5xx, and latency percentiles (the RED method), plus calls to deprecated endpoints. Usage data by client is what makes [deprecation](/evolution/deprecation/) possible: you can't contact the consumers you can't see. Ownership and audience start in `info`:

<Note kind="practice" title="Zally at Zalando" source="https://github.com/zalando/zally">

With hundreds of teams publishing APIs, Zalando couldn't review every spec by hand against its guidelines. So it built Zally, an open-source linter whose rules map to guideline numbers, reporting violations by severity in each team's pipeline. The API review meeting now spends its time on what a linter can't judge: the domain model, naming and lifecycle.

</Note>

## What to take away

A rule nobody enforces is a suggestion, so put the spec in the build: lint it, diff it, test the code against it, publish it with an owner. Events have contracts too, often with consumers you can't name at all: [event design](/events/event-design/).
