<InBrief>

- Mark deprecations in three places: the spec (`deprecated: true`), every response (`Deprecation`, `Sunset`, a `Link` to the migration guide) and a dated changelog entry.
- Log every call to a deprecated endpoint with the caller's identity. Removal is a decision about named clients, not traffic in aggregate.
- Run scheduled brownouts before the sunset, so remaining callers find out in a planned hour rather than on removal day.
- Remove only when usage is at or near zero and remaining consumers have agreed. Then return <code>410 Gone</code> with a problem body for a while.

</InBrief>

Monday, 9 a.m. Fernhill removed an old shipping endpoint over the weekend, after six months of warnings in the changelog. By 9.05 Larkspur Logistics' integration is failing on every order, and Priya learns that nobody at Larkspur reads changelogs. Every endpoint dies eventually; what you control is how.

## Give the endpoint a lifecycle with dates

Removal feels like one decision. It's six steps, each with a date:

```text
active ──► deprecated ──────────────────────────► sunset ──► gone (410)
             │  announce · measure · migrate · brownouts  │
             └────────── published support window ─────────┘
```

1. **Deprecate.** Mark it in the spec and on the wire. It still works.
2. **Announce.** Changelog, direct email to known consumers, migration guide.
3. **Measure.** Who still calls it, how often, from which client versions.
4. **Migrate.** Help the remaining consumers by name. Most stragglers are a team that missed the email.
5. **Brown out.** Disable it briefly on announced dates.
6. **Sunset.** Remove it when usage is at zero, and return <code>410</code> with a pointer to the replacement.

## Announce it where both people and software will see it

A changelog reaches people who read changelogs, which excludes Larkspur. So say it in the spec, for developers, and in every response, for software. In the spec, notice the description carries both dates and the replacement:

```yaml
paths:
  /orders/{order_id}/shipping-info:
    get:
      deprecated: true
      description: |
        Deprecated since 2026-01-01. Use GET /shipments?order_id={order_id}.
        Will be removed on 2027-06-30. Migration guide: https://api.example.com/docs/migrations/shipping-info
```

Headers reach code nobody is reading: SDKs that log warnings, gateways that report on deprecated traffic, test suites that fail on them:

```http
HTTP/1.1 200 OK
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://api.example.com/docs/migrations/shipping-info>; rel="deprecation"
```

- `Deprecation` (RFC 9745, 2025) carries the date the resource was or will be deprecated, as a Structured Field date: `@` plus a Unix timestamp. Early drafts used `true`, and you'll still see that in the wild.
- `Sunset` (RFC 8594) is the HTTP date after which the resource is expected to stop responding.
- `Link` with `rel="deprecation"` points at human-readable migration information.

Wrap the headers in something reusable. Watch the log line: it records who called, which the next section needs.

_Assumes:_ structured logging with the caller's client ID available from authentication.

def deprecated(since: datetime, sunset: datetime, guide: str):
    def decorator(view):
        @wraps(view)
        def wrapper(self, request, *args, **kwargs):
            log.info("deprecated_call", path=request.path, client=getattr(request.auth, "client_id", None))

            return response
        return wrapper

## Count callers by name, not requests

"Traffic is down 98 percent" sounds like permission to remove. It isn't, if the remaining 2 percent is your largest customer's nightly reconciliation job. Aggregates hide exactly the client you'll break, so log deprecated calls with the client identity and keep a list of remaining callers with owners and contact details. You decide removal against that list, one name at a time. Check your own house too: a Fernhill service that starts depending on a deprecated API extends its life.

## Rehearse the removal with brownouts

Some clients ignore emails and headers alike; they only notice errors. So give them one early, on your terms. A brownout disables the endpoint for a short, announced window, returning the same <code>410</code> it will return after sunset. Clients find out during a planned hour, with time left to migrate. Schedule a few, increasing in length, and announce each. Twitter did exactly this:

<Note kind="practice" title="Twitter's v1 blackout tests" year="2013" source="https://blog.x.com/developer/en_us/a/2013/api-v1-retirement-final-dates">

Before retiring API v1, Twitter scheduled a blackout test for 16 April 2013. v1 calls failed for its duration, so developers could see what would break, and Twitter warned more might follow. Then it moved the final retirement from 7 May to 11 June 2013. Brownouts are cheap to run, and they turn surprise outages into calendar entries.

</Note>

## Remove at zero, then answer 410

Even at zero, someone turns up: a forgotten cron job, a phone that never updated the mobile app. A generic <code>404</code> sends them hunting for a typo. Return <code>410 Gone</code> for a few months, with a problem body naming the replacement and migration guide, so they get an error they can act on:

## What to take away

Deprecation is a project with named callers and dates, not a deletion: announce, measure, rehearse, and remove only at zero. All of it relies on the spec telling the truth, which is a job for a machine: [specs in CI](/evolution/specs-in-ci/).
