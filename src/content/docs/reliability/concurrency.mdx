<InBrief>

- Use optimistic concurrency for HTTP. Locks held across requests outlive their owners.
- Send a strong `ETag` derived from a version column on every read, and accept `If-Match` on every write.
- Do the comparison inside the write (`UPDATE … WHERE version = ?`), never as a separate read-then-check.
- Return <Status code={412} /> when the version doesn't match, and <Status code={428} /> when a required `If-Match` is missing.
- Parse `If-Match` per the spec: lists, `*` and weak tags are all valid inputs.

</InBrief>

Alice's fix vanishes. Nobody sees an error, and the bug report a week later says "prices randomly revert". This is the lost update, and it needs nothing more exotic than two browser tabs.

## Let everyone edit, and refuse stale writes

The instinctive fix is a lock: "I'm editing this, nobody else may." Pessimistic locking needs lock ownership, timeouts and a way to break locks held by someone who went to lunch. Over HTTP, where the mobile app vanishes into a tunnel without saying goodbye, that's rarely worth it. Optimistic concurrency lets everyone edit and makes a write succeed only if the resource is still at the version the client read. Conflicts are rare in most domains, so the occasional retry is cheaper than managing locks.

HTTP has this built in. The server sends a validator, the `ETag`, on reads. The client sends it back in `If-Match` on writes. If the resource has moved on, the server refuses with <Status code={412} />. Here's Bob's save, arriving one version too late:

```http
PUT /products/sku-1
If-Match: "v7"
{ "price": 10, "description": "Shoes" }

HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json
{ "type": "https://api.example.com/problems/version-mismatch", "status": 412,
  "detail": "sku-1 is now at version v8. Reload, reapply your change and retry." }
```

Bob's client can now reload, show him what changed, and let him reapply his edit.

## Compare and write in one statement

The natural first implementation reads the version, compares it in application code, then writes. It has a race window: two requests can both pass the check before either writes The comparison has to be atomic with the write. Notice the `WHERE` clause doing the real work:

```sql
UPDATE products
SET price = :price, description = :description, version = version + 1
WHERE id = :id AND version = :expected
RETURNING version;   -- no row returned: someone else won
```

`SELECT … FOR UPDATE` in a transaction, or a conditional write in DynamoDB or another store, are equivalent.

_Assumes:_ an integer `version` column; ETags are `"v<version>"`; `parse_if_match` implements the rules in the next section.

Here's the full handler. The early `parse_if_match` check gives a fast, friendly 412; the conditional update after it is what actually guarantees correctness.

```python
@app.put("/products/{sku}")
def replace_product(sku: str, body: ProductIn, response: Response,
                    if_match: Annotated[str | None, Header()] = None) -> Product:
    if if_match is None:
        raise problem(428, "if-match-required")
    current = products.version_of(sku)
    if current is None:
        raise problem(404, "product-not-found")
    if not parse_if_match(if_match).matches(f'"v{current}"'):
        raise problem(412, "version-mismatch", current_etag=f'"v{current}"')
    updated = products.update_if_version(sku, body, expected=current)  # UPDATE … WHERE version = :expected
    if updated is None:  # lost the race between the check and the write
        raise problem(412, "version-mismatch")
    response.headers["ETag"] = f'"v{updated.version}"'
    return updated
```

class ProductDetail(APIView):
    def put(self, request, sku):
        if_match = request.headers.get("If-Match") or problem(428, "if-match-required")
        serializer = ProductSerializer(data=request.data)

        updated = Product.objects.filter(sku=sku, version=current).update(
            **serializer.validated_data, version=F("version") + 1)
        if not updated:
            return problem(412, "version-mismatch")
        product = Product.objects.get(sku=sku)

  if (!ifMatch) return problem(c, 428, "if-match-required");

## Parse If-Match as the spec wrote it

`If-Match` looks like a single quoted string, and most hand-written parsers treat it as one. RFC 9110 §13.1.1 allows three other shapes:

- **A list:** `If-Match: "v7", "v8"` matches if any entry matches.
- **`*`:** matches if the resource exists at all, which makes `PUT` "update only, never create".
- **Weak tags:** `W/"v7"` never matches, because `If-Match` uses strong comparison. A request with only weak tags must fail with <Status code={412} />, not be treated as missing or be stripped of `W/` and compared.

A parser that does `if_match.strip('"') == str(version)` gets all three wrong, sometimes in the dangerous direction of letting writes through.

Its counterpart, `If-None-Match: *`, makes `PUT` "create only, never overwrite", which is useful with client-generated IDs.

## Make If-Match mandatory where people collide

An optional `If-Match` protects only the clients that remember it, and the ones that forget are back to last-write-wins. Larkspur Logistics' integration will certainly forget. For resources edited by several people or processes, require it and return <Status code={428} /> with a problem type that explains how to get an ETag. `PATCH` with JSON Merge Patch is less exposed because only the sent fields change, but two patches to the same field still race.

There are three ways to carry the version, and the HTTP-native one wins on most counts:

| Mechanism                               | Pros                                                      | Cons                                                                    |
| --------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| `ETag` + `If-Match`                     | HTTP-native; shared with caching; tooling understands 412 | Clients must read and send a header                                     |
| `version` field in the body             | Visible, easy for form-based clients                      | Not understood by HTTP tooling; easy to forget on `PATCH`               |
| `Last-Modified` + `If-Unmodified-Since` | Already present on many resources                         | One-second resolution: two writes in the same second collide undetected |

Whichever you pick, the check lives in the write:

<Note kind="history" title="The lost update problem, by name" year="1999" source="https://www.w3.org/1999/04/Editing/">

None of this is new. In 1999, while working on editing documents over HTTP, the W3C wrote up the "lost update problem" by name and proposed exactly this unreserved checkout: fetch with an entity tag, write back with `If-Match`, get 412 on conflict. The mechanism had been in HTTP/1.1 since 1997. Most lost-update bugs in APIs today come from not using it, not from it being missing.

</Note>

<WorkedProblem kind="Review" title="An If-Match parser">

```python
def check_if_match(header: str | None, current_version: int) -> None:
    if header is None:
        return
    tag = header.replace("W/", "").strip().strip('"')
    if tag != str(current_version):
        raise problem(412, "version-mismatch")
```

Find the bugs.

<Solution>

1. **Weak tags are made strong.** Stripping `W/` lets a weak validator satisfy `If-Match`, which RFC 9110 forbids. Weak-only headers must fail.
2. **`*` fails.** `If-Match: *` should succeed for any existing resource.
3. **Lists fail.** `"v7", "v8"` becomes `v7", "v8` and never matches.
4. **A missing header passes silently.** If the endpoint needs protection, return 428.
5. **Format mismatch.** ETags elsewhere are `"v7"`, but this compares against `7`, so valid tags never match.
6. **It's only a check.** Even when correct, the write must still use `WHERE version = :expected`, or two requests that both pass the check will both write.

</Solution>
</WorkedProblem>

## What to take away

A write should succeed only against the version the client actually saw, and the database, not your application code, should make that comparison. Concurrency protects writes that finish in milliseconds. Some work takes minutes, and the request can't wait for it; that's [long-running operations](/reliability/long-running-operations/).
