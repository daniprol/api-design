<InBrief>

- Return <Status code={202} /> with `Location` pointing at an operation resource for anything that may take longer than a few seconds.
- Give operations a small, fixed state machine and put either a result link or a problem object on the terminal state.
- Make the initiating request idempotent. Its response is the one most likely to be lost.
- Use `Retry-After` to pace polling, and add a webhook for clients that need to know at once.
- For batches, return <Status code={207} /> with a result per item and document whether the batch is atomic or best effort.

</InBrief>

Fernhill's finance team clicks Export for a year of orders. Load balancers cut idle connections at 60 seconds, so at minute four someone gets a 504. Did the export finish? Nobody knows, so they click again, and now two exports are grinding through the database. Exports, imports of a million products or provisioning a database take seconds to hours, and a single HTTP request is the wrong container for that. Model the work as a resource instead.

## Answer 202 and hand back a ticket

Accept the work, give the client something durable to ask about, and hang up. <Status code={202} /> says "accepted, not done", and `Location` points at the operation resource. Notice `Retry-After`: the server sets the polling pace.

```http
POST /exports
Idempotency-Key: 0b5f…
{ "kind": "orders", "created_after": "2026-01-01T00:00:00Z" }

HTTP/1.1 202 Accepted
Location: https://api.example.com/operations/op_91
Retry-After: 5
{ "id": "op_91", "status": "pending", "created_at": "2026-11-14T09:00:00Z" }
```

The client polls the operation with plain `GET` until it reaches a result link:

```http
GET /operations/op_91
→ 200 { "id": "op_91", "status": "running", "progress": { "completed": 4200, "total": 10000 } }

GET /operations/op_91
→ 200 { "id": "op_91", "status": "succeeded",
        "result": { "href": "https://api.example.com/exports/exp_33" } }
```

Some APIs answer a finished operation with <Status code={303} /> pointing at the result. That saves a step, but many HTTP clients follow redirects automatically, and the caller never sees the operation's final state. A result link in the body is more explicit. From the finance team's chair:

## Keep the states few and the endings complete

Every polling client writes a loop, and its exit condition is your state machine. Keep it small:

```text
pending ──► running ──► succeeded   (result link)
                  ├───► failed      (problem object)
                  └───► cancelled   (if you support DELETE or :cancel)
```

Clients write `while status not in ("succeeded", "failed", "cancelled")`, so the set of terminal states is part of the contract. Add a new one later and Larkspur's loop spins forever. A `failed` operation carries a full [problem object](/http/errors/), not a bare `"error": "failed"`. Keep operations readable for a documented period after completion, such as seven days, so a mobile app that was offline can still collect the outcome.

A generic `/operations/{id}` or a domain `/exports/{id}` with a `status` field is a style choice. Google (AIP-151) and Azure both use a generic operation resource. Domain resources read better when the job produces something that lives on afterwards.

## Make the request that starts the work idempotent

The `POST` that starts slow work is, awkwardly, the request most likely to time out, because it often does real work before answering. Without an [idempotency key](/reliability/idempotency/), a retry starts a second export or provisions a second database. Store the key with the operation ID, so a retry returns the same `202` and the same `Location`.

_Assumes:_ a durable queue (Celery, BullMQ, SQS or similar); `operations` is a table, not process memory.

Here's the handler. Notice that the operation row and the queued job commit together, so a crash can't strand an operation nobody will run.

<TabItem label="FastAPI">

```python
@app.post("/exports", status_code=202)
def start_export(body: ExportIn, response: Response, account: CurrentAccount,
                 idempotency_key: Annotated[str, Header()]):
    with db.begin():
        op = operations.get_by_key(account.id, idempotency_key)
        if op is None:
            op = operations.create(account.id, idempotency_key, kind="export", params=body)
            outbox.enqueue("run_export", op_id=op.id)  # same transaction: no lost jobs
    response.headers["Location"] = f"{BASE_URL}/operations/{op.id}"
    response.headers["Retry-After"] = "5"
    return op.to_api()
```

<TabItem label="Django">

```python
class ExportCreate(APIView):
    def post(self, request):
        key = request.headers.get("Idempotency-Key")
        if not key:
            return problem(400, "idempotency-key-required")
        with transaction.atomic():
            op, created = Operation.objects.get_or_create(
                account=request.user.account, idempotency_key=key,
                defaults={"kind": "export", "params": request.data})
            if created:
                transaction.on_commit(lambda: run_export.delay(op.pk))
        return Response(OperationSerializer(op).data, status=202,
                        headers={"Location": request.build_absolute_uri(op.get_absolute_url()),
                                 "Retry-After": "5"})
```

app.post("/exports", zValidator("json", ExportIn), async (c) => {

## Set the polling pace, and offer a push channel

Left alone, clients poll in a tight loop, which is a load test you didn't schedule. `Retry-After` on both the `202` and each `running` response tells them when to check again; vary it with the expected remaining time. For clients that need to know at once, add a [webhook](/events/webhooks/) such as `operation.completed`, and keep the operation resource as the source of truth for clients that missed the event. Browser clients can use server-sent events on `GET /operations/{id}`.

For work that is usually fast, `Prefer: respond-async, wait=10` (RFC 7240) lets one endpoint serve both cases: the server answers synchronously if the work finishes within ten seconds, and with `202` otherwise.

## Report batch outcomes per item with 207

Batch endpoints save round trips, but "97 of 100 succeeded" is neither <Status code={201} /> nor <Status code={400} />. Answer <Status code={207} /> with a result per item, in request order, so the client can match each outcome to what it sent:

```http
POST /products/batch
{ "items": [ {…}, {…}, {…} ] }

HTTP/1.1 207 Multi-Status
{
  "items": [
    { "status": 201, "id": "sku-1", "href": "https://api.example.com/products/sku-1" },
    { "status": 201, "id": "sku-2", "href": "https://api.example.com/products/sku-2" },
    { "status": 422, "problem": { "type": "…/validation-error", "errors": [ { "pointer": "#/price/amount", "detail": "must be > 0" } ] } }
  ]
}
```

<Status code={207} /> means "look inside", so clients must check each item, and so must any
monitoring that counts 2xx as success, or Priya's dashboard reports a perfect day while three
products failed. If the batch as a whole is invalid, such as malformed JSON, too many items or
missing authorisation, return a normal 4xx instead.

Document whether the batch is atomic (all or nothing, so a single status is enough) or best effort (per-item results). Cap the batch size and say what the cap is.

The status code is borrowed, which is why the body is your problem.

<Note kind="history" title="207 came from WebDAV" year="1999" source="https://www.rfc-editor.org/rfc/rfc4918#section-13">

Multi-Status was defined for WebDAV, where one `PROPFIND` or `DELETE` on a folder touches many files and some may fail. Its original body was XML. JSON APIs borrowed the status and replaced the body, which the spec doesn't define for them, so your per-item format is your own contract. Document it like any other schema.

</Note>

## What to take away

When work outlives a request, turn it into a resource: a `202`, an operation the client can poll, and an idempotent start so a retry never doubles the work. When one of those operations fails at 3 a.m., someone has to find out which client, which request and why, and that is [observability](/reliability/observability/).
