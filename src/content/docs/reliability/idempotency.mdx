<InBrief>

- Make every `POST` that creates or charges something idempotent. Clients can't tell a lost response from a failed request.
- Prefer a natural key where one exists: a client-generated ID with `PUT`, or a unique business reference.
- Otherwise accept an `Idempotency-Key`. Store the key, a request fingerprint and the response in the same transaction as the effect.
- Give in-progress keys a lease that expires, or a crashed worker blocks the key forever.
- Retry only idempotent requests, with capped exponential backoff and full jitter, and honour `Retry-After`.

</InBrief>

A client sends `POST /payments`. The payment succeeds, and then the connection drops before the response arrives. From the client's side, it has no idea whether the customer paid. Retrying may charge twice; not retrying may leave the order unpaid. Networks will put every client in that position eventually, so the server has to make "retry" the safe answer.

## Assume the client can't distinguish failure from success

A timeout covers three different situations:

```text
1. The request never arrived             → retrying is safe
2. It arrived and failed partway through → retrying is safe only if the failure rolled back
3. It succeeded and the response was lost → retrying duplicates the effect
```

The client sees the same thing in all three. `GET`, `PUT` and `DELETE` are idempotent by definition, so retrying them is fine. `POST` and `PATCH` are not, and those are usually the requests that create orders and move money.

## Prefer natural keys where the domain has one

The cheapest idempotency needs no extra machinery. If the client generates the resource's ID, creation becomes a `PUT` to a known URL, which is idempotent by definition:

```http
PUT /orders/ord_01JCX3N4Q8
{ "customer_id": "cus_7", "line_items": [ … ] }
→ 201 Created   (first time)
→ 200 OK        (repeat; a different body replaces the order, as PUT means)
→ 412 Precondition Failed  (repeat sent with If-None-Match: *, which makes PUT create-only)
```

A unique business reference does the same for `POST`: a merchant's `order_reference` with a unique constraint turns a duplicate into a <Status code={409} /> or a <Status code={303} /> to the existing order. Use these when they fit, and fall back to idempotency keys when they don't.

## Use an Idempotency-Key for everything else

The client generates a unique key per logical operation, typically a UUID, and sends it with every attempt. The server records the key with the outcome and replays the outcome on a retry.

```http
POST /payments
Idempotency-Key: 6d0d3a8e-7f5c-4c71-9a5b-0f3c1e2d4b9a
{ "amount": "49.00", "currency": "EUR", "order_id": "ord_42" }
```

| Situation                                   | Response                                                                                  |
| ------------------------------------------- | ----------------------------------------------------------------------------------------- |
| New key                                     | Execute; store key, fingerprint and response                                              |
| Known key, same fingerprint, completed      | Replay the stored status and body without executing                                       |
| Known key, different request body           | <Status code={422} />: the key was reused for a different operation                       |
| Known key, still in progress                | <Status code={409} />: try again shortly                                                  |
| Missing key on an endpoint that requires it | <Status code={400} />, as the IETF draft specifies (an exception to this site's 422 rule) |

Keep keys for at least as long as clients might retry. Stripe keeps them for 24 hours. Scope keys per account, so one customer's key can't collide with or reveal another's response.

## Store the outcome in the same transaction as the effect

The subtle part is atomicity. If you record "key done" in Redis and write the payment to Postgres, a crash between the two leaves them disagreeing: either the payment exists without a key, so a retry pays again, or the key exists without a payment, so a retry replays a success that never happened. Put the key row and the effect in one database transaction. When the effect is an external call, such as a card network, record progress in recovery points around it so a retry resumes rather than repeats, and pass your own idempotency key downstream.

_Assumes:_ PostgreSQL; an `idempotency_keys` table with a unique `(account_id, key)`, a fingerprint, a nullable response and a `locked_until` lease column.

<TabItem label="FastAPI">

```python
@app.post("/payments", status_code=201)
def create_payment(body: PaymentIn, account: CurrentAccount,
                   idempotency_key: Annotated[str | None, Header()] = None):
    if idempotency_key is None:
        raise problem(400, "idempotency-key-required")
    fp = hashlib.sha256(body.model_dump_json().encode()).hexdigest()
    with db.begin():
        rec = keys.claim(account.id, idempotency_key, fp, lease=timedelta(seconds=30))
        # claim(): INSERT … ON CONFLICT DO NOTHING, then SELECT … FOR UPDATE;
        # re-acquires the lease if locked_until has passed (a crashed worker).
        if rec.fingerprint != fp:
            raise problem(422, "idempotency-key-reused")
        if rec.response is not None:
            return JSONResponse(rec.response, status_code=rec.status)  # replay
        if not rec.lease_acquired:
            raise problem(409, "request-in-progress", headers={"Retry-After": "1"})
        payment = payments.create(body, account, upstream_key=idempotency_key)
        rec.complete(201, payment.model_dump(mode="json"))  # same transaction
    return payment
```

class PaymentCreate(APIView):
    def post(self, request):
        key = request.headers.get("Idempotency-Key") or problem(400, "idempotency-key-required")
        fp = fingerprint(request.data)
        with transaction.atomic():
            rec, _ = IdempotencyKey.objects.select_for_update().get_or_create(
                account=request.user.account, key=key, defaults={"fingerprint": fp})
            if rec.fingerprint != fp:
                return problem(422, "idempotency-key-reused")
            if rec.response is not None:
                return Response(rec.response, status=rec.status)  # replay
            if rec.locked_until and rec.locked_until > now():
                return problem(409, "request-in-progress", headers={"Retry-After": "1"})
            payment = create_payment(request.data, upstream_key=key)
            rec.status, rec.response = 201, PaymentSerializer(payment).data
            rec.save(update_fields=["status", "response"])  # commits with the payment
        return Response(rec.response, status=201)

app.post("/payments", zValidator("json", PaymentIn), async (c) => {
  const key = c.req.header("Idempotency-Key");
  if (!key) return problem(c, 400, "idempotency-key-required");

<Note kind="practice" title="Stripe's recovery points" year="2017" source="https://brandur.org/idempotency-keys">

Brandur Leach, then at Stripe, described an idempotency key design where each request moves through named recovery points ("started", "ride created", "charge created", "finished") stored on the key row in Postgres. A retry picks up from the last completed point instead of starting over or replaying blindly. It's the most complete public write-up of the pattern and worth reading before building your own.

</Note>

## Retry with capped, jittered backoff

Servers make retries safe; clients still have to retry well. A thousand clients that all retry after exactly one second turn a brief outage into a synchronised second outage.

- Retry only idempotent requests, or requests with an idempotency key, and only on transient failures: connection errors, <Status code={429} />, <Status code={502} />, <Status code={503} />, <Status code={504} />. Never retry 4xx validation errors.
- Use exponential backoff with full jitter: `sleep = random(0, min(cap, base × 2^attempt))`. AWS's 2015 analysis showed full jitter cuts total work and completion time compared with plain exponential backoff.
- Honour `Retry-After` when the server sends it, and cap attempts. Retry budgets, such as at most 10 percent extra load from retries, protect the server from your fleet.

<WorkedProblem kind="Review" title="The key that never comes back">

```python
@app.post("/payments")
def create_payment(body: PaymentIn, idempotency_key: Annotated[str, Header()]):
    if not redis.set(f"idem:{idempotency_key}", "in_progress", nx=True, ex=86400):
        saved = redis.get(f"idem:{idempotency_key}")
        if saved == "in_progress":
            raise problem(409, "request-in-progress")
        return json.loads(saved)
    payment = payments.charge(body)  # writes to Postgres, calls the card network
    redis.set(f"idem:{idempotency_key}", payment.model_dump_json(), ex=86400)
    return payment
```

A worker is killed by a deploy right after `payments.charge()` returns. What do the client's retries see, and what are the two separate bugs?

<Solution>

Every retry for the next 24 hours gets 409 "in progress", because the key was claimed and never completed or released. The customer was charged, but the client can never learn the outcome.

1. **No lease.** An in-progress claim needs a short expiry (seconds, not a day) that is renewed while working, so a crashed worker's claim lapses and a retry can take over.
2. **Dual write.** The key lives in Redis and the payment in Postgres, so they can't be updated atomically. Even with a lease, a retry after the crash would charge again. Store the key in the same database transaction as the payment, and pass the key to the card network so the external call is idempotent too.

Also missing: no request fingerprint, so the same key with a different amount replays the first payment, and keys aren't scoped per account.

</Solution>
</WorkedProblem>
