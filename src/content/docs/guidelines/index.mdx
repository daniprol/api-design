Several large API producers publish their design guidelines, and they don't agree. That's the useful part. A rule tells you what one organisation decided; two rules that contradict each other tell you there was a trade-off, and the reasons on each side tell you what it was.

## Where they agree

On the fundamentals, the guides are close to unanimous:

- Model the API around resources, and use HTTP methods with their standard meaning.
- Name things consistently, and make the rules checkable by a linter.
- Never break published clients. Prefer additive change to versioning.
- Paginate collections, return structured errors, and treat the API description as the contract.
- Treat the API as a product with consumers, not as a byproduct of an implementation.

## Why the differences exist

Consistency matters within an ecosystem much more than between ecosystems. A developer integrating fifty Google APIs gains from all of them looking alike; whether Google's choices match Zalando's matters far less to them. Google optimises for gRPC and generated clients, so `lowerCamelCase` and custom methods follow from protocol buffers. Zalando optimises for hundreds of teams publishing JSON over HTTP, so it prefers snake_case and forbids URL versions. Azure serves management planes for every cloud product, so it standardises long-running operations in detail. Pick the guide whose constraints look most like yours, and then be consistent with it.

<Note kind="practice" title="Linters make guidelines real" source="https://github.com/zalando/zally">

Guidelines that nobody checks become suggestions. Zalando's Zally, Google's `api-linter` and Azure's Spectral-based rulesets all turn their guidelines into failing builds, and rule numbers in a CI report tell a team exactly which paragraph to read. If you adopt a guide, adopt or write its linter in the same week.

</Note>
