<InBrief>

- Return `application/problem+json` (RFC 9457) for every 4xx and 5xx, including errors raised by the framework and the gateway.
- Clients branch on `type`, a stable URI that resolves to documentation. `title` and `detail` are for humans and may change.
- Report every validation failure in one response, each with a JSON Pointer to the offending field.
- Never return stack traces, SQL or internal hostnames. Return a trace ID and log the rest.
- Treat problem types as part of the contract: adding one is compatible; renaming one is a breaking change.

</InBrief>

Larkspur's integration starts failing on Monday. Their logs say `400 Bad Request` and nothing else; two days and three forwarded emails later, Priya finds a postcode one character too long. Your API spends much of its life saying no, and errors are where developers form their strongest opinions about it. A vague error becomes a support ticket, and an inconsistent one becomes a special case in every client. There's a standard format, and adopting it is mostly one exception handler per framework.

## Use Problem Details for every error

RFC 9457 (which replaced RFC 7807 in 2023) defines a small JSON object with its own media type. Notice that it answers the client's next question, how many are available, in a field code can read:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/insufficient-stock",
  "title": "Insufficient stock",
  "status": 422,
  "detail": "Only 2 units of sku-123 are available; the order requested 5.",
  "instance": "/orders/ord_8xK2",
  "sku": "sku-123",
  "available": 2
}
```

| Member     | Audience                                               | Stability                                                     |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| `type`     | Code: the identifier clients branch on                 | Stable, part of the contract. Should resolve to documentation |
| `title`    | Humans: summary of the problem type                    | Same for every occurrence of the type                         |
| `status`   | Logs and proxies that rewrite the code                 | Must match the HTTP status                                    |
| `detail`   | Humans: what happened this time, and what to do        | Free text, may be localised                                   |
| `instance` | Support: identifies this occurrence                    | Per occurrence                                                |
| extensions | Code: machine-readable context (`available`, `errors`) | Part of the contract, per type                                |

Code reads `type` and the extensions; people read `title` and `detail`. Once clients parse `detail`, you can never reword a message again. When there's nothing to add beyond the status code, `type` defaults to `about:blank` and `title` should be the standard reason phrase. Use that for generic <Status code={404} /> and <Status code={500} /> responses rather than inventing a type for each.

The non-obvious requirement is coverage. Framework 404s for unknown routes, 405s, 413s from the body-size limit and 502s from the gateway all need the same format, or clients end up with two parsers anyway. Test the error paths you didn't write.

## Report all validation failures at once, with pointers

A customer on a train fixes their email in the mobile app's sign-up form; now the postcode is wrong. Then the phone number. Three round trips on patchy signal, and they give up. A form that reveals one error per submission is a tax on every integrator. Collect all failures and point at each field with a JSON Pointer (RFC 6901) so clients can highlight it:

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request is not valid",
  "status": 422,
  "errors": [
    { "pointer": "#/email", "detail": "must be a valid email address" },
    { "pointer": "#/items/0/quantity", "detail": "must be between 1 and 99, got 120" }
  ]
}
```

RFC 9457 itself uses an `errors` array with `pointer` and `detail` in its examples, which makes this shape about as standard as it gets.

_Assumes:_ FastAPI with Pydantic v2, DRF 3.15 with a custom exception handler, Hono 4 with `@hono/zod-validator`. Every other page uses the helper defined here: `raise problem(status, slug, **extensions)` in FastAPI, `return problem(status, slug, ...)` in DRF, and `return problem(c, status, slug, ...)` in Hono.

Each stack does two jobs here: it renders validation errors as pointers, and it catches the framework's own errors so they share the format.

<TabItem label="FastAPI">

```python
PROBLEMS = "https://api.example.com/problems"

def problem_response(status: int, body: dict, headers: dict | None = None) -> JSONResponse:
    return JSONResponse({"status": status, **body}, status_code=status,
                        media_type="application/problem+json", headers=headers)

class Problem(Exception):  # raise problem(404, "order-not-found", order_id=...) anywhere
    def __init__(self, status: int, slug: str, headers: dict | None = None, **ext):
        self.status, self.slug, self.headers, self.ext = status, slug, headers, ext

problem = Problem

@app.exception_handler(Problem)
async def on_problem(request: Request, exc: Problem):
    return problem_response(exc.status, {"type": f"{PROBLEMS}/{exc.slug}", **exc.ext}, exc.headers)

@app.exception_handler(RequestValidationError)
async def on_validation(request: Request, exc: RequestValidationError):
    errors = [{"pointer": "#/" + "/".join(map(str, e["loc"][1:])), "detail": e["msg"]}
              for e in exc.errors()]
    return problem_response(422, {"type": f"{PROBLEMS}/validation-error",
                                  "title": "Your request is not valid", "errors": errors})

@app.exception_handler(StarletteHTTPException)  # covers unknown routes and 405s too
async def on_http(request: Request, exc: StarletteHTTPException):
    return problem_response(exc.status_code, {"type": "about:blank",
                                              "title": HTTPStatus(exc.status_code).phrase},
                            headers=getattr(exc, "headers", None))  # keeps WWW-Authenticate
```

<TabItem label="Django">

```python
# settings.py: REST_FRAMEWORK = {"EXCEPTION_HANDLER": "shop.errors.problem_handler"}
def problem_handler(exc, context):
    response = exception_handler(exc, context)
    if response is None:
        return None  # unhandled: Django returns a 500 (no traceback when DEBUG=False)
    body = {"type": "about:blank", "title": response.status_text, "status": response.status_code}
    if isinstance(exc, ValidationError):
        body |= {"type": f"{PROBLEMS}/validation-error", "title": "Your request is not valid",
                 "errors": list(pointers(exc.detail))}
    response.data = body
    response.content_type = "application/problem+json"
    return response

def pointers(detail, path=""):
    if isinstance(detail, dict):
        for key, value in detail.items():
            yield from pointers(value, f"{path}/{key}")
    elif isinstance(detail, list) and detail and not isinstance(detail[0], str):
        for i, value in enumerate(detail):
            yield from pointers(value, f"{path}/{i}")
    else:
        for message in detail if isinstance(detail, list) else [detail]:
            yield {"pointer": f"#{path or '/'}", "detail": str(message)}
```

## Never expose internals; return a trace ID instead

A stack trace is the most detailed error there is, written for exactly the wrong audience. Compare what each tells an attacker:

<Compare>
<Prefer>

```json
{
  "type": "about:blank",
  "title": "Internal Server Error",
  "status": 500,
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

The trace ID joins this response to your logs and traces.

</Prefer>
<Avoid>

```json
{
  "error": "psycopg.errors.UndefinedColumn: column \"pwd_hash\" of relation \"users\" does not exist (db.py:214)"
}
```

Database, table, column and file layout, in one line.

</Avoid>
</Compare>

Nobody writes code that returns stack traces. They escape through defaults: `DEBUG=True` in a Django settings file that reached production, or an unhandled exception in a framework whose development error page is on. So test the default, not your intentions: trigger an unhandled exception against a production-configured app and assert the body contains nothing but a problem object.

Authentication failures need the same care in `detail`. "No account with this email" versus "wrong password" tells an attacker which emails are registered. Return one message for both.

## Write details that say what to do next

Larkspur's two-day thread needed one sentence in the right place. A good `detail` answers what happened, why, and what the caller can do about it:

| Unhelpful         | Helpful                                                                                |
| ----------------- | -------------------------------------------------------------------------------------- |
| `Invalid request` | `quantity must be between 1 and 99, got 120.`                                          |
| `Forbidden`       | `This API key is read-only. Create a key with the orders:write scope to place orders.` |
| `Unsupported`     | `Currency BTC is not supported. Supported: EUR, USD, GBP.`                             |

Stripe goes one step further, and the idea transfers directly.

<Note kind="practice" title="Stripe's doc_url" source="https://docs.stripe.com/api/errors">

A Stripe error carries a machine-readable `code` such as `card_declined`, a `decline_code` such as `insufficient_funds`, a `param` naming the offending field, and a `doc_url` linking to a page about that specific error. A developer stuck at midnight follows the link instead of opening a ticket. That last field is exactly what RFC 9457's `type` URI is for: make every problem type resolve to its own documentation page.

</Note>

<WorkedProblem kind="Design" title="An error catalogue for checkout">

Checkout can fail because a SKU is out of stock, a coupon has expired, the shipping address is outside the delivery area, or the payment provider is down. Define the problem types, status codes and extension members.

<Solution>

| `type` (under `/problems/`)    | Status              | Extensions                       |
| ------------------------------ | ------------------- | -------------------------------- |
| `insufficient-stock`           | 422                 | `sku`, `available`               |
| `coupon-expired`               | 422                 | `coupon`, `expired_at`           |
| `undeliverable-address`        | 422                 | `country`, `supported_countries` |
| `payment-provider-unavailable` | 503 + `Retry-After` | none                             |

Each type gets a documentation page at its URI. The first three are fixable by the user, so they're 4xx; the provider outage is transient and retryable, so it's 503.

**Alternatives.** Some teams use one generic `checkout-failed` type with a `reason` extension. That works, but clients then branch on an extension instead of `type`, and generic Problem Details tooling can't see the distinction.

</Solution>
</WorkedProblem>

## What to take away

An error is an interface too: one format everywhere, a stable `type` for code to branch on, every validation failure at once, and nothing internal in the body. A problem response is recognised by its media type, and media types, tracing and much else are negotiated in headers. That's [headers and content negotiation](/http/headers/).
