<InBrief>

- Reach for a registered header before inventing one. If you must invent one, drop the `X-` prefix and use Structured Field syntax.
- Propagate `traceparent` (W3C Trace Context) on every hop and return a trace ID in error bodies.
- Support `Prefer: return=minimal` on writes and `respond-async` on slow operations, and confirm with `Preference-Applied`.
- Let `Accept` choose formats and `Accept-Language` choose languages. Always send `Vary` for the headers you negotiated on.
- Keep data in the body, not in headers: headers are for metadata that intermediaries act on.

</InBrief>

Monday morning: the mobile app asked for JSON and got a spreadsheet. Priya spends an hour in the logs before she finds it. The CDN cached a CSV response and served it to everyone, because nothing told it the response depended on `Accept`.

Headers are a language every proxy, CDN, client library and tracer already speaks. Use the registered ones and you get their behaviour for free; invent your own and you get behaviour nobody implements. The [Headers reference](/reference/headers/) lists them; this page covers the decisions.

## Borrow a registered header before inventing one

The temptation is to mint `X-Fernhill-Retry-In`. Resist it. Most metadata an API needs already has a standard or draft-standard header: `Location` for where a created resource lives, `Retry-After` for when to try again, `ETag` and `If-Match` for versions, `Idempotency-Key` for retries, `RateLimit` and `RateLimit-Policy` for quotas (an IETF draft that many gateways already implement). Each comes with defined semantics and, often, existing client support.

When nothing fits, give the new header a plain name and a value in Structured Field syntax (RFC 9651): a list, dictionary or item with defined parsing rules. The alternative is another ad hoc comma-separated format, and someone at Larkspur Logistics writing a regex for it.

<Note kind="history" title="The end of X-" year="2012" source="https://www.rfc-editor.org/rfc/rfc6648">

For years, experimental headers wore an `X-` prefix so they wouldn't collide with standard ones. Then the experiments succeeded, and by then they couldn't be renamed: `X-Forwarded-For` is still everywhere, while its standard replacement `Forwarded` is far rarer. RFC 6648 deprecated the convention in 2012. The lesson: name new headers as if they might succeed.

</Note>

## Location and Content-Location mean different things

The two names look like a pair, and they answer different questions. `Location` points somewhere else: the resource just created (with <Status code={201} />), a status monitor (with <Status code={202} />) or a redirect target. It says "go there". `Content-Location` describes the body in this response: "what you're holding is a representation of that URL". One is a pointer, the other is a label on the parcel.

Here's a create where the two agree. The mobile app posts an order and gets the order back:

```http
HTTP/1.1 201 Created
Location: https://api.example.com/orders/ord_42
Content-Location: https://api.example.com/orders/ord_42
Content-Type: application/json

{"id": "ord_42", "status": "pending", "total": {"amount": "129.00", "currency": "EUR"}}
```

`Location` tells the app where the new order lives. `Content-Location` adds the promise that this body is the order's current state, not a receipt or a "created" message, so the app can store it as its copy of `ord_42` without a follow-up `GET` (RFC 9110 §8.7). Without that header, the body could legitimately be anything.

They differ when the body represents a resource other than the one you asked for and nothing has moved. A `GET /customers/cus_7/orders/latest` that answers <Status code={200} /> with `Content-Location: https://api.example.com/orders/ord_42` says "the latest order is this one, and here it is"; there's no `Location`, because the client isn't being sent anywhere. The same goes for a `POST` to a search resource whose results have their own URL. You'll rarely need `Content-Location` beyond these cases, and it never replaces `Location` on a 201. Zalando goes further and discourages `Content-Location` altogether, because its caching semantics are easy to get wrong. If you leave it out, document that the 201 body is the full resource, and clients get the same guarantee from the contract instead of the header.

Make `Location` absolute. Relative references have been allowed since RFC 7231, but clients resolve them against whatever URL they used, and behind a gateway that may not be the URL you think.

## Carry the trace ID on every hop

One Fernhill checkout can trigger thirty internal calls. When it fails, the only thing that ties Priya's logs together is a correlation ID carried through every hop. The standard is W3C Trace Context: a `traceparent` header carrying trace ID, parent span ID and flags, plus an optional `tracestate`. OpenTelemetry instrumentations read and write it automatically for most HTTP clients and servers, so the real work is making sure nothing drops it, such as a hand-rolled HTTP client or a message queue hop. The trace ID is the second field:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

Older organisations often have their own header, like Zalando's `X-Flow-ID`. If you have one, propagate both during migration. And put the trace ID into every [error body](/http/errors/), so a support ticket leads straight to the trace.

_Assumes:_ OpenTelemetry auto-instrumentation is not available, so propagation is done by hand.

Here's the middleware. Notice that a missing or malformed `traceparent` never fails the request: it mints a fresh ID.

<Tabs syncKey="stack">
<TabItem label="FastAPI">

```python
trace_id: ContextVar[str] = ContextVar("trace_id", default="-")

@app.middleware("http")
async def trace_context(request: Request, call_next):
    parent = request.headers.get("traceparent", "")
    tid = parent.split("-")[1] if parent.count("-") == 3 else secrets.token_hex(16)
    trace_id.set(tid)
    response = await call_next(request)
    response.headers["Trace-Id"] = tid  # handy for support; the body carries it on errors too
    return response
```

## Honour Prefer where it saves work

The mobile app on a train doesn't need the full order echoed back after a `PATCH` whose result it already knows. `Prefer` (RFC 7240) lets a client state optional preferences like that. The server may ignore them, and confirms the ones it applied with `Preference-Applied`:

```http
PATCH /orders/ord_42
Prefer: return=minimal              → 204 No Content, Preference-Applied: return=minimal

POST /reports
Prefer: respond-async, wait=10      → 202 Accepted after 10 s if not finished
```

`return=minimal` saves bandwidth for clients that already know the new state. `respond-async` with `wait` is the cleverer one: a single endpoint answers synchronously when the work is fast and with <Status code={202} /> when it isn't, which beats maintaining two endpoints. The third common preference is `handling=strict` versus `handling=lenient`, for clients that want unknown fields rejected rather than ignored.

## Let Accept pick the format and the language

Finance wants orders as CSV; the apps want JSON. The quick fix is `/orders.csv` or `?format=csv`, and soon every resource grows a suffix. Let the client choose with `Accept` instead:

```http
GET /orders?created_after=2026-11-01
Accept: text/csv
```

Answer <Status code={406} /> if you can't produce any acceptable type, or fall back to your default type. RFC 9110 allows both, and the fallback is friendlier to browsers. Then add `Vary: Accept` so caches store the variants separately. Forget it and you get Priya's Monday morning: a CDN serving a cached CSV to the next client that asked for JSON.

Languages work the same way. `Accept-Language: es-ES, es;q=0.9, en;q=0.5` uses BCP 47 tags with quality values, the response names its choice in `Content-Language`, and `Vary: Accept-Language` keeps caches honest. Translate text meant for people, such as problem `title` and `detail`. Never translate what code reads: enum values, problem `type` URIs and field names stay in one language.

Some data legitimately exists in several languages at once, like product names in a catalogue. There, put a language map in the body instead of negotiating:

```json
{ "id": "sku-123", "name": { "en": "Linen shirt", "es": "Camisa de lino", "de": "Leinenhemd" } }
```

In short, the protocol carries the negotiation and the URL stays the same:

Choose header names carefully; HTTP carries a reminder in every browser request.

<Note kind="curiosity" title="Referer" year="1996" source="https://www.rfc-editor.org/rfc/rfc1945#section-10.13">

The `Referer` header is misspelled, and has been since HTTP/1.0 in RFC 1945. Nobody caught it before it shipped, so every browser sends it that way and every spec since keeps it. The later `Referrer-Policy` header is spelled correctly, so the web now has both. A header name is as permanent as a URL.

</Note>

## What to take away

Headers are a vocabulary that every proxy, cache and tracer already understands, so speak it before inventing words of your own, and always tell caches what you negotiated on with `Vary`. The body is the other half of the contract, and its conventions are where most API arguments start: casing, envelopes, `null` versus absent. That's [JSON conventions](/representations/json/).
