<InBrief>

- For public and cross-team HTTP APIs, aim for Richardson level 2: resources, standard methods, meaningful status codes.
- Treat hypermedia (level 3) as optional and targeted: links for pagination and next actions, not a full HATEOAS client.
- Choose gRPC for internal, latency-sensitive service calls with generated clients on both sides.
- Choose GraphQL when many clients need differently shaped reads of one graph and you own those clients.
- Use events when the producer shouldn't know or wait for its consumers.

</InBrief>

Fernhill's architecture review has three proposals on the table: "make it RESTful", "use GraphQL like everyone else", and "gRPC, obviously". Nobody in the room means the same thing by the first one. "REST" is the most used and least precise word in API design; most APIs that claim it are JSON over HTTP with resource-shaped URLs, and that's usually a fine place to be. What matters is knowing which properties a style buys you, which you've given up, and when another style is the better tool.

## REST is a set of constraints, and the useful ones are about intermediaries

Roy Fielding defined REST in chapter 5 of his 2000 dissertation as the architectural style behind the web, which he had helped specify as an author of HTTP/1.1. Read that way, the constraints stop looking academic: each lets software you don't own help you:

| Constraint                | What it buys an API                                                                 |
| ------------------------- | ----------------------------------------------------------------------------------- |
| Client–server             | Client and server evolve independently                                              |
| Stateless                 | Any instance can serve any request; horizontal scaling and simple failover          |
| Cacheable                 | Responses declare their own freshness, so caches and CDNs can serve them            |
| Uniform interface         | Generic tooling understands methods, status codes and media types without your docs |
| Layered system            | Gateways, proxies and load balancers can sit in between, invisible to clients       |
| Code on demand (optional) | Rarely relevant to APIs                                                             |

The uniform interface is the one that pays daily. When the mobile app's retry middleware sees a `GET`, it knows retrying is safe without reading a line of your docs. A small, fixed set of methods with known semantics lets retry logic, caches and observability tools work without configuration.

## Aim for level 2 of the Richardson maturity model

"RESTful" settles no arguments, so you need a finer ruler. Leonard Richardson's model, popularised by Martin Fowler in 2010, grades an API by how much of HTTP it uses. Here is "cancel order 42" at each level; watch where the meaning moves out of the body and into the protocol:

```http
# Level 0: one endpoint, everything in the body
POST /api   {"action": "cancelOrder", "order_id": "ord_42"}

# Level 1: resources, but POST for everything and 200 for every outcome
POST /orders/ord_42/cancel

# Level 2: methods for meaning, status codes for outcomes
POST /orders/ord_42/cancellation      → 201 Created
GET  /orders/ord_42                   → 200 OK   {"status": "cancelled"}
GET  /orders/ord_99                   → 404 Not Found

# Level 3: the representation links to what the client can do next
{"id": "ord_42", "status": "placed",
 "links": {"cancellation": {"href": "https://api.example.com/orders/ord_42/cancellation"}}}
```

Level 2 is where the intermediary benefits arrive, which is why most guidelines mandate it. Level 3 adds discoverability, but fully hypermedia-driven clients remain rare outside the browser; Larkspur's integration will never follow a link it wasn't hard-coded to follow. The practical middle ground is in [Links](/representations/links/): absolute links for pagination, related resources and state-dependent actions.

The man who coined the term has views on all this.

<Note kind="history" title="REST APIs must be hypertext-driven" year="2008" source="https://roy.gbiv.com/untangled/2008/rest-apis-must-be-hypertext-driven">

By 2008, Fielding had watched one too many hypermedia-free APIs call themselves REST, and wrote a blog post saying so: by his definition, they are not. The industry listened politely and kept the word, which is why "RESTful" now usually means "level 2". Use the levels when you need precision: "level 2 with links for pagination" says more than "REST".

</Note>

## Compare the alternatives by their trade-offs, not their popularity

Back to that review meeting. Each proposal optimises for something different, and none is a successor to the others; large organisations commonly run all of them. The table is the honest argument:

|                     | REST (level 2)                        | RPC over HTTP                  | GraphQL                                      | gRPC                          | Async messaging               |
| ------------------- | ------------------------------------- | ------------------------------ | -------------------------------------------- | ----------------------------- | ----------------------------- |
| Unit of design      | Resource                              | Procedure                      | Typed graph and queries                      | Service and method (protobuf) | Event or message type         |
| HTTP caching        | Native                                | Rarely                         | Hard (mostly `POST`); persisted queries help | No                            | n/a                           |
| Over/under-fetching | Mitigated with `fields` and embedding | Per procedure                  | Client chooses fields                        | Per method                    | Event carries what it carries |
| Contract            | OpenAPI                               | OpenAPI, JSON-RPC              | Schema (SDL)                                 | `.proto` files                | AsyncAPI, schema registry     |
| Browser clients     | Yes                                   | Yes                            | Yes                                          | Needs gRPC-Web or a proxy     | Via a gateway                 |
| Streaming           | SSE, chunked responses                | Rare                           | Subscriptions                                | Native, bidirectional         | Native                        |
| Typical home        | Public and partner APIs               | Internal actions, simple tools | Product frontends with varied screens        | Internal service mesh         | Integration between domains   |

Some trade-offs only show up in production, usually on Priya's watch:

- **GraphQL moves cost control to the server.** A single query can fan out into thousands of resolver calls, so you need depth and complexity limits, and caching moves from HTTP into the client and resolvers. It works best when the same organisation owns the schema and its main clients.
- **gRPC requires HTTP/2 end to end**, generated stubs on both sides, and tooling that can read binary payloads. In return you get strict contracts, compact messages and deadlines that propagate across calls.
- **RPC over HTTP is honest about being RPC.** `POST /v1/orders:cancel` style endpoints (Google's custom methods) are a reasonable compromise for the few operations that are not resource state changes.
- **Asynchronous messaging decouples in time.** The producer doesn't wait for consumers or know how many there are. The price is eventual consistency, duplicate delivery and harder debugging ([Event design](/events/event-design/)).

## Keep the level 2 discipline in code

Frameworks make level 2 the path of least resistance; the work is in not escaping it. Here is the order resource in three stacks. Notice that cancellation is a `POST` that creates a resource and answers 201, not a verb hiding in the URL.

_Assumes:_ `OrderOut`, `CancellationIn` and an `orders.cancel()` service defined elsewhere; the `problem()` helper from [Errors](/http/errors/).

<Tabs syncKey="stack">
<TabItem label="FastAPI">

```python
router = APIRouter(prefix="/orders")

@router.get("/{order_id}")
def get_order(order_id: str) -> OrderOut: ...

@router.patch("/{order_id}")
def update_order(order_id: str, patch: OrderPatch) -> OrderOut: ...

@router.post("/{order_id}/cancellation", status_code=201)
def cancel_order(order_id: str, body: CancellationIn) -> CancellationOut: ...
```

</TabItem>
<TabItem label="Django">

```python
class OrderViewSet(viewsets.ModelViewSet):
    queryset = Order.objects.all()
    serializer_class = OrderSerializer

    @action(detail=True, methods=["post"], url_path="cancellation")
    def cancellation(self, request, pk=None):
        cancellation = cancel(self.get_object(), request.data)
        return Response(CancellationSerializer(cancellation).data, status=201)
```

</TabItem>
<TabItem label="Hono">

```ts
const orders = new Hono()
  .get("/:id", (c) => c.json(getOrder(c.req.param("id"))))
  .patch("/:id", async (c) => c.json(await updateOrder(c.req.param("id"), await c.req.json())))
  .post("/:id/cancellation", async (c) => c.json(await cancel(c.req.param("id")), 201));

app.route("/orders", orders);
```

</TabItem>

The escape usually happens one endpoint at a time, and it looks like this:

<Compare>
<Prefer label="Level 2">

```http
GET    /orders/ord_42
DELETE /orders/ord_42
```

The method says what, the URL says which.

</Prefer>
<Avoid label="Level 0 in disguise">

```http
POST /getOrder     {"id": "ord_42"}
POST /deleteOrder  {"id": "ord_42"}
```

Caches, proxies and retry logic can't tell reads from writes.

</Avoid>
</Compare>

gRPC's own assumptions make more sense once you know where it came from.

<Note kind="curiosity" title="Why it's called gRPC" source="https://github.com/grpc/grpc/blob/master/doc/g_stands_for.md">

The "g" officially stands for something different in every release: "good", "green", "gorgeous", "glamorous" and so on, listed in the repository. It grew out of Stubby, Google's internal RPC system, which is why its design assumes generated clients, deadlines and a controlled network.

</Note>

## What to take away

Pick a style for what it lets other software do for you: level 2 REST for public and partner APIs, gRPC inside the mesh, GraphQL when you own varied clients, events when the producer shouldn't wait. Level 2 only pays off if your URLs name things rather than actions, which is where [resources and actions](/modelling/resources/) comes in.
