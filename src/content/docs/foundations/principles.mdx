<InBrief>

- Treat any API with a consumer outside your team as a product with users, support costs and a retirement date.
- Write and review the contract before the implementation. The format matters less than the review.
- Keep an explicit API model between storage and the wire. Never serialise ORM rows directly.
- Optimise for consistency over local elegance: a consumer who learns one endpoint should be able to guess the rest.

</InBrief>

A Fernhill developer renames a column from `stat_cd` to `status_code` on a Tuesday. On Wednesday, Larkspur Logistics stops booking shipments, because their integration reads `stat_cd` straight from the response. On a whiteboard, that rename cost five minutes; now it costs a quarter, two migration guides and an awkward meeting. Every principle below moves mistakes to the cheap end of that curve.

## Design for the consumer's job, not your schema

The moment someone outside your team calls your endpoint, the API has users, a learning curve, a support channel and a lifecycle. So the product questions come before code: who calls this, what are they trying to get done, and what is the smallest surface that lets them do it?

The commonest way to fail those questions is to hand over your storage and call it an interface. Both responses below describe the same order; read the right-hand one as Larkspur would, without your schema:

## Keep an explicit API model between storage and the wire

Nobody decides to leak their schema. Frameworks make serialising a model straight to JSON a one-liner, and one-liners win on a Friday afternoon. A separate API model costs one mapping function per resource. In exchange, you can rename a column, split a table or add a sensitive field, and the wire never notices.

_Assumes:_ Pydantic v2, Django REST Framework 3.15, Hono 4. `Order` rows come from your persistence layer.

Here is the mapping. Notice that `status` becomes a word, not a code, and the total a decimal string with its currency.

<Tabs syncKey="stack">
<TabItem label="FastAPI">

```python
class Money(BaseModel):
    amount: str  # decimal string: no binary floating point on the wire
    currency: str  # ISO 4217

class OrderOut(BaseModel):  # the public contract, not the ORM model
    id: str
    status: Literal["placed", "paid", "shipped", "delivered", "cancelled"]
    total: Money
    created_at: datetime

def to_api(row: OrderRow) -> OrderOut:
    return OrderOut(
        id=row.public_id,
        status=STATUS_NAMES[row.stat_cd],
        total=Money(amount=f"{row.total:.2f}", currency=row.currency),
        created_at=row.created_at,
    )
```

</TabItem>
<TabItem label="Django">

```python
class OrderSerializer(serializers.ModelSerializer):
    id = serializers.CharField(source="public_id")
    status = serializers.CharField(source="get_status_display")
    total = serializers.SerializerMethodField()

    class Meta:
        model = Order
        fields = ["id", "status", "total", "created_at"]  # never "__all__"

    def get_total(self, order: Order) -> dict:
        return {"amount": f"{order.total:.2f}", "currency": order.currency}
```

</TabItem>
<TabItem label="Hono">

```ts
type OrderOut = {
  id: string;
  status: "placed" | "paid" | "shipped" | "delivered" | "cancelled";
  total: { amount: string; currency: string };
  created_at: string;
};

const toApi = (row: OrderRow): OrderOut => ({
  id: row.publicId,
  status: STATUS_NAMES[row.statCd],
  total: { amount: row.total.toFixed(2), currency: row.currency },
  created_at: row.createdAt.toISOString(),
});
```

</TabItem>

So `fields = "__all__"` or `return c.json(row)` in a public handler is a design decision made by accident. From that day on, every migration is a potential breaking change.

## Review the contract before the implementation

Otherwise the mobile team discovers your pagination scheme the week before their release, and the fix becomes a special case in an app that takes weeks to reach every phone. API first means the contract is a deliberate artefact, reviewed by the people who will call it, before the code exists. It does not require hand-written YAML. Two workflows reach the same place:

| Approach     | How                                                                   | Fits                                                       |
| ------------ | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| Design first | Write OpenAPI, review it, generate mocks, then implement against it   | Public APIs, several consuming teams, long-lived contracts |
| Code first   | Write typed route stubs, generate the spec, review the generated diff | Small teams, internal APIs, fast iteration                 |

Both need a review where consumers see the contract while changing it is still cheap, and a spec that is checked in, versioned and linted in CI ([Specs in CI](/evolution/specs-in-ci/) covers the tooling). A generated spec is only as good as the types and descriptions behind it, so treat a missing `description` the way you'd treat a missing test. A useful one looks like this:

```yaml title="openapi.yaml (excerpt)"
paths:
  /orders/{order_id}/cancellation:
    post:
      summary: Cancel an order
      description: |
        Only orders in status `placed` or `paid` can be cancelled.
        Shipped orders are returned through POST /returns instead.
      responses:
        "201": { $ref: "#/components/responses/Cancellation" }
        "409": { $ref: "#/components/responses/Problem" }
```

The description carries what the path can't: the precondition, the alternative route for shipped orders, and the error a client should expect. "Cancel order endpoint" tells the reader nothing the path didn't.

Amazon turned this into an order two decades ago.

<Note kind="history" title="The Bezos API mandate" year="2002" source="https://courses.cs.washington.edu/courses/cse452/22wi/papers/yegge-platform-rant.html">

Steve Yegge retold it in a 2011 Google+ post he accidentally made public. Jeff Bezos had ordered every Amazon team to expose its data only through service interfaces designed to be externalisable, with no back doors into each other's databases. Those interfaces could later be sold to outsiders, which is roughly what AWS became. Design internal APIs as if strangers will call them, and you keep that option open.

</Note>

## Optimise for consistency over local elegance

Consumers learn your API by pattern-matching. Once Priya has called two Fernhill collections, she should be able to guess the third. If one paginates with `cursor` and another `page`, or one resource says `created_at` and another `creationDate`, every endpoint has to be learned on its own and every client library grows special cases. A slightly worse convention applied everywhere beats a better one applied in one place. That is the real job of a style guide: it settles arguments once, so reviews can focus on the domain.

Most guidelines aim for the same handful of qualities. The API should be understandable from names alone and easy to use correctly. It should be hard to misuse, so mistakes produce clear errors rather than corrupt data. It should be consistent and abstract from the backend. And it should evolve for years without breaking anyone, which is harder than it sounds:

<Note kind="aside" title="Hyrum's Law" source="https://www.hyrumslaw.com/">

"With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviours of your system will be depended on by somebody." Response field order, error message wording, the latency of a slow endpoint. The practical consequence: expose as little as possible, because everything you expose becomes contract.

</Note>

<WorkedProblem kind="Review" title="A new field for the mobile team">

The mobile team needs `estimated_delivery` on orders. The quickest change is:

```python
class OrderSerializer(serializers.ModelSerializer):
    class Meta:
        model = Order
        fields = "__all__"
```

What does this ship besides the new field?

<Solution>

Every column on `Order`, now and in future: internal status codes, foreign keys, and whatever someone adds next quarter, possibly a fraud score. Each later migration becomes a public change, and removing any of those fields is now a breaking change because someone will have started reading them.

Add `estimated_delivery` to the explicit field list, with a type and description in the spec.

**Alternatives.** If the field is expensive to compute, make it opt-in via a `fields` or `embed` parameter (see [Filtering and sorting](/collections/filtering/)) instead of adding it to every response.

</Solution>
</WorkedProblem>

## What to take away

Users depend on everything they can see, so decide what they see on purpose: an explicit API model, a contract reviewed before the code, conventions that hold everywhere. Next comes the style of that contract, and whether REST is the right shape. That's [REST and alternatives](/foundations/rest-and-alternatives/).
