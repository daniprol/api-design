<InBrief>

- Sign every delivery with HMAC-SHA256 over the delivery ID, a timestamp and the raw body. Receivers verify before parsing, and reject stale timestamps.
- Give each event a stable ID that stays the same across retries, so receivers can deduplicate.
- Treat only 2xx as success. Retry everything else with exponential backoff and jitter for days, then disable the endpoint and tell a human.
- Receiver URLs are attacker-supplied. Send from workers that can't reach your internal network.
- Ask receivers to verify, enqueue and answer 2xx within seconds, and to process asynchronously.

</InBrief>

Larkspur Logistics asks Fernhill for newly paid orders every thirty seconds, day and night. It's a child in the back seat asking "are we there yet?": most answers are no, each one costs a request, and the real answer still arrives up to thirty seconds late. A webhook inverts the conversation. The client registers a URL, and you `POST` to it when something happens. It's the cheapest way to push events across organisational boundaries, which is why every payment, source-control and messaging platform offers one. It's also an HTTP request from your servers to a URL a stranger typed into a form, and that sentence contains most of this page's advice.

## Adopt the standard envelope instead of inventing one

Every provider used to invent its own headers and signature format, and every receiver wrote a bespoke verifier for each. Standard Webhooks, a specification written by a group of webhook-sending companies, settles those details. Adopt it unless you have a reason not to; receivers then verify your deliveries with an existing library. In this delivery, the three `webhook-` headers carry everything the receiver needs to trust it:

```http
POST /hooks/shop HTTP/1.1
Host: partner.example.net
Content-Type: application/json
webhook-id: msg_2KWPBgLlAfxdpx2AI54pPJ85f4W
webhook-timestamp: 1767225600
webhook-signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{"type": "order.shipped", "timestamp": "2026-01-01T00:00:00Z",
 "data": {"order_id": "ord_42", "shipment_id": "shp_9"}}
```

| Header              | Meaning                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `webhook-id`        | The message ID. Identical on every retry of the same event, so receivers deduplicate on it. |
| `webhook-timestamp` | Unix seconds when this attempt was signed. Receivers reject values too far from now.        |
| `webhook-signature` | Space-separated list of `v1,<base64 HMAC>`. More than one entry during secret rotation.     |

Public webhook types follow the `resource.past_tense` style that Stripe and GitHub use (`order.shipped`), which reads well in a subscription UI. Internal event types on a bus stay namespaced kebab-case (`shop.order-placed`, see [Event design](/events/event-design/)). Pick one style per audience and document it.

And keep payloads small. A "thin" event carries the type and the resource ID and lets the receiver fetch the current state through the API. That avoids stale snapshots, avoids leaking data to a URL that changed hands, and sidesteps ordering problems. Stripe now recommends this shape for new integrations.

## Sign the ID, the timestamp and the body together

A webhook endpoint is a public URL that triggers business actions. Without a signature, anyone who learns it can mark orders as paid. So sign: an HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{raw body}` with a per-endpoint secret. Why all three parts? The timestamp stops replays of an old, captured delivery, and the ID stops an attacker from swapping IDs to defeat deduplication. Leave either out and you've signed a cheque with the amount blank.

The receiver must verify against the raw bytes before any JSON parsing, because re-serialising changes whitespace and key order and the signature no longer matches. Compare in constant time, accept any matching `v1` entry so secrets can rotate, and reject timestamps more than a few minutes old. In each receiver below, notice the raw body is verified before anything touches the JSON.

_Assumes:_ the per-endpoint secret is stored base64-encoded after the `whsec_` prefix, as Standard Webhooks specifies; `TOLERANCE` is 300 seconds.

<TabItem label="FastAPI">

```python
def verify(secret: str, msg_id: str, ts: str, body: bytes, header: str) -> bool:
    if abs(time.time() - int(ts)) > TOLERANCE:
        return False
    key = base64.b64decode(secret.removeprefix("whsec_"))
    expected = base64.b64encode(hmac.new(key, f"{msg_id}.{ts}.".encode() + body, "sha256").digest()).decode()
    return any(hmac.compare_digest(expected, sig.split(",", 1)[1])
               for sig in header.split() if sig.startswith("v1,"))

@app.post("/hooks/shop", status_code=204)
async def receive(request: Request, webhook_id: Annotated[str, Header()],
                  webhook_timestamp: Annotated[str, Header()], webhook_signature: Annotated[str, Header()]):
    body = await request.body()  # raw bytes, not request.json()
    if not verify(SECRET, webhook_id, webhook_timestamp, body, webhook_signature):
        raise problem(401, "invalid-webhook-signature")
    await queue.enqueue("shop-events", id=webhook_id, body=body)  # dedupe and process later
```

```ts
app.post("/hooks/shop", async (c) => {
  const body = await c.req.text(); // raw body, before any JSON.parse
  const id = c.req.header("webhook-id") ?? "";
  const ts = c.req.header("webhook-timestamp") ?? "";
  if (Math.abs(Date.now() / 1000 - Number(ts)) > TOLERANCE) return problem(c, 401, "stale-webhook");

  const key = await crypto.subtle.importKey(
    "raw",
    base64ToBytes(SECRET.slice(6)),
    { name: "HMAC", hash: "SHA-256" },
    false,
    ["sign"],
  );
  const mac = bytesToBase64(
    new Uint8Array(await crypto.subtle.sign("HMAC", key, encode(`${id}.${ts}.${body}`))),
  );
  const sigs = (c.req.header("webhook-signature") ?? "")
    .split(" ")
    .filter((s) => s.startsWith("v1,"));
  if (!sigs.some((s) => timingSafeEqual(s.slice(3), mac)))
    return problem(c, 401, "invalid-webhook-signature");

  await queue.send({ id, body });
  return c.body(null, 204);
});
```

## Retry for days, then stop and tell someone

Larkspur's server will be down at some point: a deploy, an expired TLS certificate, a migration that runs into the weekend. Give up after a minute and those events are gone. So treat only 2xx as delivered, and retry with exponential backoff and jitter on a schedule that spans days. Redirects count as failures too: the receiver should update the URL rather than have you follow it. Standard Webhooks gives an example schedule from immediately to 24-hour gaps over roughly three days, and Stripe retries live events for up to three days. The response decides what happens next:

| Response                                                                                   | Sender does                                 |
| ------------------------------------------------------------------------------------------ | ------------------------------------------- |
| 2xx                                                                                        | Done.                                       |
| <Status code={410} />                                                                      | Disable the endpoint and stop sending.      |
| <Status code={429} />, <Status code={502} />, <Status code={503} />, <Status code={504} /> | Slow down; honour `Retry-After` if present. |
| 3xx, other 4xx and 5xx, timeout                                                            | Retry on the schedule.                      |

Give each attempt a timeout of 15 to 30 seconds. When the schedule runs out, disable the endpoint and email its owner. Then let them see delivery attempts and resend events from a dashboard or an API, so recovery needs neither a support ticket nor Priya.

## Keep receiver URLs away from your network

A webhook URL is input from a stranger. Register `http://169.254.169.254/latest/meta-data/` or `http://localhost:6379/` as an endpoint, and a naive sender will helpfully fetch cloud credentials or poke an internal Redis. This is server-side request forgery, API7 in the OWASP API Security Top 10, and webhook senders are the textbook target. Three defences, all needed:

- Send from workers in a network segment that can't reach internal services, or through an egress proxy that blocks private, loopback and link-local ranges.
- Check the resolved IP at connection time, not only at registration, because DNS answers change.
- Require HTTPS, don't follow redirects, and don't echo response bodies back to the endpoint owner.

## Tell receivers exactly what you expect

Whoever writes a partner's handler will do what your docs say and nothing more. So the docs are half a contract with the sender and half instructions to the receiver. Say plainly:

- **Verify first.** Reject unsigned or stale deliveries with <Status code={401} />.
- **Answer fast.** Enqueue and return 2xx within a few seconds; do the work afterwards. Slow handlers time out and turn into retries.
- **Expect duplicates and disorder.** Deduplicate on `webhook-id`, and fetch the current state when order matters (see [Consuming events](/events/consuming-events/)).
- **Ignore unknown event types and fields.** New ones will appear.

One handler answers in milliseconds and works later; the other works inline and gets retried for its trouble:

In May 2007, Jeff Lindsay named the idea in a blog post, describing web hooks as "user defined callbacks made with HTTP POST". His pitch was composition: any service could notify any other without either knowing the other's API. The mechanism hasn't changed since. What took the industry until the 2020s to write down in a shared specification was everything around it: IDs, retries, and how to sign the request.

<WorkedProblem kind="Review" title="An unsigned webhook">

A shop sends `order.paid` webhooks to merchants. The docs say: "We POST JSON to your URL. To check it's us, compare the `X-Shop-Token` header with the token in your dashboard. We retry three times, a minute apart. Respond with 200 once you've fulfilled the order." What's wrong?

<Solution>

- **A static token isn't a signature.** It proves nothing about the body, and anyone who sees one request (a log, a proxy) can forge every future one. Use HMAC over ID, timestamp and body.
- **No timestamp**, so a captured request can be replayed to fulfil the same order again.
- **No delivery ID**, so receivers can't tell a retry from a second payment.
- **Three retries a minute apart** lose every event sent during a ten-minute deploy. Retry for days with backoff.
- **"Respond once you've fulfilled"** invites slow handlers, timeouts and retries that fulfil twice. Ask for a fast 2xx after enqueueing.
- **No word on SSRF**, which is the sender's own problem: merchant URLs need egress filtering.

</Solution>
</WorkedProblem>

## What to take away

A webhook is an HTTP request to a stranger's URL, so sign it over ID, timestamp and body, retry for days, keep it off your internal network, and ask receivers to acknowledge fast and deduplicate.
