<InBrief>

- Treat each event type as a public interface: named, owned, schema-registered, reviewed and versioned like an endpoint.
- Give every event mandatory metadata: a unique ID, a type, when it occurred, and a schema version.
- Decide the category: a business event records a step in a process; a data change event records a mutation of a resource.
- Preserve order per entity: partition by entity key and carry an explicit version or sequence number.
- Never save and then publish in two steps. Write the event to an outbox in the same transaction as the change.

</InBrief>

Request and response is a conversation: the client asks, and you answer. Events turn it around. Checkout announces "order placed", and Shipping, Billing, Analytics and the email service each react, without Checkout knowing any of them exist. That decoupling is the point, and also the catch. The event's shape is now relied on by people you can't see, can't ask, and can't make upgrade, which is the definition of a public API with the safety rails removed.

```text
Request/response   Checkout ──"create shipment"──► Shipping           Checkout knows Shipping
Events             Checkout ──"order-placed"──► bus ──► Shipping, Billing, Analytics, Email
```

## Give every event an envelope

```json
{
  "metadata": {
    "eid": "5b2c9a4e-8f1d-4a3b-9c6e-2d7f0a1b3c4d",
    "event_type": "shop.order-placed",
    "occurred_at": "2026-03-14T09:26:53Z",
    "version": "1.2.0",
    "flow_id": "4bf92f3577b34da6"
  },
  "order_id": "ord_42",
  "customer_id": "cus_7",
  "total": { "amount": "59.90", "currency": "EUR" }
}
```

| Field         | Why it's there                                                      |
| ------------- | ------------------------------------------------------------------- |
| `eid`         | Unique per event. Consumers deduplicate on it.                      |
| `event_type`  | Registered and namespaced. Consumers subscribe by type.             |
| `occurred_at` | When it happened in the business, not when it was sent or received. |
| `version`     | Schema version (SemVer), so consumers know which shape to expect.   |
| `flow_id`     | Correlates the event with the request that caused it, for tracing.  |

The payload follows the same rules as your HTTP API: snake_case, RFC 3339 timestamps, money as objects, IDs as strings. If your organisation spans several producers, the CNCF CloudEvents envelope (`id`, `source`, `type`, `time`) gives them a common shape, and most brokers and SDKs understand it.

## Pick a category: business event or data change

**Business events** record a step in a process: order placed, payment authorised, parcel delivered. Consumers react to something that happened, and the payload carries what they need to react.

**Data change events** record a mutation of a resource, usually with a snapshot, and exist so other services can keep a local copy:

```json
{
  "metadata": {
    "eid": "…",
    "event_type": "shop.product-changed",
    "occurred_at": "…",
    "version": "1.0.0"
  },
  "data_op": "U",
  "data_type": "shop:product",
  "data": {
    "id": "sku-1042",
    "name": "Trail runner",
    "price": { "amount": "79.00", "currency": "EUR" },
    "revision": 9
  }
}
```

The data in a change event should match the resource your API already exposes, not your table layout. Otherwise every column rename becomes a breaking change for every consumer.

<Compare>
<Prefer>

```json
{
  "metadata": { "eid": "…", "event_type": "shop.order-placed", "occurred_at": "…" },
  "order_id": "ord_42",
  "total": { "amount": "59.90", "currency": "EUR" }
}
```

</Prefer>
<Avoid>

```json
{
  "table": "orders",
  "op": "INSERT",
  "row": { "ORD_PK": 1842, "stat_cd": 3, "tot_amt_cents": 5990 }
}
```

</Avoid>

## Preserve order per entity

"Price changed to 79" followed by "price changed to 89" must not be applied backwards. Brokers like Kafka guarantee order only within a partition, so:

- **Partition by entity key** (`order_id`, `sku`). All events for one entity land in one partition, in order.
- **Carry an explicit ordering field**, a per-entity `revision` or sequence number. Retries, replays and repartitioning break broker order eventually, and a number lets consumers detect stale events instead of trusting delivery order.

Order across different entities is rarely needed and expensive to provide. Don't promise it.

## Publish atomically with the change

The obvious implementation saves the order and then publishes the event. If the process dies between the two, the order exists and no one hears about it. Publish first and the opposite happens: an event for an order that was rolled back. This is the dual-write problem, and the standard fix is a transactional outbox: write the event as a row in the same database transaction as the change, and let a relay publish outbox rows to the broker. The relay may publish a row twice, which is fine, because consumers deduplicate on `eid` (see [Consuming events](/events/consuming-events/)).

_Assumes:_ a relational database shared by the service and its outbox table; a relay (a poller or change data capture) that publishes unsent rows keyed by `partition_key`.

```python
class EventMetadata(BaseModel):
    eid: UUID = Field(default_factory=uuid4)
    event_type: str
    occurred_at: AwareDatetime
    version: str
    flow_id: str | None = None

async def place_order(cart: Cart, customer_id: str, flow_id: str) -> Order:
    async with db.transaction():
        order = await orders.insert(cart, customer_id)
        event = OrderPlaced(
            metadata=EventMetadata(event_type="shop.order-placed", occurred_at=order.placed_at,
                                   version="1.2.0", flow_id=flow_id),
            order_id=order.id, customer_id=customer_id, total=order.total,
        )
        await outbox.insert(event_type="shop.order-placed", partition_key=order.id,
                            payload=event.model_dump_json())
    return order  # the relay publishes the outbox row; no broker call here
```

## Register, own and version event types

Put each event type and its schema in a registry or catalogue with an owner, and review changes the way you review an OpenAPI diff. The [compatibility](/evolution/compatibility/) rules apply with less forgiveness: consumers replay events from months ago, archives keep them for years, and a breaking change can't be fixed by a new endpoint version when the old events are already on disk. Only add optional fields; never remove, rename or retype.

<Note kind="practice" title="Nakadi" source="https://github.com/zalando/nakadi">

Zalando built Nakadi, an open-source event bus with a RESTful API in front of Kafka. Producers register an event type with a JSON Schema, an owner, a category and a compatibility mode, and Nakadi rejects events that don't validate and schema changes that would break consumers. Most of the event rules in Zalando's guidelines read like a description of what Nakadi enforces, which is the point: rules a platform checks get followed.

</Note>

<WorkedProblem kind="Review" title="Publishing after the commit">

A payment service handles `POST /payments` like this. What can go wrong, and how would you fix it?

```python
payment = Payment.objects.create(order_id=order_id, amount=amount, status="captured")
producer.send("shop.payment-captured", value=serialize(payment))
return Response(PaymentSerializer(payment).data, status=201)
```

<Solution>

- **Lost event.** If the process crashes or the broker is unreachable after `create` commits, the payment exists but Shipping never hears about it. The order waits forever.
- **Phantom event.** If the save runs inside a request transaction that later rolls back, the event announces a payment that doesn't exist.
- **No ordering key.** Without `key=order_id`, a later `payment-refunded` for the same order can land on another partition and overtake it.
- **No metadata.** `serialize(payment)` has no `eid`, `occurred_at` or version, so consumers can't deduplicate or detect stale events.

The fix: write an outbox row with the full envelope inside the same `transaction.atomic()` as the payment, keyed by `order_id`, and let a relay publish it.

</Solution>
</WorkedProblem>
