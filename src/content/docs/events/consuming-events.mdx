<InBrief>

- Expect every event at least once and sometimes out of order. That's the normal case, not an incident.
- Record each processed `eid` in the same transaction as the side effect, and acknowledge only after it commits.
- Prefer effects that are safe to repeat ("set to X") over increments ("add X").
- Compare the producer's version or revision with what you hold, and ignore anything older.
- Put identifiers in events, not personal data. Copies of events are hard to find and harder to erase.

</InBrief>

Every event system eventually delivers the same event twice. Nothing is broken when it happens: a consumer processed an event, crashed before it recorded the fact, and the broker did its job by redelivering. Networks give you a choice between at-most-once (sometimes lose events) and at-least-once (sometimes repeat them), and nobody wants to lose a payment. So consumers are built to make repetition harmless. Once that's in place, retries, replays and redeliveries become boring, which is the goal.

```text
1. Consumer receives event e-1 and adds 100 loyalty points
2. Consumer crashes before committing its offset
3. Broker redelivers e-1 to the restarted consumer → another 100 points
```

## Deduplicate by event ID, in the same transaction

Keep a table of processed `eid`s. Insert the ID and perform the effect in one transaction, and commit the broker offset (or answer the webhook) only after that transaction commits. If the insert conflicts, you've seen the event before: skip the effect and acknowledge anyway, so the broker stops redelivering.

_Assumes:_ the consumer's own database holds both the effect and a `processed_events(eid primary key)` table; `OrderPlaced` is the schema from [Event design](/events/event-design/).

```python
async def handle_order_placed(raw: bytes) -> None:
    event = OrderPlaced.model_validate_json(raw)
    async with db.transaction():
        inserted = await db.execute(
            "INSERT INTO processed_events (eid) VALUES (:eid) ON CONFLICT DO NOTHING",
            {"eid": event.metadata.eid},
        )
        if inserted == 0:
            return  # seen before: already handled
        await loyalty.add_points(event.customer_id, points_for(event.total))
    # the caller commits the offset only after this returns
```

Processed-ID tables grow forever unless you prune them. Keep IDs at least as long as the broker's retention plus the longest replay you'd run, and no longer.

## Prefer effects that are safe to repeat

A deduplication table is a safety net. Better still is an effect that a duplicate can't hurt, because it states a result instead of a change.

<Compare>
<Prefer label="Repeatable">

```sql
UPDATE product_copies SET price = 79.00 WHERE sku = 'sku-1042';
INSERT INTO shipments (order_id, …) VALUES ('ord_42', …)
  ON CONFLICT (order_id) DO NOTHING;
```

</Prefer>
<Avoid label="Accumulating">

```sql
UPDATE accounts SET points = points + 100 WHERE customer_id = 'cus_7';
UPDATE stock SET quantity = quantity - 1 WHERE sku = 'sku-1042';
```

</Avoid>
</Compare>

Some effects can't be made repeatable: an email, a charge, an SMS. For those, the deduplication table is not optional, and the external call should carry its own idempotency key, derived from the `eid`.

## Ignore stale events

Events for one entity can arrive out of order after a retry, a replay or a repartition. Use the producer's ordering field and apply only what is newer than what you hold:

```sql
UPDATE product_copies
SET name = :name, price = :price, revision = :revision
WHERE sku = :sku AND revision < :revision;
```

This is last-writer-wins by revision, and it absorbs exact duplicates for free, because a duplicate has the same revision. It only works if the producer provides the number. A consumer that sorts by `occurred_at` is trusting clocks on different machines, and clocks are worse at ordering than counters.

## Keep personal data out of events

Events are copied to every consumer, retained for days or forever, replayed into new services and archived in data lakes. When a customer exercises their right to erasure, every copy of every event that names them is now your problem. Send identifiers, and let authorised consumers fetch the details through an API that checks permissions and can forget.

<Prefer>

<Note kind="curiosity" title="Exactly-once, with fine print" year="2017" source="https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/">

Kafka 0.11 introduced exactly-once semantics in 2017, with an announcement whose title argued against years of conference talks saying it was impossible. The feature is real: idempotent producers and transactions make a read-process-write cycle within Kafka atomic. The fine print is the boundary. Once your consumer sends an email or charges a card, the side effect sits outside Kafka's transaction, and deduplication is your job again.

</Note>

<Note kind="practice" title="Stripe says it out loud" source="https://docs.stripe.com/webhooks">

Stripe's webhook documentation tells integrators that endpoints might receive the same event more than once and should log processed event IDs and skip duplicates. It also says Stripe doesn't guarantee delivery in the order events were generated, warns against using timestamps to order them, and suggests retrieving missing objects from the API instead. Saying this in the docs is a design decision: consumers who are told to expect duplicates write code that survives them.

</Note>
