<InBrief>

- Return absolute URIs in links. Relative references break as soon as a response is logged, queued or forwarded.
- Use simple link objects (`{"href": …}`) in the body, named with registered relations where one exists: `self`, `next`, `prev`.
- Add links for pagination, related resources and actions that depend on state. That captures most of hypermedia's value.
- Configure forwarded-header handling, or your absolute links will point at internal hostnames.

</InBrief>

Fernhill moves customers to a new hostname. The web shop updates in an afternoon; the mobile app has `/customers/{id}` compiled in, and the fix takes weeks to reach every phone. Larkspur Logistics never upgrades at all.

The web avoided this long ago: pages link to pages, and nobody builds the next article's URL by hand. APIs can borrow that without full hypermedia. A few well-placed links remove URL templates from every client and leave you free to move resources.

## Hand clients links, not URL templates

Start with what most APIs send:

```json
{ "id": "ord_42", "customer_id": "cus_7" }
```

To fetch the customer, the client must know that customers live at `/customers/{id}` on a particular host. That rule is now compiled into every client, which is how that migration got stuck. With a link, the client follows instead of constructing:

```json
{
  "id": "ord_42",
  "customer_id": "cus_7",
  "links": {
    "self": { "href": "https://api.example.com/orders/ord_42" },
    "customer": { "href": "https://customers.api.example.com/customers/cus_7" }
  }
}
```

Keep the ID as well: clients need it as a key in their own storage. The link is for navigation.

For names, use the [IANA link relation registry](https://www.iana.org/assignments/link-relations/link-relations.xhtml) for common relations (`self`, `next`, `prev`, `first`, `last`, `related`, `collection`) and plain domain names (`customer`, `line_items`) for the rest. Then pick one structure and use it everywhere. A `links` object, `_links` in HAL, or individual `{"href"}` properties all work; two of them in one API means two parsers in every client. This site uses a `links` object of `{"href"}` objects for relations, and keeps pagination's `next` and `self` as top-level strings on collection pages, because every client reads those.

## Make every link absolute

A relative link only makes sense beside the request that produced it, and responses get logged, queued and forwarded far from it.

<Compare>
<Prefer>

```json
{ "links": { "customer": { "href": "https://api.example.com/customers/cus_7" } } }
```

Works wherever the response ends up: logs, queues, another service.

</Prefer>
<Avoid>

```json
{ "next": { "href": "/orders?cursor=b2Jq" } }
```

Relative to what? Behind a gateway, the client may have called a different host.

</Avoid>
</Compare>

Building them correctly is the non-obvious part. Your app sits behind a load balancer that terminates TLS and forwards to `http://10.0.3.7:8000`, so a naive `url_for` hands every partner `http://10.0.3.7:8000/orders/ord_42`. The framework needs to trust the proxy's `X-Forwarded-Proto` and `X-Forwarded-Host` headers (or the standard `Forwarded` header, RFC 7239), and only from the proxy, otherwise clients can spoof them. Configure a canonical public base URL if your topology makes trust awkward.

_Assumes:_ the app runs behind a reverse proxy that sets `X-Forwarded-*` headers.

Here's the order endpoint in each stack. The line to notice is the proxy setting, or the fixed public base URL, not the handler.

class OrderSerializer(serializers.ModelSerializer):

## Put links in the body for JSON APIs

HTTP has a `Link` header (RFC 8288), and some well-known APIs use it for pagination. For JSON APIs, the body is better: headers are lost when a response is stored or forwarded, and can't sit next to the item they describe in a list. Every JSON parser already reads body links. Reserve the `Link` header for responses without a JSON body, such as a file download that points to its metadata.

GitHub went the other way, and its documentation shows the cost.

<Note kind="practice" title="GitHub's Link header" source="https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api">

GitHub's REST API paginates through the `Link` header: `<https://api.github.com/…&page=2>; rel="next", <…&page=34>; rel="last"`. It works, and it's standard. It also means every client needs a parser for a header format most developers have never seen, which is why GitHub's documentation devotes a page to it. Links in the JSON body need no special parsing.

</Note>

## Let links say what the client can do next

Fernhill's app shows a Cancel button on cancellable orders, a rule that lives in the server and has already changed twice. Copy it into the app and the two drift. Instead, advertise what can be done next, depending on state:

```json
{
  "id": "ord_42",
  "status": "placed",
  "links": {
    "self": { "href": "https://api.example.com/orders/ord_42" },
    "cancellation": { "href": "https://api.example.com/orders/ord_42/cancellation" },
    "payments": { "href": "https://api.example.com/orders/ord_42/payments" }
  }
}
```

Once the order ships, `cancellation` disappears and `returns` appears. The app shows Cancel when the link is there and hides it when it isn't, without knowing which states are cancellable. When the rule changes a third time, the app follows without a release.

Full HATEOAS goes further: clients discover the whole workflow at runtime, with nothing about it compiled in. That remains rare. Client developers read docs and write code against known flows, generic hypermedia clients never caught on, and the formats (HAL, JSON:API, Siren, JSON-LD with Hydra) never converged. Take the cheap, high-value parts and skip the rest.

## What to take away

A link moves a rule out of every client and back into the server: where a resource lives, and what can be done to it now. Make links absolute and keep them in the body. Photos, invoices and multi-gigabyte exports need different handling. That's [files and large payloads](/representations/files/).
