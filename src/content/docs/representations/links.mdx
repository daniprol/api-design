<InBrief>

- Return absolute URIs in links. Relative references break as soon as a response is logged, queued or forwarded.
- Use simple link objects (`{"href": …}`) in the body, named with registered relations where one exists: `self`, `next`, `prev`.
- Add links for pagination, related resources and actions that depend on state. That captures most of hypermedia's value.
- Configure forwarded-header handling, or your absolute links will point at internal hostnames.

</InBrief>

The web works because pages link to pages: nobody builds the URL of the next article by hand. APIs can borrow that without adopting a full hypermedia architecture. A few well-placed links remove URL templates from every client and leave you free to move resources later.

## Prefer links over IDs plus URL templates

```json
{ "id": "ord_42", "customer_id": "cus_7" }
```

To fetch the customer, the client must know that customers live at `/customers/{id}` on a particular host. That rule is now compiled into every client. With a link, the client follows and doesn't construct:

```json
{
  "id": "ord_42",
  "customer_id": "cus_7",
  "links": {
    "self": { "href": "https://api.example.com/orders/ord_42" },
    "customer": { "href": "https://customers.api.example.com/customers/cus_7" }
  }
}
```

Keep the ID as well: clients need it as a key in their own storage. The link is for navigation.

Use the [IANA link relation registry](https://www.iana.org/assignments/link-relations/link-relations.xhtml) for common relations (`self`, `next`, `prev`, `first`, `last`, `related`, `collection`) and plain domain names (`customer`, `line_items`) for the rest. Choose one structure for links and use it everywhere. A `links` object, `_links` in HAL, or individual `{"href"}` properties all work, as long as there's only one. This site uses a `links` object of `{"href"}` objects for relations, and keeps pagination's `next` and `self` as top-level strings on collection pages, because every client reads those.

## Make every link absolute

<Compare>
<Prefer>

```json
{ "links": { "customer": { "href": "https://api.example.com/customers/cus_7" } } }
```

Works wherever the response ends up: logs, queues, another service.

</Prefer>
<Avoid>

```json
{ "next": { "href": "/orders?cursor=b2Jq" } }
```

Relative to what? Behind a gateway, the client may have called a different host.

</Avoid>
</Compare>

The non-obvious part is building them correctly. Your app usually sits behind a load balancer that terminates TLS and forwards to `http://10.0.3.7:8000`. A naive `url_for` then produces `http://10.0.3.7:8000/orders/ord_42`. The framework needs to trust the proxy's `X-Forwarded-Proto` and `X-Forwarded-Host` headers (or the standard `Forwarded` header, RFC 7239), and only from the proxy, otherwise clients can spoof them. Configure a canonical public base URL if your topology makes trust awkward.

_Assumes:_ the app runs behind a reverse proxy that sets `X-Forwarded-*` headers.

```python
# uvicorn app:app --proxy-headers --forwarded-allow-ips="10.0.0.0/8"
class Link(BaseModel):
    href: str

@app.get("/orders/{order_id}", name="get_order")
def get_order(order_id: str, request: Request) -> OrderOut:
    order = orders.get_or_404(order_id)
    return OrderOut(
        id=order.id,
        customer_id=order.customer_id,
        links={
            "self": Link(href=str(request.url_for("get_order", order_id=order.id))),
            "customer": Link(href=str(request.url_for("get_customer", customer_id=order.customer_id))),
        },
    )
```

## Put links in the body for JSON APIs

HTTP has a `Link` header (RFC 8288), and some well-known APIs use it for pagination. For JSON APIs, links in the body are easier: every JSON parser sees them, they survive being stored or forwarded without headers, and they can sit next to the item they describe in a list. Reserve the `Link` header for responses without a JSON body, such as a file download that points to its metadata.

<Note kind="practice" title="GitHub's Link header" source="https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api">

GitHub's REST API paginates through the `Link` header: `<https://api.github.com/…&page=2>; rel="next", <…&page=34>; rel="last"`. It works, and it's standard. It also means every client needs a parser for a header format most developers have never seen, which is why GitHub's documentation devotes a page to it. Links in the JSON body need no special parsing.

</Note>

## Use links for actions that depend on state

The most useful step towards hypermedia is advertising what can be done next, depending on the resource's state:

```json
{
  "id": "ord_42",
  "status": "placed",
  "links": {
    "self": { "href": "https://api.example.com/orders/ord_42" },
    "cancellation": { "href": "https://api.example.com/orders/ord_42/cancellation" },
    "payments": { "href": "https://api.example.com/orders/ord_42/payments" }
  }
}
```

Once the order ships, `cancellation` disappears and `returns` appears. A UI can decide whether to show a Cancel button by checking for the link, instead of duplicating the server's business rules about which states are cancellable. When those rules change, the UI follows without a release.

Full HATEOAS goes further: clients discover the whole workflow at runtime, with nothing about it compiled in. That remains rare. Client developers read docs and write code against known flows, generic hypermedia clients never caught on, and the formats (HAL, JSON:API, Siren, JSON-LD with Hydra) never converged. Take the cheap, high-value parts and skip the rest.
