<InBrief>

- Choose one property casing and apply it to every field, query parameter and event. Consistency matters more than which one.
- Return an object at the top level, never a bare array, so you can add metadata later.
- Use string enums, and make clients treat unknown values as expected. This site uses lowercase `snake_case` values.
- Treat `null` and absent as the same thing in responses. Never make a boolean nullable; use an enum for the third state.
- Return empty collections as `[]`, and don't use `""` to mean "no value".

</InBrief>

JSON is simple enough that everyone uses it and loose enough that everyone uses it differently. RFC 8259 says almost nothing about naming, nesting, numbers or nulls, so each API makes those choices itself, consciously or not. The conventions below are small. Their value is that payloads become predictable and can grow without breaking anyone.

## Pick one casing and never mix

Both `snake_case` and `camelCase` are defensible, and the major guidelines split on it. What's never defensible is mixing: a client that maps fields automatically fails on the one field that doesn't follow the pattern.

<GuidesDiffer id="json-casing" />

The casing has to match the query parameters (`?created_after=` for a `created_after` field) and your event payloads. This guide uses `snake_case`. Python serialises it naturally, and TypeScript code maps at the edge or adopts it in its API types.

## Return an object at the top level

<Compare>
<Prefer>

```json
{
  "items": [{ "id": "ord_1" }, { "id": "ord_2" }],
  "next": "https://api.example.com/orders?cursor=b2Jq"
}
```

Room for `next`, `warnings` or anything else later.

</Prefer>
<Avoid>

```json
[{ "id": "ord_1" }, { "id": "ord_2" }]
```

Adding pagination later means changing the root type, which breaks every client.

</Avoid>
</Compare>

Name arrays in the plural (`items`, `line_items`, `tags`), and use an object with dynamic keys when the keys are data, such as language codes or SKUs, documented with `additionalProperties`.

## Use string enums, and expect them to grow

Enum values are strings, not integers that need a lookup table: `"status": "partially_shipped"`, not `"status": 4`. This guide uses lowercase `snake_case` values, which match the field names; Zalando and Google use `UPPER_SNAKE_CASE`. Either works if applied everywhere.

The decision that matters more is what clients do with a value they don't know. Adding `"partially_shipped"` to an order's status is one of the most common changes an API makes. If clients use exhaustive `switch` statements that throw on unknown values, it's a breaking change. Document every enum as open-ended, and make sure your own SDKs map unknown values to a fallback ([Compatibility](/evolution/compatibility/) covers this).

_Assumes:_ Pydantic v2, DRF 3.15, Zod 3 with `@hono/zod-openapi` for schema metadata.

## Give nothing a single meaning

JSON has at least four ways to say nothing: an absent field, `null`, `""` and `[]`. If each carries a different private meaning, every client has to learn it. Make three of them boring.

**`null` and absent mean the same in responses.** Many languages can't tell them apart after deserialisation. Pick one style, either always include optional fields as `null` or always omit them, and apply it everywhere. The single, well-known exception is JSON Merge Patch on requests, where absent means "leave alone" and `null` means "remove" (see [Methods](/http/methods/)).

**Booleans are never `null`.** A nullable boolean is a three-state enum that doesn't name its third state. Does `"newsletter_consent": null` mean declined, never asked, or not loaded? For consent, the difference is a legal question.

<Compare>
<Prefer>

```json
{ "newsletter_consent": "not_asked" }
```

Three states, each with a name: `granted`, `declined`, `not_asked`.

</Prefer>
<Avoid>

```json
{ "newsletter_consent": null }
```

</Avoid>
</Compare>

**Empty collections are `[]`.** Clients can iterate without a null check, and "no tags" isn't confused with "tags not loaded".

**`""` is a real empty string,** not a stand-in for "no value". Otherwise every client has to check for both.

<Note kind="history" title="The billion-dollar mistake" year="2009" source="https://www.infoq.com/presentations/Null-References-The-Billion-Dollar-Mistake-Tony-Hoare/">

Tony Hoare called his 1965 invention of the null reference in ALGOL W his "billion-dollar mistake": it was added "simply because it was so easy to implement". Kotlin, Swift, Rust and TypeScript with `strictNullChecks` spend real complexity making null explicit. An API that makes null mean one specific thing gives its clients the same benefit.

</Note>

<Note kind="incident" title="A licence plate reading NULL" year="2019" source="https://www.wired.com/story/null-license-plate-landed-one-hacker-ticket-hell/">

A security researcher registered the California vanity plate "NULL" and began receiving parking fines for vehicles whose plate had never been recorded: a system had stored missing plates as the string `NULL`. He was billed thousands of dollars. Absence must be represented as absence, never as a sentinel string that a real value can collide with.

</Note>

<WorkedProblem kind="Review" title="A customer payload">

```json
{
  "customerId": "cus_7",
  "created_at": 1773480413,
  "is_vip": null,
  "tags": null,
  "nickname": "",
  "status": 2
}
```

List every convention this breaks and propose a corrected payload.

<Solution>

- Mixed casing: `customerId` next to `created_at`.
- A Unix timestamp instead of an RFC 3339 string (see [Data formats](/representations/data-formats/)).
- A nullable boolean: is the customer not VIP, or not evaluated yet?
- `tags: null` instead of `[]`.
- `""` used to mean "no nickname".
- An integer enum that needs a lookup table.

```json
{
  "customer_id": "cus_7",
  "created_at": "2026-03-14T09:26:53Z",
  "vip_status": "not_evaluated",
  "tags": [],
  "status": "active"
}
```

`nickname` is omitted (or `null`, if that's the house style), because there isn't one.

</Solution>
</WorkedProblem>
