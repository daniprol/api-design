<InBrief>

- Accept small files (up to a few MB) as `multipart/form-data` or a raw body with the right `Content-Type`. Never base64 them into JSON.
- For anything larger, issue a short-lived presigned URL and let the client upload straight to object storage, then confirm.
- Make uploads above roughly 100 MB resumable: tus today, the IETF resumable upload protocol as it matures.
- Serve downloads with `Accept-Ranges`, `ETag` and <Status code={206} />, so clients can resume and seek.
- Set and document explicit size and type limits, verify content rather than trusting the declared type, and checksum the bytes.

</InBrief>

A customer uploads a 40 MB video of a torn tent seam from a campsite with one bar of signal. The request holds an API worker for four minutes, then dies at 92 percent, and the app starts again from zero. Meanwhile Priya watches checkout latency climb.

A JSON API sends kilobytes. Files are megabytes or gigabytes, and they break assumptions everywhere in the stack: request timeouts, proxy body-size limits, worker memory, the cost of retrying from zero. The design question is mostly how to keep those bytes off your application servers.

## Choose the upload path by size

A receipt photo and a 2 GB product video fail differently, so pick the path by size:

| Size                                   | Path                                                       | Why                                                         |
| -------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------- |
| Up to a few MB                         | `multipart/form-data` or a raw body to your API            | One request, metadata alongside, simple clients             |
| Tens of MB and up                      | Presigned URL to object storage                            | Bytes skip your servers; storage scales and retries for you |
| Hundreds of MB, or unreliable networks | Resumable upload (tus, or object storage multipart upload) | A dropped connection costs a chunk, not the whole file      |

Base64 inside JSON is missing on purpose. It inflates the payload by a third, forces the whole file into memory to parse, and defeats streaming. It's the file equivalent of posting a sofa through the letterbox one cushion at a time. Keep it for small values such as signatures, as discussed in [Data formats](/representations/data-formats/).

## Send large files straight to storage

Keep your servers out of the byte-moving business. The API issues an upload slot, the client sends the bytes straight to object storage, and the API confirms. Your servers handle a few hundred bytes of JSON; the storage service handles the gigabytes. Here's the exchange. Notice that the response is a resource in `pending_upload`, not a success:

```http
POST /orders/ord_42/attachments
{ "filename": "invoice.pdf", "content_type": "application/pdf", "size": 48213760 }

HTTP/1.1 201 Created
Location: https://api.example.com/orders/ord_42/attachments/att_9
{
  "id": "att_9",
  "status": "pending_upload",
  "upload": {
    "method": "PUT",
    "url": "https://uploads.s3.eu-west-1.amazonaws.com/att_9?X-Amz-Signature=…",
    "headers": { "Content-Type": "application/pdf" },
    "expires_at": "2026-11-14T10:15:00Z"
  }
}
```

The client then `PUT`s the bytes to `upload.url`. Completion is detected either by a storage event notification or by the client calling `POST /orders/ord_42/attachments/att_9/completion`. Then the attachment moves from `pending_upload` to `processing` (virus scan, thumbnailing) to `ready`.

That URL is a bearer credential: anyone who has it can upload until it expires. So constrain the slot tightly. Sign the content type and the exact length (or use a presigned `POST` policy with `content-length-range` when you need a maximum; a presigned `PUT` can't express one), keep the expiry to minutes, and use a key you generate rather than the client's filename.

_Assumes:_ boto3 for S3 in Python, `@aws-sdk/s3-request-presigner` in TypeScript.

Here's the endpoint. Notice that validation runs before anything is signed, and that size and type end up inside the signature.

```python
MAX_BYTES = 100 * 1024 * 1024
ALLOWED = {"application/pdf", "image/png", "image/jpeg"}

@app.post("/orders/{order_id}/attachments", status_code=201)
def create_attachment(order_id: str, body: AttachmentIn) -> AttachmentOut:

        raise problem(422, "unsupported-attachment-type", allowed=sorted(ALLOWED))
    if body.size > MAX_BYTES:
        raise problem(422, "attachment-too-large", max_bytes=MAX_BYTES)
    att = attachments.create(order_id, body, status="pending_upload")
    url = s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": BUCKET, "Key": att.storage_key, "ContentType": body.content_type,
                "ContentLength": body.size},
        ExpiresIn=600,
    )
    return AttachmentOut.pending(att, upload_url=url)
```

## Make big uploads resumable

Presigned URLs don't make the network kinder. A 2 GB upload over a train's Wi-Fi will be interrupted, and without resumption the client starts again from byte zero and may never finish. Two options:

- **tus**, an open protocol since 2013 with servers and clients for most platforms. The client creates an upload, sends chunks with `PATCH` and an `Upload-Offset` header, and after a disconnect asks the server with `HEAD` how far it got.
- **The IETF resumable upload protocol** (draft-ietf-httpbis-resumable-upload), which builds on tus's experience and aims to let any HTTP client resume uploads natively. Track it, and design so you can adopt it later.

Object stores have their own variants (S3 multipart upload, GCS resumable uploads) that pair well with presigned URLs: one presigned URL per part.

tus has a better origin story than most protocols.

<Note kind="history" title="tus" year="2013" source="https://tus.io/protocols/resumable-upload">

Transloadit, a file-processing company, had a support problem: its customers kept losing uploads on mobile networks. Instead of another proprietary resume scheme, it published an open protocol, tus. It later became the starting point for the IETF HTTP working group's resumable upload draft. A small company's fix for a support queue is turning into part of HTTP.

</Note>

## Serve downloads with ranges and validators

Downloads drop too. HTTP range requests (RFC 9110 §14) make large downloads resumable and seekable. Advertise `Accept-Ranges: bytes`, answer a `Range: bytes=1048576-` request with <Status code={206} /> and `Content-Range`, and send an `ETag`, so a client resuming with `If-Range` gets the remainder only if the file hasn't changed, and the whole new file if it has. The `If-Range` line is what stops a resume from splicing two versions together:

```http
GET /orders/ord_42/attachments/att_9/content
Range: bytes=1048576-
If-Range: "a1b2c3"

HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-48213759/48213760
Content-Type: application/pdf
```

In practice you rarely implement this yourself. Redirect with <Status code={303} /> or <Status code={307} /> to a short-lived presigned download URL, or serve through a CDN, and both handle ranges. Add `Content-Disposition: attachment; filename="invoice.pdf"` when browsers should download the file instead of rendering it.

## Set limits, verify content, and checksum

Every upload endpoint invites something large, wrong or hostile. Four checks cover most of it:

- **Size.** Enforce a maximum before reading the body and return <Status code={413} /> with the limit in a problem body. Document it, because the gateway's default (often 1 MB or 10 MB) is otherwise your real limit, and nobody knows it.
- **Type.** Treat the declared `Content-Type` and the filename as hints. Sniff the magic bytes, allow-list the result and return <Status code={415} /> otherwise. Never serve user uploads from your API's origin with a type the browser will execute.
- **Integrity.** Ask clients to send a digest, `Content-Digest` or `Repr-Digest` (RFC 9530), or the storage service's checksum header, and verify it. Silent corruption on long uploads is rare but real.
- **Processing.** Scan, transcode and extract asynchronously, and expose the status on the resource ([Long-running operations](/reliability/long-running-operations/)).

An attachment is a resource with a status and a link to its bytes, never the bytes themselves:

<WorkedProblem kind="Review" title="Profile picture upload">

```python
@app.post("/customers/{customer_id}/avatar")
async def upload_avatar(customer_id: str, request: Request):
    body = await request.json()
    data = base64.b64decode(body["image"])
    path = f"/var/www/static/avatars/{body['filename']}"
    open(path, "wb").write(data)
    return {"url": f"https://www.example.com/static/avatars/{body['filename']}"}
```

What's wrong, ordered by severity?

<Solution>

1. **Path traversal.** `filename` is used unsanitised: `../../app/settings.py` overwrites code. Generate the storage key server-side.
2. **Stored XSS.** Files are served from the main web origin with whatever type the extension implies. An `.html` or `.svg` "avatar" runs script in your users' sessions. Serve uploads from a separate, cookieless domain, and allow-list types by sniffing content.
3. **No limits.** No size check, and base64 JSON means the whole image is in memory three times over. Cap the size, and accept a raw `image/*` body or `multipart/form-data`.
4. **No authorisation check** that the caller owns `customer_id`.
5. **Synchronous local disk.** This doesn't work with more than one server. Use object storage.

</Solution>
</WorkedProblem>

## What to take away

Your API should talk about files, not carry them: it issues slots, tracks status and hands out links, while storage and CDNs move the bytes. Collections have the same problem at a different scale, when `GET /orders` would return a million rows. That's [pagination](/collections/pagination/).
