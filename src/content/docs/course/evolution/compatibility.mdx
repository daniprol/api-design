<Hook>

Shipping an API is easy. Changing it **without breaking anyone** is the real craft. You often can't see your clients, can't force them to upgrade, and can't know which "harmless" detail they depend on. Mastering compatibility is what lets an API live for ten years instead of being rewritten every two.

</Hook>

## The golden rule

> **Don't break your clients.** Every change to a published API must be backward compatible, or it's a new API.

So what counts as breaking?

## Safe vs. breaking changes

| ✅ Usually safe (compatible)                     | 💥 Breaking                                                       |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| Add a new endpoint / resource                    | Remove or rename an endpoint                                      |
| Add an **optional** request field or parameter   | Add a **required** request field or parameter                     |
| Add a response field                             | Remove or rename a response field                                 |
| Make a required request field optional           | Make an optional request field required                           |
| Accept more input values (relax validation)      | Reject input that used to be accepted (tighten validation)        |
| Add a new error type with a standard status code | Change the type of a field (`"42"` → `42`)                        |
|                                                  | Change the meaning of a field or a default value                  |
|                                                  | Return a new enum value… _if clients aren't prepared_ (see below) |

## Robustness principle (and its limits)

The famous **Postel's Law**: _"Be conservative in what you send, be liberal in what you accept."_

- **Servers**: be conservative in what you add and promise. Every field you return is a promise.
- **Clients**: be **tolerant readers**. Ignore unknown fields. Don't fail on unknown enum values. Don't depend on field order.

<TabItem label="FastAPI" icon="seti:python">

```python
# A tolerant CLIENT model: unknown fields are ignored (pydantic's default),
# unknown enum values don't crash.
from pydantic import BaseModel, ConfigDict

class OrderView(BaseModel):
    model_config = ConfigDict(extra="ignore")
    id: str
    status: str            # NOT Literal[...]: new statuses must not crash us

    @property
    def is_done(self) -> bool:
        return self.status in {"DELIVERED", "CANCELED"}  # unknown → treated as "not done"

# On the SERVER side, be strict about input instead:
class OrderIn(BaseModel):
    model_config = ConfigDict(extra="forbid")  # typos like "quantitty" → 422
```

## The enum trap

Adding an enum value _looks_ additive. But a client with `switch (status)` and no default branch, or a strict enum parser, will crash on the new value. Two defences:

1. **Document enums as extensible** from day one ("clients must handle unknown values"). Zalando uses an open-ended list of values for this.
2. **Clients always have a fallback** for unknown values.

```yaml
status:
  type: string
  description: Order status. New values may be added; treat unknown values as "in progress".
  examples: [PLACED, PAID, SHIPPED, DELIVERED, CANCELED]
```

## Design conservatively

The cheapest compatibility problem is the one you never create:

- Don't return fields "just in case". Every field is a forever promise.
- Prefer **objects** over primitives where growth is likely: `"price": {"amount": ..., "currency": ...}` can grow; `"price": 19.99` can't.
- Start strict with input, then relax. Going the other way is breaking.

<Story kind="fun-fact" title="Hyrum's Law">

Google engineer Hyrum Wright observed: _"With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody."_ The order of keys in your JSON, the exact wording of an error message, the time it takes to respond: someone, somewhere, depends on it. The famous XKCD #1172 ("Workflow") shows a user whose workflow relied on a bug that made the CPU overheat when holding the spacebar.

</Story>

<Story kind="history" title="Postel's Law, revisited">

Jon Postel wrote the robustness principle in the TCP specification (RFC 761, 1980). It helped the early internet interoperate, but decades later, being "liberal in what you accept" also meant protocols accumulated quirks and security holes, because everyone had to accept everyone else's bugs forever. RFC 9413 (2023), _"Maintaining Robust Protocols"_, revisits the principle. Modern advice: **tolerant readers, yes; sloppy servers, no**.

</Story>

<Takeaways>

- **Never break clients**: additive changes only.
- Removing, renaming, retyping, or tightening = breaking.
- Clients are **tolerant readers**: ignore unknown fields, handle unknown enum values.
- Design conservatively: every field is a promise (Hyrum's Law).

</Takeaways>
