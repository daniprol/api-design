<Hook>

Every API endpoint will eventually die. The question is whether it dies **gracefully** (announced, measured, with clients migrated) or **suddenly**, at 9 AM on a Monday, breaking a partner's checkout. Deprecation is a process, not a deletion.

</Hook>

## The lifecycle

```text
 ACTIVE ──► DEPRECATED ──► SUNSET (removed)
             │                 ▲
             └─ warn, measure, help clients migrate ─┘
```

1. **Deprecate**: mark it in the spec and in responses. It still works!
2. **Communicate**: changelog, emails, docs, migration guide.
3. **Monitor**: who still calls it? How often?
4. **Migrate**: help the remaining clients move. Talk to them.
5. **Sunset**: remove it only when usage is (near) zero and clients have agreed.

## Mark it in the spec

```yaml
paths:
  /orders/{id}/shipping-info:
    get:
      deprecated: true
      description: |
        Deprecated, use `GET /shipments?order_id={id}` instead.
        Will be removed on 2027-06-30.
```

## Mark it on the wire: Deprecation and Sunset headers

Two standard headers make deprecation **machine-readable**, so client SDKs, gateways and monitoring can warn developers automatically:

```http
HTTP/1.1 200 OK
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://api.example.com/docs/migrations/shipping-info>; rel="deprecation"
```

- **`Deprecation`** (RFC 9745): when the resource was (or will be) deprecated, as a Unix timestamp prefixed with `@`.
- **`Sunset`** (RFC 8594): the date after which it's expected to stop working.

from fastapi import Depends, Response

def deprecated(sunset: str, docs: str, since: int):
    def mark(response: Response):
        response.headers["Deprecation"] = f"@{since}"
        response.headers["Sunset"] = sunset
        response.headers["Link"] = f'<{docs}>; rel="deprecation"'
        metrics.increment("deprecated_endpoint_calls")  # who still uses it?
    return Depends(mark)

)

from functools import wraps

def deprecated(sunset, docs, since):
    def decorator(view):
        @wraps(view)
        def wrapper(self, request, *args, **kwargs):
            logger.info("deprecated_call", extra={
                "client": request.auth and request.auth.client_id, "path": request.path})
            response = view(self, request, *args, **kwargs)
            response["Deprecation"] = f"@{since}"
            response["Sunset"] = sunset
            response["Link"] = f'<{docs}>; rel="deprecation"'
            return response
        return wrapper
    return decorator

## After the sunset

Once removed, respond with <Status code={410} /> ("this existed, and it's gone on purpose") plus a problem body pointing to the replacement, at least for a while. It's much friendlier than a confusing <Status code={404} />.

## Consumers have duties too

If _you_ consume an API: watch for `Deprecation` and `Sunset` headers in your HTTP client (log a warning!), and **never start using an endpoint that's already deprecated**.

<DoDont>
<Do>

- Announce early, with a date and a migration guide.
- Measure usage per client.
- Reach out to remaining clients personally.
- Remove only when usage is ~0 and clients agreed.

</Do>
<Dont>

- Delete the endpoint and wait to see who complains.
- Announce in a changelog nobody reads, then remove a month later.
- Keep a deprecated endpoint forever "just in case" with no plan.

</Dont>
</DoDont>

<Story kind="war-story" title="The Twitter API shutdown of 2023">

In February 2023, Twitter announced it would end free access to its API with about a week's notice, later moving to paid tiers. Thousands of apps, research projects, bots and accessibility tools broke or shut down, including beloved third-party clients that had been abruptly cut off weeks earlier. Whatever the business reasons, it's a textbook example of how much a sudden sunset costs the ecosystem built on an API.

</Story>

<Story kind="real-world" title="Google's Graveyard">

There's a popular website, _Killed by Google_, that lists products and APIs Google has shut down: well over 200 of them. Developers joke about it, but it reflects a real trust problem: every sudden shutdown makes people hesitate to build on the next API. Predictable deprecation policies are a competitive advantage.

</Story>

`410 Gone` says the removal is intentional and permanent, unlike a `404` that could be a typo. A problem body with a link to the migration guide turns an outage into a to-do item.

<Takeaways>

- Deprecation is a **process**: mark → communicate → monitor → migrate → sunset.
- Use `deprecated: true` in the spec plus `Deprecation` and `Sunset` headers.
- Measure who still calls it; talk to them.
- After removal, answer <Status code={410} /> with a pointer to the replacement.

</Takeaways>
