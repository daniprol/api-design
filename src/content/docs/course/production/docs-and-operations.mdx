In a company with 5 APIs, everyone knows who owns what. With 500, nobody does. Who owns this API? Who's allowed to call it? Which version is deployed? Who's still using that endpoint? **Metadata and operations** are the boring answers to those questions, and they're what makes an API landscape navigable.

## Metadata every spec should carry

```yaml
openapi: 3.1.0
info:
  title: Order Management API
  version: 1.4.2 # semantic version of the SPEC
  description: Place, track and cancel customer orders.
  contact:
    name: Team Checkout
    url: https://wiki.example.com/teams/checkout
    email: checkout@example.com
  x-api-id: 0f3c1e2d-7a0e-4b8e-9d2b-1f2a3b4c5d6e # stable, never changes
  x-audience: company-internal # who may use it
servers:
  - url: https://order-management.api.example.com
```

## Semantic versioning for the spec

Even if the API itself is never "versioned" (see [Versioning](/course/evolution/versioning/)), the **spec document** changes. Version it with SemVer:

| Bump    | When                                               | Example         |
| ------- | -------------------------------------------------- | --------------- |
| `MAJOR` | Incompatible change (should be extremely rare)     | `1.4.2 → 2.0.0` |
| `MINOR` | Backward-compatible addition (new field, endpoint) | `1.4.2 → 1.5.0` |
| `PATCH` | Docs fixes, clarifications                         | `1.4.2 → 1.4.3` |

## Audience: who is this for?

Being explicit about the intended audience changes how careful you need to be:

```text
component-internal → business-unit-internal → company-internal → external-partner → external-public
     (move fast)                                                              (move very carefully)
```

An API for your own frontend can evolve faster than one used by 3,000 external developers.

## Functional naming

Name APIs and their hosts after **what they do**, not which team or tech built them: `order-management.api.example.com`, not `team-falcon-svc-prod-2.example.com`. Teams and technologies change; functions are more stable.

## Publish your spec

A spec that lives only in a repo isn't discoverable. Publish it to an **API portal/catalog** (Backstage, an internal developer portal, or even a static page) so people can find APIs before they build duplicates.

## Monitor real usage

Docs tell you how an API _should_ be used; monitoring tells you how it _is_ used. Track per endpoint **and per client**:

- Request rate, error rate (4xx vs 5xx), latency percentiles (p50, p95, p99).
- Which clients call what, so you can contact them about changes.
- Usage of deprecated endpoints (from [Deprecation & sunset](/course/evolution/deprecation/)).

A common starting point is the **RED method**: **R**ate, **E**rrors, **D**uration for every endpoint.

<Story kind="real-world" title="Zalando's API linter: Zally">

With hundreds of teams and APIs, reviewing every spec by hand doesn't scale. So Zalando built **Zally**, an open-source API linter that checks OpenAPI specs against their guidelines (many of the rules you've seen in this course) and reports violations by severity. Tools like **Spectral** do the same thing generically. Encoding your style guide as lint rules is how you get consistency at scale.

</Story>

<Story kind="fun-fact" title="Backstage">

Spotify built **Backstage** internally to answer "who owns this service and where are its docs?" across thousands of components, then open-sourced it in 2020. It's now a CNCF project and a common home for API catalogs. The problem is universal: past a certain size, _discoverability_ is the bottleneck, not technology.

</Story>

<Takeaways>

- Specs carry **owner, version, id and audience**; make APIs findable.
- Version the spec with **SemVer**; MAJOR bumps should be rare.
- Name APIs and hosts by **function**, not by team or tech.
- Publish specs to a catalog and **monitor usage per client**.

</Takeaways>
