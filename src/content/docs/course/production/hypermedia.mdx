<Hook>

The web works because pages link to other pages: you never construct a URL by hand to read the next article. APIs can borrow that idea. You don't need to go "full HATEOAS" to benefit: even a few well-placed links (`self`, `next`, related resources) make clients simpler and your URLs free to change.

</Hook>

## Level 1 of linking: IDs

```json
{ "id": "ord_42", "customer_id": "cus_7" }
```

The client must know the rule "customers live at `/customers/{id}`". That knowledge is now hard-coded in every client.

## Level 2: links

```json
{
  "id": "ord_42",
  "customer": { "href": "https://api.example.com/customers/cus_7" },
  "self": { "href": "https://api.example.com/orders/ord_42" }
}
```

The client follows the link. If the customer service moves to a new host tomorrow, clients don't care.

Keep link objects **simple and consistent**: an object with an `href` (and optionally a `title` or `type`), using a small set of well-known relation names: `self`, `next`, `prev`, `first`, `last`, plus domain names like `customer` or `items`.

## Use full, absolute URIs

<DoDont>
<Do>

```json
{ "next": "https://api.example.com/orders?cursor=abc" }
```

Works no matter where the response travels: logs, queues, other services.

</Do>
<Dont>

```json
{ "next": "/orders?cursor=abc" }
{ "next": "../orders?cursor=abc" }
```

Relative to _what_? Behind a gateway or proxy, the client may not know.

</Dont>
</DoDont>

## Links in the body, not the Link header

HTTP has a `Link` header (RFC 8288), and some APIs (like GitHub's) use it for pagination. For JSON APIs, it's simpler for clients if links live **in the JSON body**, alongside the data, where every JSON parser can see them.

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
class Link(BaseModel):
    href: str

class OrderOut(BaseModel):
    id: str
    status: str
    self: Link
    customer: Link

@app.get("/orders/{order_id}", name="get_order")
def get_order(order_id: str, request: Request) -> OrderOut:
    order = repo.get(order_id) or raise_404()
    return OrderOut(
        id=order.id,
        status=order.status,
        self=Link(href=str(request.url_for("get_order", order_id=order.id))),       # absolute
        customer=Link(href=str(request.url_for("get_customer", customer_id=order.customer_id))),
    )
```

</TabItem>
<TabItem label="Django" icon="seti:python">

```python
from rest_framework.reverse import reverse

class LinkField(serializers.Field):
    def __init__(self, view_name, lookup="pk", **kwargs):
        self.view_name, self.lookup = view_name, lookup
        super().__init__(source="*", read_only=True, **kwargs)

    def to_representation(self, obj):
        url = reverse(self.view_name, kwargs={"pk": getattr(obj, self.lookup)},
                      request=self.context["request"])  # request → absolute URI
        return {"href": url}

class OrderSerializer(serializers.ModelSerializer):
    self = LinkField("order-detail")
    customer = LinkField("customer-detail", lookup="customer_id")

    class Meta:
        model = Order
        fields = ["id", "status", "self", "customer"]
```

</TabItem>

const link = (c: Context, path: string) => ({ href: new URL(path, c.req.url).toString() });

app.get("/orders/:id", async (c) => {
  const order = await repo.get(c.req.param("id"));
  if (!order) return c.notFound();
  return c.json({

    status: order.status,
    self: link(c, `/orders/${order.id}`),
    customer: link(c, `/customers/${order.customerId}`),
  });
});

## Level 3: HATEOAS, honestly

**HATEOAS** (Hypermedia As The Engine Of Application State) goes further: the server tells the client what it can do **next**, and the client discovers actions instead of hard-coding them.

```json
{
  "id": "ord_42",
  "status": "PLACED",
  "_links": {
    "self": { "href": "https://api.example.com/orders/ord_42" },
    "pay": { "href": "https://api.example.com/orders/ord_42/payments" },
    "cancel": { "href": "https://api.example.com/orders/ord_42/cancellations" }
  }
}
```

Once shipped, `cancel` disappears and `track` appears. The client doesn't need to know the business rules for "can I cancel?"; it checks whether the link is there.

**Why isn't everyone doing it?** Because, in practice, client developers still read docs and hard-code flows, generic hypermedia clients never really took off, and formats (HAL, JSON:API, Siren, JSON-LD, Hydra…) never converged. Most teams adopt the cheap, high-value parts (`self`, pagination links, related resources) and skip the rest.

<Story kind="history" title="The acronym nobody can pronounce">

"HATEOAS" has been pronounced "hate-ee-oh-ass", "hat-ee-os", and "hey, toes!". Fielding himself mostly calls the idea the **hypermedia constraint**. Whatever you call it, it's the part of REST that most APIs skip, which is exactly what his 2008 rant (from [REST in a nutshell](/course/foundations/rest-in-a-nutshell/)) was about.

</Story>

<Takeaways>

- Links beat IDs + URL templates: clients follow, they don't construct.
- Use **absolute** URIs in simple `{"href": ...}` objects, in the JSON body.
- Start with `self`, pagination links and related resources.
- Full HATEOAS is optional; be pragmatic.

</Takeaways>
