A status code is the first thing a client looks at, and often the _only_ thing generic tooling looks at. Load balancers, retry libraries, dashboards and alerts all make decisions from that number. Return <Status code={200} /> with `{"error": "failed"}` and you've made every one of those tools blind.

</Hook>

## The five families

The first digit tells you almost everything:

| Family | Meaning       | Mnemonic                |
| ------ | ------------- | ----------------------- |
| `1xx`  | Informational | "Hold on…"              |
| `2xx`  | Success       | "Here you go!"          |
| `3xx`  | Redirection   | "Go away (over there)." |
| `4xx`  | Client error  | "You messed up."        |
| `5xx`  | Server error  | "I messed up."          |

Clients that don't know a specific code must treat it like the `x00` of its family. So an unknown <Status code={422} /> is at least understood as "a client error". That's why picking the right family matters most of all.

## The working set

You can build an excellent API with about 15 codes:

| Code                  | When to use it                                                               |
| --------------------- | ---------------------------------------------------------------------------- |
| <Status code={200} /> | Generic success with a body.                                                 |
| <Status code={201} /> | A resource was created. Add a `Location` header.                             |
| <Status code={202} /> | Accepted for async processing; not done yet.                                 |
| <Status code={204} /> | Success, nothing to return (common for `DELETE`).                            |
| <Status code={304} /> | Your cached copy is still fresh (conditional `GET`).                         |
| <Status code={400} /> | Malformed request or failed validation.                                      |
| <Status code={401} /> | Missing or invalid credentials (really means _unauthenticated_).             |
| <Status code={403} /> | Authenticated, but not allowed.                                              |
| <Status code={404} /> | Resource doesn't exist (or you're not allowed to know it does).              |
| <Status code={409} /> | Conflict with current state (duplicate, invalid state transition).           |
| <Status code={412} /> | A precondition (`If-Match`) failed: someone else changed it.                 |
| <Status code={415} /> | Unsupported `Content-Type`.                                                  |
| <Status code={422} /> | Well-formed but semantically invalid (many APIs prefer this for validation). |
| <Status code={429} /> | Slow down: rate limit hit.                                                   |
| <Status code={500} /> | Unexpected server failure.                                                   |
| <Status code={503} /> | Temporarily unavailable (maintenance, overload). Add `Retry-After`.          |

For the full annotated list, see the [status code cheat sheet](/reference/status-codes/).

## Be specific

When there's a more specific code that fits, use it. It lets clients react programmatically without parsing error messages.

```

```

## 404 is ambiguous

<Status code={404} /> can mean very different things: _"this order doesn't exist"_, _"this URL path
doesn't exist at all"_ (typo, wrong version, wrong host), or _"you're not allowed to see it, and I
won't confirm it exists"_. Clients should be careful about interpreting it, e.g. don't delete a
local record just because a `GET` returned 404: maybe the client called the wrong URL. Help them
with a precise error body.

## Status codes in code

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
from fastapi import HTTPException, Response, status

@app.post("/users", status_code=status.HTTP_201_CREATED)
def create_user(body: UserIn, response: Response) -> User:
    if repo.email_exists(body.email):
        raise HTTPException(status.HTTP_409_CONFLICT, "Email already registered")
    user = repo.create(body)
    response.headers["Location"] = f"/users/{user.id}"
    return user

@app.delete("/users/{user_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_user(user_id: str) -> None:
    if not repo.delete(user_id):
        raise HTTPException(status.HTTP_404_NOT_FOUND, "User not found")
```

<TabItem label="Django" icon="seti:python">

```python
from rest_framework import status
from rest_framework.exceptions import APIException

class Conflict(APIException):
    status_code = status.HTTP_409_CONFLICT
    default_detail = "Conflict with the current state of the resource."

class UserViewSet(viewsets.ModelViewSet):
    def perform_create(self, serializer):
        if User.objects.filter(email=serializer.validated_data["email"]).exists():
            raise Conflict("Email already registered")
        serializer.save()
    # create() → 201 (with Location if you add it), destroy() → 204 out of the box
```

## Don't pass through downstream codes blindly

If your service calls another service and _that_ returns <Status code={401} />, forwarding it tells **your** client their credentials are wrong, when actually _your_ service's credentials are wrong. Translate downstream failures into what they mean for your client, usually <Status code={500} />, <Status code={502} /> or <Status code={503} />.

## Avoid redirects in APIs

Browsers handle <Status code={301} /> and <Status code={302} /> gracefully. API clients… not so much: many don't follow redirects, or drop the body and switch `POST` to `GET` when they do. Prefer stable URLs and proper deprecation over redirects.

<Story kind="history" title="I'm a teapot">

<Status code={418} /> comes from RFC 2324, the **Hyper Text Coffee Pot Control Protocol**, an April
Fools' joke from 1998. A teapot asked to brew coffee should respond `418 I'm a teapot`. In 2017
there was a proposal to remove it from Node.js, Go and other platforms; the internet responded with
the **#save418** movement, and it stayed. Today RFC 9110 officially reserves the code so it can
never be assigned to anything serious. Please don't use it in production. (Okay, maybe for an easter
egg.)

</Story>

<Story kind="fun-fact" title="401 Unauthorized is misnamed">

<Status code={401} /> actually means **unauthenticated** ("I don't know who you are"), while
<Status code={403} /> means **unauthorized** ("I know who you are, and the answer is no"). The name
is a historical accident that has confused developers for over 25 years.

</Story>

<Takeaways>

- The **family** (first digit) matters most; clients fall back to it.
- Use a small working set, and the **most specific** code that fits.
- Never wrap errors in <Status code={200} />.
- 401 = who are you? 403 = no. 404 can be ambiguous.
- Translate downstream errors; avoid redirects in APIs.

</Takeaways>
