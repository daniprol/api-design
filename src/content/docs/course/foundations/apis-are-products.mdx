<Hook>

An API is a **user interface for developers**. Every endpoint name, every error message and every weird field is something a real person will read, puzzle over, and build on top of. Once they've built on it, you can't take it back. That's why API design is one of the highest-leverage skills in software: a good API makes hundreds of other people faster, and a bad one taxes them forever.

</Hook>

## Your API has customers

The moment someone other than you calls your endpoint, your API is a **product**. It has:

- **Users**: frontend teams, partner companies, other microservices, your future self at 3 AM.
- **A user experience**: how fast can someone go from "I found the docs" to "my first request worked"?
- **A lifecycle**: it's launched, it grows, it gets deprecated, and it's (eventually) retired.
- **Support costs**: every confusing design produces Slack questions, tickets and bugs.

Teams that treat APIs as products ask product questions _before_ writing code: **Who is this for? What job are they trying to do? What's the simplest thing that lets them do it?**

## The "leaky database" smell

The most common way an API stops being a product is when it becomes a thin wrapper over the database. Compare these two responses for the same order:

<DoDont>
<Do title="Designed for the consumer">

```json
{
  "id": "ord_8xK2",
  "status": "SHIPPED",
  "total": { "amount": "59.90", "currency": "EUR" },
  "created_at": "2026-03-14T09:26:53Z"
}
```

</Do>
<Dont title="Leaking the database">

```json
{
  "ORD_PK": 1842,
  "stat_cd": 3,
  "tot_amt_cents": 5990,
  "cur_fk": 978,
  "crt_ts": 1773480413,
  "legacy_flag2": null
}
```

</Dont>
</DoDont>

The right-hand version forces every consumer to learn your internal codes (`stat_cd: 3` means… shipped?), and it chains your public contract to your schema. Rename a column and you break your customers.

## Your framework is not your design

Modern frameworks make it _very_ easy to expose a model directly. That's great for prototypes and dangerous for products. Keep a separate, intentional **API model** between your storage and the outside world:

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
from pydantic import BaseModel
from datetime import datetime

class Money(BaseModel):
    amount: str        # decimal as string, no float surprises
    currency: str      # ISO 4217, e.g. "EUR"

class Order(BaseModel):  # the public contract, NOT the ORM model
    id: str
    status: str
    total: Money
    created_at: datetime

@app.get("/orders/{order_id}", response_model=Order)
def get_order(order_id: str) -> Order:
    row = db.fetch_order(order_id)          # internal shape
    return Order(
        id=row.public_id,
        status=STATUS_NAMES[row.stat_cd],
        total=Money(amount=str(row.tot_amt_cents / 100), currency=row.currency),
        created_at=row.crt_ts,
    )
```

</TabItem>
<TabItem label="Django" icon="seti:python">

```python
from rest_framework import serializers

class OrderSerializer(serializers.ModelSerializer):
    # Explicit public names, decoupled from model fields
    id = serializers.CharField(source="public_id")
    status = serializers.CharField(source="get_status_display")
    total = serializers.SerializerMethodField()
    created_at = serializers.DateTimeField(source="crt_ts")

    class Meta:
        model = Order
        fields = ["id", "status", "total", "created_at"]  # never "__all__"

    def get_total(self, order):
        return {"amount": str(order.total), "currency": order.currency}
```

</TabItem>
<TabItem label="Hono" icon="seti:typescript">

```ts
import { Hono } from "hono";

type Order = {
  id: string;
  status: "PLACED" | "SHIPPED" | "DELIVERED";
  total: { amount: string; currency: string };
  created_at: string;
};

const toApi = (row: OrderRow): Order => ({
  id: row.publicId,
  status: STATUS_NAMES[row.statCd],
  total: { amount: (row.totAmtCents / 100).toFixed(2), currency: row.currency },
  created_at: new Date(row.crtTs * 1000).toISOString(),
});

const app = new Hono();
app.get("/orders/:id", async (c) => c.json(toApi(await db.fetchOrder(c.req.param("id")))));
```

</TabItem>
</Tabs>

:::tip[Rule of thumb]
If `fields = "__all__"` or `return c.json(row)` appears in your code, you are publishing your database schema as an API. Sometimes that's fine for an internal admin tool. For anything with real consumers, map explicitly.
:::

## What makes an API "good"?

Zalando's guidelines open with a list of qualities that a good API should have. They're a great north star for everything else in this course:

| Quality                   | In plain words                                                  |
| ------------------------- | --------------------------------------------------------------- |
| Easy to understand        | A new developer can guess what an endpoint does from its name.  |
| Easy to use correctly     | The obvious way to call it is the right way.                    |
| Hard to misuse            | Mistakes produce clear errors, not silent corruption.           |
| Consistent                | Learn one endpoint, and you've learned the patterns of all.     |
| Robust & evolvable        | It can grow for years without breaking anyone.                  |
| Abstract from the backend | It talks about business concepts, not tables or implementation. |

<Story kind="history" title="The Bezos API mandate">

Around 2002, Jeff Bezos reportedly sent Amazon an email that changed the industry. Paraphrased: _all teams will expose their data and functionality through service interfaces; teams will communicate with each other only through these interfaces; no direct database access, no shared memory, no back doors. All interfaces must be designed to be externalizable. Anyone who doesn't do this will be fired._

The world learned about it in 2011, when Google engineer Steve Yegge accidentally posted a long internal rant publicly. One consequence of forcing every team to build "externalizable" APIs: Amazon could later sell its internal infrastructure to everyone else. You may have heard of it: **AWS**.

</Story>

<Story kind="real-world" title="Stripe's 7 lines of code">

Stripe famously won developers over in the early 2010s by making the _first API call_ ridiculously easy: a single `curl` command with a test key, right on the homepage. Payments APIs existed before Stripe. What Stripe sold was the **developer experience**. Many companies now measure "time to first successful call" as a product metric for exactly this reason.

</Story>

<Rule guide="zalando" title="API as a product">

Zalando's guidelines treat APIs as products with real customers, and ask teams to put themselves in the shoes of their consumers, aim for an excellent developer experience, and actively improve and maintain API consistency over the long term.

</Rule>

Exposing all model fields couples your public contract to your storage. Adding a sensitive column, renaming a field or changing a type now leaks out to (and breaks) consumers. Add the one field they need, on purpose.

</Quiz>

<Takeaways>

- An API with at least one consumer is a **product** with users, UX and a lifecycle.
- Design around the consumer's job, not your database tables.
- Keep an explicit API model between storage and the outside world.
- Good APIs are understandable, consistent, hard to misuse and built to evolve.

</Takeaways>
