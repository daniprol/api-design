## The 30-second definition

**REST** (Representational State Transfer) is an _architectural style_, not a protocol or a standard. Its core idea:

> Your system exposes **resources** (things), identified by **URLs**, that clients manipulate by exchanging **representations** (like JSON) using a small, **uniform set of operations** (HTTP methods).

Instead of inventing a new verb for every action (`getUser`, `createUser`, `banUser`…), you use the same handful of methods on many different things. That uniformity is the superpower: caches, proxies, browsers, monitoring tools and developers all already understand `GET`, `PUT` and `DELETE`.

## The constraints, briefly

REST is defined by a set of constraints. You don't need to memorize them, but they explain _why_ the rules in the rest of this course exist:

| Constraint                | What it means                                                | Why you care                                  |
| ------------------------- | ------------------------------------------------------------ | --------------------------------------------- |
| Client–server             | UI and data storage evolve separately                        | Frontend and backend teams ship independently |
| Stateless                 | Each request carries everything needed to process it         | Any server can handle any request: scaling!   |
| Cacheable                 | Responses say whether they can be cached                     | Speed, and less load on your servers          |
| Uniform interface         | Resources, URLs, standard methods, self-descriptive messages | Generic tooling just works                    |
| Layered system            | Clients can't tell if there's a proxy or gateway in between  | Load balancers, CDNs, API gateways            |
| Code on demand (optional) | Servers may send executable code                             | JavaScript in browsers. Rare for APIs.        |

## The Richardson Maturity Model

Leonard Richardson proposed a simple ladder to measure how "RESTful" an API is. Let's climb it with the same feature: _cancel order 42_.

### Level 0: the swamp of POX

One URL, one method, everything in the body. (POX = Plain Old XML. These days it's JSON, but the swamp is the same.)

```http
POST /api
Content-Type: application/json

{ "action": "cancelOrder", "order_id": 42 }
```

### Level 1: resources

Different things get different URLs. Still `POST` for everything, though.

```http
POST /orders/42/cancel
```

### Level 2: HTTP verbs (and status codes)

Use methods for their meaning, and status codes for outcomes. This is where most good APIs live.

```http
GET /orders/42              → 200 OK
PATCH /orders/42            → 200 OK
{ "status": "CANCELED" }

DELETE /orders/42           → 204 No Content
GET /orders/999             → 404 Not Found
```

### Level 3: hypermedia controls (HATEOAS)

Responses include links that tell the client what it can do next, like a web page with buttons.

```json
{
  "id": "42",
  "status": "PLACED",
  "_links": {
    "self": { "href": "https://api.example.com/orders/42" },
    "cancel": { "href": "https://api.example.com/orders/42/cancellation" }
  }
}
```

We'll come back to level 3 in [Links & hypermedia](/course/production/hypermedia/).

<DoDont>
<Do title="Level 2">

```http
GET    /orders/42
DELETE /orders/42
```

The method says _what_, the URL says _which thing_.

</Do>
<Dont title="Level 0 in disguise">

```http
POST /getOrder      {"id": 42}
POST /deleteOrder   {"id": 42}
```

Caches, proxies and retries can't tell reads from writes.

</Dont>
</DoDont>

<Story kind="history" title="A PhD thesis that runs the web">

REST was defined by **Roy Fielding** in chapter 5 of his 2000 doctoral dissertation at UC Irvine, _Architectural Styles and the Design of Network-based Software Architectures_. Fielding wasn't theorizing in a vacuum: he was one of the principal authors of the HTTP/1.1 specification. REST was his description of _why the web worked so well_, written after helping build it.

</Story>

<Story kind="fun-fact" title="Fielding's frustration">

In 2008, Fielding wrote a blog post titled _"REST APIs must be hypertext-driven"_, complaining that people were calling everything REST, even APIs without hypermedia. By his definition, most "REST APIs" in the world are not REST. The industry mostly shrugged and kept the name. That's why people now say "RESTful" or "REST-ish".

</Story>

<Takeaways>

- REST is an architectural style: **resources + URLs + representations + a uniform interface**.
- Statelessness and caching are what make REST scale.
- The Richardson model: 0 (one endpoint) → 1 (resources) → 2 (verbs + status codes) → 3 (hypermedia).
- Level 2 is the practical sweet spot; it's what Zalando mandates.

</Takeaways>
