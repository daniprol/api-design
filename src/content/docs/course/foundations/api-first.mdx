<Hook>

Changing an API design on a whiteboard costs five minutes. Changing it after three teams have integrated costs three months. **API first** is the habit of designing and reviewing the contract _before_ anyone writes the implementation, so you make your mistakes while they're still cheap.

</Hook>

## Design first vs. code first

There are two ways to end up with an API specification:

| Approach         | How it works                                                                        | Great when…                                         |
| ---------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------- |
| **Design first** | Write the OpenAPI spec, review it, then implement it.                               | Several teams depend on the API; the API is public. |
| **Code first**   | Write the code, generate the spec from it (FastAPI, drf-spectacular, hono-openapi). | Small teams, fast iteration, internal APIs.         |

They're less opposed than they sound. What matters is the _principle_: **the contract is a deliberate artifact that is reviewed by humans before it becomes real**. You can do that by writing YAML, or by opening a pull request with only the route signatures and models and letting consumers comment before you write the logic.

<Steps>

1. **Understand the domain.** Talk to the people who will call the API. What are the nouns? What are the jobs to be done?
2. **Draft the contract.** Resources, operations, payloads, errors. In OpenAPI or as typed stubs.
3. **Review it.** Peers and consumers review the _contract_, ideally against a style guide (like this course!).
4. **Mock it.** Consumers can start building against a mock server generated from the spec.
5. **Implement and test against the contract.** The spec becomes a test oracle, not just documentation.

</Steps>

## OpenAPI in 30 seconds

OpenAPI (formerly Swagger) is the de-facto language for describing HTTP APIs. A tiny but complete example:

```yaml title="openapi.yaml"
openapi: 3.1.0
info:
  title: Order API
  version: 1.2.0
  description: Place and track customer orders.
paths:
  /orders/{order_id}:
    get:
      summary: Get one order
      parameters:
        - name: order_id
          in: path
          required: true
          schema: { type: string }
      responses:
        "200":
          description: The order.
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Order" }
        "404":
          description: No order with this id.
components:
  schemas:
    Order:
      type: object
      required: [id, status]
      properties:
        id: { type: string, example: ord_8xK2 }
        status: { type: string, example: SHIPPED }
```

## Getting a spec from your framework

All three of our frameworks can produce OpenAPI. Use it, but remember: a generated spec is only as good as the types and descriptions you give it.

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI(title="Order API", version="1.2.0")

class Order(BaseModel):
    id: str = Field(examples=["ord_8xK2"])
    status: str = Field(description="Lifecycle state of the order.")

@app.get(
    "/orders/{order_id}",
    response_model=Order,
    summary="Get one order",
    responses={404: {"description": "No order with this id."}},
)
def get_order(order_id: str): ...

# Spec served at /openapi.json, interactive docs at /docs
```

<TabItem label="Hono" icon="seti:typescript">

```ts
import { OpenAPIHono, createRoute, z } from "@hono/zod-openapi";

const Order = z
  .object({
    id: z.string().openapi({ example: "ord_8xK2" }),
    status: z.string().openapi({ description: "Lifecycle state of the order." }),
  })
  .openapi("Order");

const getOrder = createRoute({
  method: "get",
  path: "/orders/{order_id}",
  summary: "Get one order",
  request: { params: z.object({ order_id: z.string() }) },
  responses: {
    200: { description: "The order.", content: { "application/json": { schema: Order } } },
    404: { description: "No order with this id." },
  },
});

const app = new OpenAPIHono();
app.openapi(getOrder, (c) => c.json({ id: c.req.valid("param").order_id, status: "SHIPPED" }, 200));
app.doc("/openapi.json", { openapi: "3.1.0", info: { title: "Order API", version: "1.2.0" } });
```

## Write for humans, too

A spec says _what_ is possible. People also need to know _why_ and _how_: a getting-started guide, authentication walkthrough, common workflows ("how do I refund an order?") and the gotchas. Zalando calls this the **API user manual**.

<DoDont>
<Do>

```yaml
description: |
  Cancels an order. Only orders in status PLACED
  or PAID can be cancelled; shipped orders must be
  returned via POST /returns instead.
```

</Do>
<Dont>

```yaml
description: Cancel order endpoint.
```

</Dont>
</DoDont>

<Story kind="history" title="From Swagger to OpenAPI">

Swagger was created by Tony Tam in 2010 at the dictionary site Wordnik, to describe their own API. It became so popular that in 2015 SmartBear donated the specification to the Linux Foundation, where it was renamed the **OpenAPI Specification**. "Swagger" lives on as the name of the tooling (Swagger UI, Swagger Editor). So if someone says "the Swagger file", they mean the OpenAPI spec.

</Story>

<Story kind="fun-fact" title="U.S. English, everywhere">

Zalando is a German company, with engineers from over 100 nations. Their rule: APIs are written in U.S. English. That means `color`, not `colour`, and `canceled`… or is it `cancelled`? Both are accepted in U.S. English, which is exactly why a style guide that picks one is so useful.

</Story>

<Takeaways>

- Design and review the contract **before** implementation.
- OpenAPI is the common language; generated specs are fine if you curate types and descriptions.
- A spec is not enough: write a user manual with workflows and gotchas.
- Pick one language and style (Zalando: U.S. English) and stick to it.

</Takeaways>
