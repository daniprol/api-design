<Hook>

Not everything finishes in 200 ms. Generating a 500-page PDF, importing 1 million products, or provisioning a server takes seconds or hours. Holding an HTTP connection open that long is fragile: proxies time out, mobile apps go to background. And when you send 100 things in one request, "it worked" is rarely the whole truth. Some succeeded, some didn't.

</Hook>

## Part 1: long-running work with 202 Accepted

The pattern: **accept the work, give the client a URL to check on it**.

```http
POST /reports
{ "type": "SALES", "period": "2026-Q1" }

HTTP/1.1 202 Accepted
Location: https://api.example.com/report-jobs/job_91
Retry-After: 5

{ "id": "job_91", "status": "PENDING" }
```

The job is a **resource**, so the client polls it with plain `GET`:

```http
GET /report-jobs/job_91
→ 200 OK  { "id": "job_91", "status": "RUNNING", "progress": 0.4 }

GET /report-jobs/job_91
→ 200 OK  {
    "id": "job_91",
    "status": "SUCCEEDED",
    "result": "https://api.example.com/reports/rep_33"
  }
```

```text
PENDING ──► RUNNING ──► SUCCEEDED
                  └───► FAILED (with a problem object)
```

:::tip[Polling isn't the only option]
Polling is simple and works everywhere. If clients need instant notification, add **webhooks** (you call them back) or an **event stream** on top. Many APIs offer the job resource _and_ a webhook.
:::

from fastapi import BackgroundTasks

@app.post("/reports", status_code=202)
def request_report(body: ReportRequest, background: BackgroundTasks, response: Response):
    job = jobs.create(kind="report", params=body.model_dump())
    background.add_task(generate_report, job.id)  # for real workloads: a queue (Celery, RQ, arq…)
    response.headers["Location"] = f"/report-jobs/{job.id}"
    response.headers["Retry-After"] = "5"
    return {"id": job.id, "status": job.status}

@app.get("/report-jobs/{job_id}")
def get_job(job_id: str) -> Job:
    return jobs.get(job_id) or raise_404()

@shared_task
def generate_report(job_id):
    job = ReportJob.objects.get(pk=job_id)
    job.status = "RUNNING"; job.save()
    try:
        job.result = build_report(job.params); job.status = "SUCCEEDED"

class ReportCreate(APIView):
    def post(self, request):
        job = ReportJob.objects.create(params=request.data, status="PENDING")
        generate_report.delay(job.pk)
        return Response(

            status=202,
            headers={"Location": f"/report-jobs/{job.pk}", "Retry-After": "5"},
        )

## Part 2: batch requests with 207 Multi-Status

Batch endpoints save round trips: "create these 100 products". But what if 97 succeed and 3 fail? Neither <Status code={201} /> nor <Status code={400} /> tells the truth.

Answer with <Status code={207} /> and a **per-item result**:

```http
POST /products/batch
[ {...}, {...}, {...} ]

HTTP/1.1 207 Multi-Status
{
  "items": [
    { "id": "p_1", "status": 201 },
    { "id": "p_2", "status": 201 },
    { "status": 400, "problem": { "title": "Invalid price", "detail": "price.amount must be > 0" } }
  ]
}
```

Rules of thumb:

- <Status code={207} /> means "look inside". Clients **must** check each item.
- If the batch _as a whole_ is invalid (malformed JSON, too many items, no auth), return a normal 4xx.
- Document whether the batch is **atomic** (all or nothing) or **best effort**. Best effort is more common, and is what 207 is for.

<Story kind="history" title="207 was born in WebDAV">

<Status code={207} /> comes from **WebDAV** (RFC 2518, 1999), the extension that turned HTTP into a
remote file system: it's what let you "map a network drive" to a web server. Operations like "delete
this folder" touch many files, some of which might be locked, so WebDAV needed a way to report
per-file results. API designers later borrowed it for batch operations.

</Story>

<Story kind="real-world" title="Google's long-running operations">

Google Cloud APIs standardize async work as **long-running operations** (AIP-151): methods return an `Operation` resource with a `name`, a `done` flag, and either a `response` or an `error`. Clients poll `GET /v1/operations/{name}`. Same idea as our job resource, applied consistently across hundreds of APIs.

</Story>

<Rule guide="zalando" id="253" level="MAY" title="Support asynchronous request processing">

Zalando's recommended pattern: return <Status code={202} /> with a `Location` to a job (or the eventual resource), and model the job as a resource clients can `GET`.

</Rule>

<Rule guide="zalando" id="152" level="MUST" title="Use code 207 for batch or bulk requests" />

<Quiz
  question="A batch import of 50 items: 48 succeed, 2 fail validation. Best response?"
  options={[
    "<code>201 Created</code>, since most succeeded",
    "<code>400 Bad Request</code>, since some failed",
    "<code>207 Multi-Status</code> with per-item results",
    "<code>202 Accepted</code>",
  ]}
  answer={2}
>

Neither a blanket success nor a blanket failure is true. `207` with a status per item lets the client retry exactly the two that failed.

</Quiz>

<Takeaways>

- Slow work → <Status code={202} /> + `Location` to a **job resource** the client can poll.
- Model job states explicitly (`PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`).
- Batch with partial success → <Status code={207} /> + per-item status.
- Document whether batches are atomic or best effort.

</Takeaways>
