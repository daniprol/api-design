<Hook>

So far, clients have been _asking_ your API questions. But many systems also need to _tell_ others what happened: "order placed", "payment failed", "stock changed". Those events flow through Kafka, a message bus or webhooks to consumers you may never meet. **An event schema is an API contract**, with all the same design and compatibility concerns, and fewer chances to fix mistakes.

</Hook>

## Why events?

```text
Request/response:  Checkout ──"create shipment"──► Shipping   (Checkout must know Shipping)
Events:            Checkout ──"order.placed"──► bus ──► Shipping, Billing, Analytics, Emails…
```

With events, the producer doesn't need to know who's listening. New consumers can join without changing the producer. The price: the event's shape is now depended on by people you can't see.

## Anatomy of a good event

```json
{
  "metadata": {
    "eid": "5b2c9a4e-8f1d-4a3b-9c6e-2d7f0a1b3c4d",
    "event_type": "shop.order-placed",
    "occurred_at": "2026-03-14T09:26:53Z",
    "version": "1.2.0",
    "flow_id": "4bf92f3577b34da6"
  },
  "order_id": "ord_42",
  "customer_id": "cus_7",
  "total": { "amount": "59.90", "currency": "EUR" },
  "item_count": 3
}
```

| Part          | Why it's there                                                          |
| ------------- | ----------------------------------------------------------------------- |
| `eid`         | Unique event ID: consumers use it to detect duplicates.                 |
| `event_type`  | A registered, namespaced, versioned type. Consumers subscribe to types. |
| `occurred_at` | When it happened in the business (not when it was sent).                |
| `version`     | Schema version (SemVer), so consumers know what to expect.              |
| `flow_id`     | Trace correlation across the request that caused it.                    |
| payload       | Business data, following the same JSON rules as your REST API.          |

## Two categories

**Business (general) events** describe a **step in a business process**: "order placed", "payment authorized", "parcel delivered". Consumers react to things that _happened_.

**Data change events** describe a **mutation of an entity**: created, updated, deleted, often with a full snapshot. They're used to replicate data across services ("keep a local copy of products").

```json
{
  "metadata": { "eid": "…", "event_type": "shop.product-changed", "occurred_at": "…" },
  "data_op": "U",
  "data_type": "shop:product",
  "data": { "id": "p_1", "name": "Sneaker", "price": { "amount": "79.00", "currency": "EUR" } }
}
```

## Ordering and partitioning

Events for the **same entity** must be processed in order: "price changed to 79" then "to 89" must not be applied backwards. Two techniques:

- **Partition by entity key** (`product_id`): message buses like Kafka guarantee order **within a partition**, so all events for `p_1` land in order.
- **Explicit ordering fields**: a per-entity sequence number or version, so consumers can detect out-of-order or stale events.

```python
from uuid import uuid4

class EventMetadata(BaseModel):
    eid: str = Field(default_factory=lambda: str(uuid4()))
    event_type: str
    occurred_at: AwareDatetime
    version: str
    flow_id: str | None = None

class OrderPlaced(BaseModel):
    metadata: EventMetadata
    order_id: str
    customer_id: str
    total: Money

async def publish_order_placed(order: Order, flow_id: str):
    event = OrderPlaced(
        metadata=EventMetadata(event_type="shop.order-placed", occurred_at=order.placed_at,
                               version="1.2.0", flow_id=flow_id),
        order_id=order.id, customer_id=order.customer_id, total=order.total,
    )
    # key = order id → all events of one order go to the same partition, in order
    await producer.send("shop.order-placed", key=order.id, value=event.model_dump_json())
```

```python
# Transactional outbox: write the event in the SAME transaction as the data change,
# a relay process publishes outbox rows to the bus. No "saved but never published".
class OutboxEvent(models.Model):
    eid = models.UUIDField(default=uuid.uuid4, unique=True)
    event_type = models.CharField(max_length=200)
    partition_key = models.CharField(max_length=200)
    payload = models.JSONField()
    occurred_at = models.DateTimeField()
    published_at = models.DateTimeField(null=True)

def place_order(cart, user):
    with transaction.atomic():
        order = Order.objects.create(customer=user, total=cart.total)
        OutboxEvent.objects.create(
            event_type="shop.order-placed",
            partition_key=str(order.pk),
            occurred_at=order.placed_at,
            payload={"order_id": str(order.pk), "customer_id": str(user.pk),
                     "total": {"amount": str(order.total), "currency": "EUR"}},
        )
    return order
```

## Event schemas follow API rules

Everything from this course applies: snake_case, RFC 3339 dates, money objects, no `null` booleans, **backward compatibility**. Register event types and their schemas somewhere central (a schema registry or catalog), with an owner, and review them like API specs. Events tend to live even longer than endpoints, because they're replayed and archived.

<DoDont>
<Do>

```json
{
  "metadata": { "eid": "…", "event_type": "shop.order-placed", "occurred_at": "…" },
  "order_id": "ord_42",
  "total": { "amount": "59.90", "currency": "EUR" }
}
```

Business meaning, stable schema, ID for deduplication.

</Do>
<Dont>

```json
{
  "table": "orders",
  "op": "INSERT",
  "row": { "ORD_PK": 1842, "stat_cd": 3, "tot_amt_cents": 5990 }
}
```

A database changelog leaking to the world: every column rename is a breaking change.

</Dont>

<Story kind="real-world" title="Nakadi, Zalando's event bus">

Zalando built **Nakadi**, an open-source event bus with a RESTful API on top of Kafka. Its design bakes in many rules from this lesson: registered event types with JSON schemas, compatibility modes, mandatory metadata (`eid`, `occurred_at`), and the business vs. data change categories. That's why Zalando's guidelines have whole chapters on events.

</Story>

<Story kind="history" title="Webhooks: events over HTTP">

The term **webhook** was coined by Jeff Lindsay around 2007: "user-defined HTTP callbacks". Instead of polling an API, you give it a URL and it `POST`s events to you. Stripe, GitHub and Slack all use them. The **CloudEvents** specification (a CNCF project) later standardized a common event envelope (`id`, `source`, `type`, `time`) so different producers can look alike.

</Story>

<Quiz
  question="Why partition data change events by the entity's ID?"
  options={[
    "To spread load randomly across consumers",
    "So all events of the same entity are delivered in order",
    "To encrypt the events",
    "Because event IDs must be unique",
  ]}
  answer={1}
>

Message buses typically guarantee ordering only within a partition. Hashing by entity ID puts all of an entity's events in the same partition, so consumers see them in order.

</Quiz>

<Takeaways>

- Events are a **public interface**: design, review and version them like APIs.
- Always include metadata: unique `eid`, `event_type`, `occurred_at`, schema version.
- **Business events** describe process steps; **data change events** describe mutations.
- Preserve per-entity ordering: partition by key and/or explicit sequence numbers.

</Takeaways>
