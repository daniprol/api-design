<Hook>

Here's the uncomfortable truth about event systems: **you will receive the same event twice**, and sometimes **in the wrong order**. Not because anything is broken, but because "exactly once, in order" is impossible to guarantee across networks. Good consumers are designed for this from the start, and then it stops being scary.

</Hook>

## Why duplicates happen

```text
1. Consumer receives event #1, processes it ✅
2. Consumer crashes before committing "I processed #1"
3. Consumer restarts → bus redelivers event #1 → processed again 💸
```

Message buses typically offer **at-least-once** delivery. That's the honest guarantee. The consumer makes it _effectively_ once by being **idempotent**.

## Technique 1: deduplicate by event ID

Remember `eid` from the [previous lesson](/course/events/events-as-apis/)? Keep a record of processed IDs, and do the work and the record **in one transaction**.

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
async def handle_order_placed(raw: bytes):
    event = OrderPlaced.model_validate_json(raw)

    async with db.transaction():
        # INSERT ... ON CONFLICT DO NOTHING returns 0 rows if we've seen it
        inserted = await db.execute(
            "INSERT INTO processed_events (eid) VALUES (:eid) ON CONFLICT DO NOTHING",
            {"eid": event.metadata.eid},
        )
        if inserted == 0:
            return  # duplicate: already handled, safely ignore

        await loyalty.add_points(event.customer_id, points_for(event.total))
    # commit offset to the bus only after the transaction committed
```

## Technique 2: make the operation itself idempotent

Even better: design the effect so repeating it changes nothing.

<DoDont>
<Do title="Idempotent effect">

```sql
-- set to a value: repeating it is harmless
UPDATE products SET price = 79.00 WHERE id = 'p_1';
INSERT ... ON CONFLICT (order_id) DO NOTHING;
```

</Do>
<Dont title="Non-idempotent effect">

```sql
-- increments: every duplicate adds again
UPDATE accounts SET points = points + 100;
UPDATE stock SET quantity = quantity - 1;
```

</Dont>
</DoDont>

## Out-of-order events

Events for the same entity may arrive out of order (retries, multiple partitions, replays). Use an **ordering field** from the producer (a version or sequence number) and ignore anything older than what you have:

```sql
-- only apply if this event is newer than what we've stored
UPDATE product_copies
SET name = :name, price = :price, version = :version
WHERE id = :id AND version < :version;
```

This is "last writer wins, by version", and it handles duplicates for free: an exact duplicate has the same version, so it's ignored too.

## Don't put sensitive data in events

Events are copied to many consumers, retained for days or forever, replayed and archived in data lakes. Deleting a person's data (hello, **GDPR**) from every copy of every event is a nightmare. Prefer **IDs over personal data**, and let authorized consumers fetch details through an API that enforces permissions.

<DoDont>
<Do>

```json
{ "customer_id": "cus_7", "order_id": "ord_42" }
```

</Do>
<Dont>

```json
{ "customer_email": "ada@example.com", "card_number": "4111111111111111", "home_address": "…" }
```

</Dont>
</DoDont>

## Events must stay backward compatible

Consumers may replay old events years later, or be months behind on deployments. The rules from [Backward compatibility](/course/evolution/compatibility/) apply even more strictly: only add optional fields, never remove or retype, and consumers must ignore unknown fields.

<Story kind="fun-fact" title="Exactly-once is a (useful) lie">

Kafka famously added "exactly-once semantics" in 2017. It's a real and impressive feature, but read the fine print: it covers reading from and writing to Kafka within a transaction. The moment your consumer has a side effect _outside_ Kafka (sending an email, charging a card, calling an API), you're back to at-least-once, and idempotency is your job again.

</Story>

<Story kind="real-world" title="Stripe tells you to expect duplicates">

Stripe's webhook documentation says it plainly: endpoints might occasionally receive the same event more than once, so you should log the event IDs you've processed and skip duplicates. It also says events may not arrive in the order they were generated. When a company that processes billions of events gives this advice, believe it.

</Story>

<Takeaways>

- Delivery is **at-least-once**: duplicates and reordering are normal.
- Deduplicate by `eid` in the same transaction as the side effect.
- Prefer idempotent effects ("set to X") over increments.
- Use versions to ignore stale events; keep **personal data** out of events.

</Takeaways>
