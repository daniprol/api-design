<Hook>

Once your collections are paginated, the next question is always: _"Can I get only the shipped orders from last week, newest first, and only their ids and totals?"_ If every API answers that with different parameter names, every client has to read every doc. If they all use the **same small vocabulary**, clients just guess, and they're right.

</Hook>

## The conventional vocabulary

A good, widely used set (this is Zalando's list):

| Parameter | Meaning                         | Example                   |
| --------- | ------------------------------- | ------------------------- |
| `q`       | Free-text search                | `?q=red sneakers`         |
| `sort`    | Sort order, `-` for descending  | `?sort=-created_at,id`    |
| `fields`  | Return only these fields        | `?fields=id,status,total` |
| `embed`   | Inline related resources        | `?embed=customer,items`   |
| `limit`   | Page size                       | `?limit=50`               |
| `cursor`  | Pagination cursor               | `?cursor=eyJpZCI6…`       |
| `offset`  | Pagination offset (if you must) | `?offset=100`             |

Plus **filters named after the field** they filter:

```http
GET /orders?status=SHIPPED&customer_id=cus_7&created_after=2026-03-01T00:00:00Z
```

## Filtering

Keep simple filters as query parameters with the field's name. For ranges, use suffixes like `_after`/`_before` or `min_`/`max_`.

For "any of these values", choose **one** collection format and document it:

```http
GET /orders?status=SHIPPED,DELIVERED          # comma-separated (CSV)
GET /orders?status=SHIPPED&status=DELIVERED   # repeated parameter (multi)
```

Both are common. OpenAPI calls them `style: form, explode: false` and `explode: true`. Mixing them within one API is the real mistake.

## Sorting

```http
GET /products?sort=-rating,price
```

Sort by `rating` descending, then `price` ascending. (Zalando also allows a `+` prefix for ascending, but remember that a raw `+` in a query string decodes to a space, so clients must send it as `%2B`.) Always add a unique tiebreaker internally (like `id`) so pagination is stable.

SORTABLE = {"created_at", "total", "id"}

@app.get("/orders")
def list_orders(
    status: Annotated[str | None, Query(description="Comma-separated, e.g. SHIPPED,DELIVERED")] = None,
    customer_id: str | None = None,
    created_after: AwareDatetime | None = None,
    sort: str = "-created_at",
    fields: str | None = None,
):
    query = select(OrderRow)
    if status:
        query = query.where(OrderRow.status.in_(status.split(",")))
    if customer_id:
        query = query.where(OrderRow.customer_id == customer_id)
    if created_after:
        query = query.where(OrderRow.created_at > created_after)
    for key in sort.split(","):
        name = key.lstrip("-")
        if name not in SORTABLE:
            raise HTTPException(400, f"Cannot sort by '{name}'")
        col = getattr(OrderRow, name)
        query = query.order_by(col.desc() if key.startswith("-") else col)
    ...

import django_filters
from rest_framework.filters import OrderingFilter, SearchFilter

class CharInFilter(django_filters.BaseInFilter, django_filters.CharFilter):
    pass  # BaseInFilter must be combined with a concrete filter type

class OrderFilter(django_filters.FilterSet):
    status = CharInFilter(field_name="status")  # ?status=A,B
    created_after = django_filters.IsoDateTimeFilter(field_name="created_at", lookup_expr="gt")

    class Meta:
        model = Order
        fields = ["status", "customer_id", "created_after"]

class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Order.objects.all()
    serializer_class = OrderSerializer
    filter_backends = [django_filters.rest_framework.DjangoFilterBackend,
                       SearchFilter, OrderingFilter]
    filterset_class = OrderFilter
    search_fields = ["reference", "customer__email"]   # ?search= → rename to "q":
    ordering_fields = ["created_at", "total"]          # ?ordering= → rename to "sort":
    ordering = ["-created_at"]

# settings.py: use the conventional names
REST_FRAMEWORK = {"SEARCH_PARAM": "q", "ORDERING_PARAM": "sort"}

## Complex queries: make the search a resource

When filters get truly complex (nested AND/OR, many fields, long lists of ids) query strings hit their limits: URLs get unreadable, and some proxies cap them at a few KB. Model the search as a resource and send the query as JSON:

```http
POST /order-searches
Content-Type: application/json

{
  "filter": {
    "and": [
      { "field": "status", "in": ["SHIPPED", "DELIVERED"] },
      { "or": [
        { "field": "total.amount", "gte": "100.00" },
        { "field": "customer.tier", "eq": "GOLD" }
      ]}
    ]
  },
  "sort": ["-created_at"],
  "limit": 50
}
```

You lose HTTP caching for these (it's a `POST`), so keep simple queries on `GET`.

## Implicit filtering must be documented

Often results are filtered by _who's asking_: `GET /orders` returns only the caller's orders. That's fine, but **say so in the docs**. Otherwise an admin and a customer calling the same URL get different results and nobody knows why.

<Story kind="war-story" title="The query string that leaked to analytics">

Sensitive data in query strings ends up in places you'd never expect: server access logs, proxy logs, browser history, and `Referer` headers sent to third parties. In 2015, the Associated Press reported that HealthCare.gov was sending details like age, income, ZIP code and whether someone was pregnant to third-party tracking sites, partly through URLs. If a filter value is sensitive (an email, a national ID), prefer a `POST` search with a body, or at least scrub your logs.

</Story>

<Takeaways>

- Use a **conventional vocabulary**: `q`, `sort`, `fields`, `embed`, `limit`, `cursor`.
- Filters are named after the field; pick one multi-value format.
- Whitelist sortable fields; add a unique tiebreaker.
- For complex queries, `POST` a search resource with a JSON body.
- Document implicit (permission-based) filtering.

</Takeaways>
