<Hook>

Every collection starts small. Then one day `GET /orders` returns 2 million rows, your database melts, and the mobile app times out. **Paginate from day one**: adding pagination later is a breaking change, and choosing the wrong kind is a performance time bomb.

</Hook>

## Offset pagination: simple, but…

The classic: "skip N, take M".

```http
GET /orders?offset=40&limit=20
```

```sql
SELECT * FROM orders ORDER BY created_at DESC OFFSET 40 LIMIT 20;
```

Easy to understand, lets you jump to page 37. But it has two nasty problems:

1. **It gets slower with depth.** `OFFSET 1000000` makes the database read and throw away a million rows.
2. **Items shift while you paginate.** If a new order arrives while you're on page 2, everything moves down by one: page 3 repeats an item you already saw. If one is deleted, you _skip_ one.

```text
Page 1: [A B C]        ← you read this
           new order Z arrives at the top
Page 2: [C D E]        ← C again! 🙃
```

## Cursor pagination: robust and fast

Instead of "skip N", the server gives you an **opaque cursor** that encodes _where you left off_, typically the sort key of the last item.

```http
GET /orders?limit=20
→ { "items": [...], "next": "https://api.example.com/orders?cursor=eyJjIjoiMjAyNi0wMy0xNFQwOToyNjo1M1oiLCJpZCI6Im9yZF80MiJ9&limit=20" }
```

```sql
-- cursor decodes to (created_at, id) of the last item seen
SELECT * FROM orders
WHERE (created_at, id) < ('2026-03-14T09:26:53Z', 'ord_42')
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

With an index on `(created_at, id)`, page 50,000 is as fast as page 1. Inserts and deletes don't cause duplicates or gaps. The trade-off: no jumping to an arbitrary page. (For feeds, timelines, syncs and infinite scroll, nobody needs page 37 anyway.)

:::tip[Make cursors opaque]
Base64-encode the cursor (or encrypt it) and document it as an opaque string. If clients can't parse it, you're free to change its contents later.
:::

## The response: a page object with links

Give clients **links**, not instructions for building URLs:

```json
{
  "self": "https://api.example.com/orders?cursor=abc&limit=20",
  "first": "https://api.example.com/orders?limit=20",
  "prev": "https://api.example.com/orders?cursor=xyz&limit=20",
  "next": "https://api.example.com/orders?cursor=def&limit=20",
  "items": [{ "id": "ord_42" }, { "id": "ord_41" }]
}
```

When `next` is missing, you're at the end. The client loop becomes trivial:

```ts
let url: string | undefined = "https://api.example.com/orders?limit=100";
while (url) {
  const page = await fetch(url).then((r) => r.json());
  process(page.items);
  url = page.next; // no URL building, no off-by-one errors
}
```

<TabItem label="FastAPI" icon="seti:python">

```python
import base64, json

def encode_cursor(created_at: datetime, id_: str) -> str:
    raw = json.dumps({"c": created_at.isoformat(), "id": id_})
    return base64.urlsafe_b64encode(raw.encode()).decode()

def decode_cursor(cursor: str) -> tuple[str, str]:
    data = json.loads(base64.urlsafe_b64decode(cursor))
    return data["c"], data["id"]

@app.get("/orders")
def list_orders(request: Request, cursor: str | None = None,
                limit: int = Query(20, ge=1, le=100)) -> OrderPage:
    after = decode_cursor(cursor) if cursor else None
    rows = repo.orders_page(after=after, limit=limit + 1)  # fetch one extra
    has_more = len(rows) > limit
    rows = rows[:limit]
    next_url = None
    if has_more:
        last = rows[-1]
        next_url = str(request.url.include_query_params(
            cursor=encode_cursor(last.created_at, last.id)))
    return OrderPage(self=str(request.url), next=next_url, items=rows)
```

```python
from rest_framework.pagination import CursorPagination
from rest_framework.response import Response

class OrderCursorPagination(CursorPagination):
    ordering = ("-created_at", "-id")    # needs a unique, stable ordering
    page_size = 20
    page_size_query_param = "limit"
    max_page_size = 100

    def get_paginated_response(self, data):  # Zalando-style page object
        return Response({
            "self": self.request.build_absolute_uri(),
            "next": self.get_next_link(),
            "prev": self.get_previous_link(),
            "items": data,
        })

class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Order.objects.all()
    serializer_class = OrderSerializer
    pagination_class = OrderCursorPagination  # cursors are opaque + base64 ✨
```

```ts
const encode = (o: object) => Buffer.from(JSON.stringify(o)).toString("base64url");
const decode = (s: string) => JSON.parse(Buffer.from(s, "base64url").toString());

app.get("/orders", async (c) => {
  const limit = Math.min(Number(c.req.query("limit") ?? 20), 100);
  const cursor = c.req.query("cursor");
  const rows = await repo.ordersPage({
    after: cursor ? decode(cursor) : undefined,
    limit: limit + 1,
  });

  const items = rows.slice(0, limit);
  const last = items.at(-1);
  const next = new URL(c.req.url);
  if (last) next.searchParams.set("cursor", encode({ c: last.createdAt, id: last.id }));

  return c.json({
    self: c.req.url,
    next: rows.length > limit ? next.toString() : undefined,
    items: items.map(toApi),
  });
});
```

## About that total count…

"Showing 1–20 of **1,284,302**" looks nice, but on large tables, `COUNT(*)` with filters can cost more than fetching the page itself (in PostgreSQL, a count often means scanning everything that matches). Ask: does the client _really_ need the exact number? Usually "there are more" (a `next` link) is enough. If needed, make it opt-in or approximate.

<DoDont>
<Do>

```http
GET /orders?limit=20
→ { "items": [...], "next": "..." }
```

Paginated from day one, with a server-enforced max limit.

</Do>
<Dont>

```http
GET /orders
→ [ ...all 2,000,000 orders... ]
```

Fine in the demo, an outage in production.

</Dont>

<Story kind="real-world" title="Slack's switch to cursors">

Slack's Web API originally used several pagination styles across methods, including page-number and offset-based ones. As workspaces grew to hundreds of thousands of channels and users, those got slow and unreliable. In 2017, Slack's engineering blog explained their move to **cursor-based pagination** across the API, with a uniform `next_cursor` in `response_metadata`. The post (_"Evolving API Pagination at Slack"_) is a great read on the trade-offs.

</Story>

<Story kind="fun-fact" title="Keyset pagination has a fan club">

Database expert Markus Winand runs a site called _Use The Index, Luke_ and even made a "No Offset" campaign logo, arguing that `OFFSET` should be avoided for pagination. What APIs call "cursor pagination" is usually what database folks call **keyset pagination** or the "seek method".

</Story>

<Quiz
  question="A client syncs all orders using <code>?offset=N&amp;limit=100</code> while new orders keep arriving at the top. What can go wrong?"
  options={[
    "Nothing, offsets are stable",
    "Some orders appear twice (and deletes can cause skipped orders)",
    "The client gets a 409 Conflict",
    "The response will be cached incorrectly",
  ]}
  answer={1}
>

New items shift everything down, so the next page starts with items already seen; deletions shift things up, so items get skipped. Cursor pagination anchors on the last item seen and avoids both.

</Quiz>

<Takeaways>

- **Paginate from day one**, with a server-enforced max page size.
- Prefer **cursor (keyset)** pagination: fast at any depth, stable under writes.
- Return a page object with **links** (`next`, `prev`, `self`); keep cursors opaque.
- Avoid exact total counts unless they're truly needed.

</Takeaways>
