<Hook>

Every developer eventually loses a day to a time zone bug, a rounding error in a price, or an ID that changes when JavaScript touches it. The fix is never clever code. It's **using the boring, standard formats** that thousands of people have already debugged for you.

</Hook>

## Dates and times: RFC 3339

Use **RFC 3339** (a strict, simple profile of ISO 8601) for timestamps. Always include the offset, and prefer UTC (`Z`).

<DoDont>
<Do>

```json
{
  "created_at": "2026-03-14T09:26:53Z",
  "delivery_date": "2026-03-20",
  "opens_at": "09:00:00"
}
```

Timestamp with zone, plain date, and time, each with the right format.

</Do>
<Dont>

```json
{
  "created_at": "14/03/2026 10:26",
  "updated": 1773480413,
  "deliveryDate": "2026-03-20T00:00:00"
}
```

Locale format, unlabelled epoch, and a "date" pretending to be a midnight timestamp with no zone.

</Dont>
</DoDont>

A few habits help:

- **Name timestamps with `_at`**: `created_at`, `modified_at`, `shipped_at`. Dates without time: `_date` (`birth_date`).
- **Use the right type**: a birthday is a `date`, not a `date-time` at midnight UTC (which becomes the day before in New York!).
- **Durations** in ISO 8601: `"PT1H30M"` (1 hour 30 min), `"P14D"` (14 days). **Intervals**: `"2026-03-01T00:00:00Z/2026-04-01T00:00:00Z"`, or separate `start`/`end` fields.

## Countries, languages, currencies: ISO codes

| What     | Standard           | Example                       |
| -------- | ------------------ | ----------------------------- |
| Country  | ISO 3166-1 alpha-2 | `"DE"`, `"ES"`, `"US"`        |
| Language | ISO 639-1 / BCP 47 | `"de"`, `"en-GB"`, `"es-419"` |
| Currency | ISO 4217           | `"EUR"`, `"USD"`, `"JPY"`     |

Never invent your own (`"Germany"`, `"german"`, `"€"`).

## Money: never use floats

```python
>>> 0.1 + 0.2
0.30000000000000004
```

Binary floating-point cannot represent most decimal fractions exactly. Fine for physics, unacceptable for invoices. Two good options:

<DoDont>
<Do title="Decimal amount + currency">

```json
{ "price": { "amount": "19.99", "currency": "EUR" } }
```

Decimal (as a string or a JSON number parsed as decimal) **plus** the currency, always together.

</Do>
<Do title="Integer minor units + currency">

```json
{ "price": { "amount": 1999, "currency": "EUR" } }
```

The Stripe way: amounts in cents. Careful: not every currency has 2 decimals (`JPY` has 0, `KWD` has 3).

</Do>
</DoDont>

The non-negotiable part: **an amount without a currency is not money**. Never send `"price": 19.99` alone.

## Numbers: say how big

JSON has one number type. Your OpenAPI spec should say what it really is with `format`: `int32`, `int64`, `float`, `double`, or `decimal`.

And watch out for **big integers**: JavaScript numbers are 64-bit floats, so integers above 2⁵³ (about 9 quadrillion) silently lose precision.

```js
JSON.parse('{"id": 1234567890123456789}').id;
// → 1234567890123456800   😱 not the same id!
```

If your IDs might exceed 2⁵³, send them as **strings**.

## Identifiers: strings, and UUIDs only when needed

Make IDs **strings** in the API, even if they're integers in your database: it lets you change the implementation later and avoids the problem above. As for UUIDs: they're great when you need IDs generated in many places without coordination, but they're long and unfriendly in URLs and logs. Consider readable, prefixed IDs (`ord_8xK2`, `cus_7Hq2`), and if you use UUIDs, prefer **UUIDv7** (time-ordered, much kinder to database indexes).

## Binary data

Rarely, binary data has to go inside JSON (a small thumbnail, a signature). Encode it with base64. OpenAPI's `format: byte` means standard base64; Zalando asks for the URL-safe variant, **base64url**, which avoids `+` and `/`. For files, use a proper media type or a separate download URL instead.

## In code

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
from datetime import date, datetime, timedelta
from decimal import Decimal
from pydantic import AwareDatetime, BaseModel, Field, PlainSerializer
from typing import Annotated

# Serialize Decimal as a string so no client parses it as a float
DecimalStr = Annotated[Decimal, PlainSerializer(str, return_type=str)]

class Money(BaseModel):
    amount: DecimalStr
    currency: Annotated[str, Field(pattern=r"^[A-Z]{3}$")]

class Order(BaseModel):
    id: str                       # string, even if it's a bigint internally
    total: Money
    created_at: AwareDatetime     # rejects naive datetimes without a zone!
    delivery_date: date           # "2026-03-20"
    return_window: timedelta      # serialized as ISO 8601 duration "P14D"
```

</TabItem>

```python
# settings.py
USE_TZ = True  # store aware datetimes in UTC
REST_FRAMEWORK = {
    "COERCE_DECIMAL_TO_STRING": True,   # default: Decimals become "19.99"
    "DATETIME_FORMAT": "iso-8601",
}

class MoneySerializer(serializers.Serializer):
    amount = serializers.DecimalField(max_digits=12, decimal_places=2)
    currency = serializers.RegexField(r"^[A-Z]{3}$")

class OrderSerializer(serializers.ModelSerializer):
    id = serializers.CharField(read_only=True)  # bigint PK → string
    total = MoneySerializer(source="*")

    class Meta:
        model = Order
        fields = ["id", "total", "created_at", "delivery_date"]
```

## Content negotiation

If a resource can be represented in several formats (JSON, CSV, PDF), let the client choose with the `Accept` header instead of inventing `/orders.csv` or `?format=csv`:

```http
GET /reports/2026-q1
Accept: text/csv
```

Unsupported? Answer `406 Not Acceptable`.

<Story kind="war-story" title="Twitter's id_str">

In 2010, Twitter switched to **Snowflake** IDs: 64-bit integers generated across many machines. Soon, tweet IDs exceeded 2⁵³, and every JavaScript client started reading _wrong IDs_, silently, because `JSON.parse` rounded them. Twitter's fix was to add a second field, `id_str`, with the same ID as a string. For over a decade, every tweet in the API carried its ID twice.

</Story>

<Story kind="history" title="The Unix epoch ends in 2038">

Many systems store time as seconds since 1 January 1970 in a signed 32-bit integer. That counter overflows on **19 January 2038 at 03:14:07 UTC**, wrapping around to 1901. This is the "Y2K38" problem. RFC 3339 strings don't have it, and they're readable in logs, too.

</Story>

<Takeaways>

- Timestamps: **RFC 3339 with zone**, preferably UTC; name them `*_at`.
- Use ISO codes for countries, languages and currencies.
- **Money = decimal amount + currency.** Never floats, never alone.
- IDs are strings; big integers break JavaScript.
- Let `Accept` choose formats; use UUIDs (v7) only when you need them.

</Takeaways>
