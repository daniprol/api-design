<Hook>

JSON is the lingua franca of web APIs. It's simple enough that everyone uses it, and loose enough that everyone uses it _differently_. A handful of conventions turn "some JSON" into payloads that are predictable, evolvable and pleasant to work with.

</Hook>

## 1. Pick a property case, and never mix

The two big camps: `snake_case` (Zalando, Stripe, GitHub, Twitter/X) and `camelCase` (Google, Microsoft, many JS shops). Both are fine. **Mixing is not.**

<DoDont>
<Do>

```json
{
  "customer_id": "cus_7",
  "created_at": "2026-03-14T09:26:53Z",
  "shipping_address": { "zip_code": "10115" }
}
```

</Do>
<Dont>

```json
{
  "customerId": "cus_7",
  "created_at": "2026-03-14T09:26:53Z",
  "ShippingAddress": { "ZIP": "10115" }
}
```

</Dont>
</DoDont>

## 2. Always return an object at the top level

<DoDont>
<Do>

```json
{
  "items": [{ "id": "1" }, { "id": "2" }],
  "next": "https://api.example.com/orders?cursor=abc"
}
```

You can add `next`, `total`, `warnings`… later without breaking anyone.

</Do>
<Dont>

```json
[{ "id": "1" }, { "id": "2" }]
```

A bare array can never grow new metadata. Adding pagination later = breaking change.

</Dont>
</DoDont>

## 3. Plural names for arrays

If it's a list, the name says so: `items`, `tags`, `line_items`, `addresses`. Singular names (`item`, `address`) are for single values.

## 4. Enums: UPPER_SNAKE_CASE strings

Enum values are strings, not magic numbers, and written in a way that stands out from free text.

```json
{ "status": "PARTIALLY_SHIPPED", "payment_method": "CREDIT_CARD" }
```

(Tip: in [Backward compatibility](/course/evolution/compatibility/) you'll learn why clients must be ready for enum values they don't know yet.)

## 5. Maps are objects with dynamic keys

When keys are data (language codes, SKU ids…), use an object as a map, and document it with `additionalProperties`:

```json
{
  "translations": {
    "en": "Shoe",
    "de": "Schuh",
    "es": "Zapato"
  }
}
```

```yaml
translations:
  type: object
  additionalProperties:
    type: string
```

## 6. One schema for reading and writing

Avoid separate `OrderCreate`, `OrderUpdate`, `OrderResponse` shapes that drift apart. Prefer **one resource schema**, marking server-generated fields as `readOnly` (`id`, `created_at`) and secrets as `writeOnly` (`password`).

It's a trade-off, not a law: with one schema, code generators and validators must honour `readOnly`/`writeOnly`, otherwise clients are asked to send an `id` on create. Many teams (and frameworks) pragmatically keep a separate _input_ model for `POST`, as long as both describe the same resource with the same field names.

<TabItem label="FastAPI" icon="seti:python">

```python
from pydantic import BaseModel, Field

# Python attributes are already snake_case, so the JSON is too.
# (A camelCase API would add: model_config = ConfigDict(alias_generator=to_camel))
class Order(BaseModel):
    id: str = Field(json_schema_extra={"readOnly": True})
    status: Literal["PLACED", "PAID", "SHIPPED", "PARTIALLY_SHIPPED"]
    line_items: list[LineItem]
    created_at: datetime = Field(json_schema_extra={"readOnly": True})

class OrderList(BaseModel):  # top-level object, never a bare list
    items: list[Order]
    next: str | None = None
```

## 7. Payload format: JSON (with standard media types)

Use `application/json` (or a more specific type like `application/problem+json` for errors, `application/merge-patch+json` for patches). For non-JSON data, use the proper standard format: `image/png`, `application/pdf`, `text/csv`. Don't base64 a PDF into JSON unless you have to.

<Story kind="history" title="JSON was discovered, not invented">

Douglas Crockford likes to say he **discovered** JSON rather than invented it: it's just the object literal syntax JavaScript already had. Around 2001 he and his colleagues started sending these literals between browser and server. He registered json.org in 2002, put the grammar on a single page (with those famous railroad diagrams), and JSON slowly ate XML's lunch. The spec is so small that it famously fits on a business card.

</Story>

<Story kind="fun-fact" title="No comments in JSON, on purpose">

Crockford removed comments from JSON deliberately: he saw people using them to hold parsing directives, which would have destroyed interoperability. That's why your `package.json` can't have comments, and why formats like JSONC and JSON5 exist.

</Story>

Clients parse the response as an array. Changing it to `{"items": [...], "next": ...}` breaks all of them. Starting with an object costs nothing and leaves room to grow.

<Takeaways>

- One property case (Zalando: `snake_case`), applied everywhere.
- Top-level responses are **objects**, never bare arrays.
- Plural array names; enum values as `UPPER_SNAKE_CASE` strings.
- One schema for read and write, with `readOnly`/`writeOnly`.

</Takeaways>
