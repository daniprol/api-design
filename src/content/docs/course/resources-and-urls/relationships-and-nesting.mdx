<Hook>

Orders have line items. Customers have addresses. Teams have members. Every API has to decide: is it `/orders/42/items/3` or `/order-items/3`? Get it right and URLs tell a story. Get it wrong and you end up with `/companies/1/departments/4/teams/9/members/17/roles/2`, a URL that needs a map.

</Hook>

## Sub-resources: "belongs to" relationships

When a resource **only exists in the context of a parent**, nest it. A line item without its order makes no sense, and nesting makes ownership obvious:

```http
GET    /orders/42/items          # all items of order 42
POST   /orders/42/items          # add an item to order 42
GET    /orders/42/items/3        # item 3 of order 42
DELETE /orders/42/items/3
```

## Top-level resources: "references" relationships

When a resource has an **identity of its own**, keep it top-level, even if it's related to something else. A customer exists independently of any particular order:

<DoDont>
<Do>

```http
GET /customers/7
GET /orders?customer_id=7
```

Customers are top-level; filter orders by customer.

</Do>
<Dont>

```http
GET /orders/42/customer
GET /stores/3/orders/42/customer/addresses
```

Now the customer has as many URLs as it has orders.

</Dont>
</DoDont>

**The test:** _Can this thing exist, or be looked up, without the parent?_ If yes, it probably deserves a top-level URL. You can still offer a nested _view_ (`/customers/7/orders`) as a convenience, as long as the canonical identity is clear.

## How deep is too deep?

Each level of nesting adds an ID that the client must know. Deep paths are hard to construct and easy to get wrong. A practical limit: **no more than 3 levels** of sub-resources.

```text
/orders/42/items/3                  ✅ 2 levels: clear
/orders/42/items/3/discounts/1      🤔 3 levels: OK, borderline
/shops/1/orders/42/items/3/discounts/1/audits   😵 too deep
```

If you're hitting the limit, ask whether a deeper resource has its own identity (it probably does) and promote it to the top level.

## Compound keys

Sometimes a resource is naturally identified by _two_ things, e.g. a product's stock _in a specific warehouse_. You can nest it, or expose a **compound key** as a single, opaque-looking ID:

```http
GET /warehouses/BER-1/stocks/sku-123   # nested
GET /stocks/BER-1:sku-123              # compound key as one id
```

:::caution[Always scope by the parent]
A classic security bug: `GET /orders/42/items/3` returns item 3 even though it belongs to order 99, which belongs to someone else. When you nest, **filter by the parent ID** (and by the caller's permissions). This bug class is called IDOR (Insecure Direct Object Reference), and it's [#1 on the OWASP API Security Top 10](https://owasp.org/API-Security/) as "Broken Object Level Authorization".
:::

## Keep the number of resource types small

An API with 40 resource types is really several APIs in a trench coat. If an API grows past roughly **4 to 8 resource types**, consider whether it should be split by subdomain.

<Story kind="war-story" title="The 2018 USPS API leak">

In 2018, security researcher Brian Krebs reported that a U.S. Postal Service API let any logged-in user query account details of _other_ users, about 60 million of them, just by changing parameters. The API checked that you were logged in, not that the data was _yours_. Object-level authorization is unglamorous and absolutely essential.

</Story>

<Takeaways>

- Nest resources that **only exist inside a parent** (order items).
- Keep resources with their **own identity** top-level, and relate them via filters.
- Max ~3 nesting levels; promote deeper things to top-level.
- When nesting, **always scope queries by the parent** and the caller's permissions.

</Takeaways>
