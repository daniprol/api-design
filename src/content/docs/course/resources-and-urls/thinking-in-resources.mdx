<Hook>

Most of us learned programming by writing functions: `cancelOrder()`, `sendInvoice()`, `approveRefund()`. REST asks you to flip that around and ask: **what _thing_ gets created, read, changed or removed?** Once this clicks, you stop inventing endpoints and start _discovering_ them.

</Hook>

## Nouns, not verbs

In a resource-oriented API, the URL names a **thing** and the HTTP method names the **action**.

<DoDont>
<Do>

```http
GET    /customers/123
POST   /orders
DELETE /carts/abc/items/7
```

</Do>
<Dont>

```http
GET  /getCustomer?id=123
POST /createOrder
POST /removeItemFromCart
```

</Dont>
</DoDont>

The verb-in-URL version looks harmless, but it scales badly. With 20 kinds of things and 5 actions each, you get 100 snowflake endpoints, each with its own naming quirks. With resources, you get 20 nouns and the same 5 methods everyone already knows.

## "But my operation is an action!"

This is where it gets interesting. Real businesses are full of actions: cancel, approve, publish, ship, refund. The trick is to ask: **what is the thing that this action creates or changes?** There are three classic moves.

### Move 1: the action changes a field → update the resource

```http
PATCH /articles/42
Content-Type: application/merge-patch+json

{ "status": "PUBLISHED" }
```

### Move 2: the action creates a record → create a new resource

A cancellation, a refund, a shipment, an approval: these are _things_ with their own data (who, when, why). Make them resources.

```http
POST /orders/42/cancellations
{ "reason": "CUSTOMER_REQUEST" }

→ 201 Created
Location: /orders/42/cancellations/1
```

### Move 3: the action is a calculation → model the result

Searches, quotes and previews are "things" too: a _search result_, a _price quote_.

```http
POST /shipping-quotes
{ "from": "DE", "to": "ES", "weight_grams": 1200 }

→ 201 Created
{ "id": "q_77", "price": { "amount": "7.90", "currency": "EUR" }, "valid_until": "..." }
```

## In code: cancellation as a resource

<Tabs syncKey="stack">
<TabItem label="FastAPI" icon="seti:python">

```python
from fastapi import Response, status

class CancellationIn(BaseModel):
    reason: Literal["CUSTOMER_REQUEST", "OUT_OF_STOCK", "FRAUD"]

@app.post("/orders/{order_id}/cancellations", status_code=status.HTTP_201_CREATED)
def cancel_order(order_id: str, body: CancellationIn, response: Response) -> Cancellation:
    cancellation = orders.cancel(order_id, reason=body.reason)
    response.headers["Location"] = f"/orders/{order_id}/cancellations/{cancellation.id}"
    return cancellation
```

## Use the language of the business

Resource names should come from the **domain**, not from generic computer-speak. Talk to the people who run the business and use their words.

| Generic (meh)       | Domain-specific (yes!)                  |
| ------------------- | --------------------------------------- |
| `/items`            | `/products`, `/articles`, `/sku-stocks` |
| `/data`             | `/shipments`                            |
| `/entries`          | `/ledger-entries`                       |
| `/objects/42/state` | `/orders/42/cancellations`              |

And model **useful** resources: things consumers actually need, covering the **complete business process**. A `/payments` resource that can be created but never refunded, queried or reconciled is half a product.

## When a verb is OK

Sometimes no honest noun exists, for example `POST /emails/42/send` or `POST /calculator/evaluate`. Many respected APIs (Google's _custom methods_, like `POST /v1/books/42:archive`) explicitly allow this as an escape hatch. Use it sparingly, and only after trying the three moves above.

<Story kind="real-world" title="GitHub stars as a resource">

How do you "star" a repository? GitHub's REST API doesn't have a `/star` action. Instead, the star is a resource: `PUT /user/starred/{owner}/{repo}` stars it, `DELETE` un-stars it, and `GET` returns `204` if starred or `404` if not. Idempotent, cacheable, and no new verbs required.

</Story>

<Quiz
  question="You need an endpoint to approve an expense report. Which design is the most resource-oriented?"
  options={[
    "<code>POST /approveExpenseReport?id=9</code>",
    "<code>GET /expense-reports/9/approve</code>",
    "<code>POST /expense-reports/9/approvals</code>",
    "<code>PUT /expense-reports/approve/9</code>",
  ]}
  answer={2}
>

An approval is a _thing_ (who approved, when, with what comment). Creating it with `POST` is clean, and you get a natural place to list approval history later. And never use `GET` for something that changes state: crawlers and link previewers will happily "approve" things for you.

</Quiz>

<Takeaways>

- URLs name **things**; HTTP methods name **actions**.
- Turn actions into: field updates (`PATCH`), new resources (`POST`), or calculated results.
- Use domain words that the business uses.
- Verbs in URLs are a last-resort escape hatch, not a default.

</Takeaways>
