<InBrief>

- Collections are plural and kebab-case: `/sales-orders/ord_42/line-items`. Query parameters use the JSON casing.
- Pick one form, with or without a trailing slash, and redirect or reject the other. Put the API on its own host instead of an `/api` prefix.
- Use opaque, prefixed identifiers that need no escaping: `ord_8xK2`, `cus_7Hq2`, `sku-123`.
- Nest only resources that can't exist without their parent, at most two or three levels. Keep everything with its own identity top-level.
- Always scope nested lookups by the parent and the caller.

</InBrief>

Larkspur's integration has a 404 problem. Their developer, long gone, guessed `/order_items` because the neighbouring endpoint was `/userProfiles`, and Fernhill had shipped `/order-items`. None of the conventions on this page is deep. Their value is that consumers can guess a URL they've never seen, and a reviewer can spot an odd one at a glance. An API that mixes `/userProfiles`, `/order_items` and `/Shipment/` makes every endpoint a separate thing to learn.

## Anatomy, and one convention per part

Each part of a URL deserves exactly one convention. Here are the parts, labelled:

```text
https://order-management.api.example.com/sales-orders/ord_42/line-items?sort=-created_at&limit=20
        └──────────── host ─────────────┘└─ collection ┘└ id ┘└ sub-coll. ┘└──── query ─────────────┘
```

| Part            | Convention                                                             | Example                            |
| --------------- | ---------------------------------------------------------------------- | ---------------------------------- |
| Host            | functional name, kebab-case                                            | `order-management.api.example.com` |
| Path segment    | plural noun, kebab-case                                                | `/sales-orders/ord_42/line-items`  |
| Identifier      | opaque, prefixed, URL-safe                                             | `ord_8xK2`, `sku-ab-123`           |
| Query parameter | same casing as JSON fields                                             | `?created_after=…&limit=20`        |
| JSON property   | one casing everywhere (see [JSON conventions](/representations/json/)) | `"created_at"`                     |
| Header          | Hyphenated-Pascal-Case                                                 | `Idempotency-Key`                  |

Paths are case-sensitive after the host, so lowercase kebab-case is the safe choice: nobody has to remember whether it was `lineItems` or `LineItems`.

## Make trailing slashes and prefixes boring

`/orders` and `/orders/` look identical to a human and are different URLs to HTTP, to caches and to your routing table. Allow both and you get two cache keys for one resource. Pick one, then redirect or reject the other. For APIs the common choice is no trailing slash. Frameworks default differently, so set it explicitly.

_Assumes:_ FastAPI 0.110+, DRF 3.15 routers, Hono 4.

The comments say which default you're overriding.


The same thinking applies to the start of the path: leave `/api` out. Everything on an API host is an API, and a path prefix tends to collect deployment details (`/api/v2/internal/…`) until they become contract. A dedicated host also lets you route, rate-limit and cache API traffic separately from the website. RFC 8820 makes a related point for standards authors: the path belongs to the API owner, so don't build designs that require fixed paths on other people's hosts.

## Use opaque, prefixed identifiers

When Priya greps a log at 3 a.m., the line says `1842`. Is that an order, a customer or a line item? Identifiers turn up in URLs, logs, support tickets and other people's databases, so they have to work in all of them. Good ones need no escaping (roughly `[A-Za-z0-9._~-]`, plus `:` if you use compound keys), say what they are, and reveal nothing.

<Compare>
<Prefer>

```http
/customers/cus_7Hq2
/orders/ord_8xK2
/products/sku-ab-123
```

A type prefix makes a misplaced ID obvious in a log line and lets the server reject `cus_` where `ord_` was expected with a precise error.

</Prefer>
<Avoid>

```http
/customers/jane%40example.com
/products/Blue%20T-Shirt%20(L)
/orders/1842
```

Emails and names change and need escaping. Sequential integers reveal volume and invite enumeration.

</Avoid>
</Compare>

Sequential IDs are not a vulnerability by themselves, because authorisation should stop enumeration. In practice, they turn one missing authorisation check into a full data export, and they tell competitors how many orders you take per day.

## Nest only what can't exist without its parent

Nesting is tempting because it reads like a sentence. Sometimes the sentence is true. Line items belong to exactly one order and mean nothing without it, so nesting makes that ownership visible:

```http
GET    /orders/ord_42/line-items
POST   /orders/ord_42/line-items
DELETE /orders/ord_42/line-items/li_3
```

A customer, though, exists independently of any order. Nest it and one customer has as many URLs as orders, and the mobile app needs an order ID before it can show a profile.

<Compare>
<Prefer>

```http
GET /customers/cus_7
GET /orders?customer_id=cus_7
GET /customers/cus_7/orders     (a convenience view)
```

</Prefer>
<Avoid>

```http
GET /orders/ord_42/customer
GET /stores/sto_3/orders/ord_42/customer/addresses
```

</Avoid>
</Compare>

The test is whether the thing can be looked up without its parent. If it has a globally unique ID, give it a top-level URL and relate it through filters. Stop at two or three levels; anything deeper usually has its own identity and should be promoted.

For resources that really are identified by two keys, such as stock of a product in a warehouse, both shapes work: `/warehouses/ber-1/stocks/sku-123` or a compound ID like `/stocks/ber-1:sku-123`.

## Scope every nested lookup by its parent and the caller

Nesting has a trap. `GET /orders/ord_42/line-items/li_3` returns `li_3` even though it belongs to `ord_99`, which belongs to someone else. The handler looked up the line item by its own ID and treated the rest of the path as decoration. Broken object-level authorisation is first on the OWASP API Security Top 10. Query through the parent, and through the caller's permissions, every time. Notice that the filter comes before the lookup:

```python
item = (LineItem.objects
        .filter(order__customer=request.user.customer)  # the caller's orders
        .get(order__public_id=order_id, public_id=item_id))  # within that order
```

More on this in [Authentication and authorization](/security/auth/).

If all this seems fussy for a URL, consider the most famous URL decision of all.

<Note kind="curiosity" title="The regretted double slash" year="2009" source="https://bits.blogs.nytimes.com/2009/10/12/the-webs-inventor-regrets-one-small-thing/">

In 2009, Tim Berners-Lee admitted that the `//` after `http:` was unnecessary, and that he would drop it if he could design URLs again. By then it had been printed and typed more times than anyone can count, and it is still there. URL conventions are permanent once published, so choose yours before the first consumer bookmarks one.

</Note>

## What to take away

A good URL is guessable, boring and permanent: plural kebab-case nouns, opaque prefixed IDs, shallow nesting, and every nested lookup scoped by its parent and caller. The URL says which thing; the method says what happens to it, and choosing the wrong one has consequences for every retry and cache. That's [methods](/http/methods/).
