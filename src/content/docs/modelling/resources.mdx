<InBrief>

- URLs name things, methods name what happens to them. Keep verbs out of paths.
- Turn an action into a field update, a new sub-resource that records the event, or a computed resource.
- Prefer a sub-resource such as `/cancellation` over a status `PATCH` when the action has its own data, rules or side effects.
- Take names from the business's vocabulary, and model the whole process, including reversal and reconciliation.

</InBrief>

A Fernhill customer's order says "cancelled", nobody knows who cancelled it or why, and the refund never went out. Priya traces it to `POST /cancelOrder`, which flipped a flag and recorded nothing. We learned to program writing functions, so endpoints like that feel natural. A resource-oriented API asks a different question: what thing is created, read, changed or removed? Asked consistently, it stops you inventing endpoints and starts you discovering them.

## Name things in the URL and let the method say what happens

Twenty nouns with the same five methods are learnable; a hundred bespoke verbs aren't.

<Compare>
<Prefer>

```http
GET    /customers/cus_7
POST   /orders
DELETE /carts/crt_3/items/sku-123
```

</Prefer>
<Avoid>

```http
GET  /getCustomer?id=cus_7
POST /createOrder
POST /removeItemFromCart
```

</Avoid>
</Compare>

The verb-in-URL style looks harmless at five endpoints. At fifty, every endpoint has its own naming quirks and its own idea of which method to use, and nothing has shared semantics a cache or retry policy can rely on. Is `POST /removeItemFromCart` safe to retry? Only its author knows.

## Turn actions into one of three resource shapes

So what do you do with the verbs? Businesses are full of them: cancel, approve, publish, ship, refund. Each turns out to be one of three shapes.

**A field changes.** If "publishing" an article only moves a field to a new value and carries no data of its own, it isn't really an action. Update the resource:

```http
PATCH /articles/art_42
Content-Type: application/merge-patch+json

{ "visibility": "public" }
```

**A record is created.** Cancellations, refunds, shipments and approvals have their own data (who, when, why), their own validation rules and often their own lifecycle. That is the record Priya's support call was missing. Make them resources, and notice the `Location` header pointing at the new one:

```http
POST /orders/ord_42/cancellation
{ "reason": "customer_request" }

HTTP/1.1 201 Created
Location: https://api.example.com/orders/ord_42/cancellation
```

**A result is computed.** Quotes, previews and validations are things too. When Larkspur asks what a parcel to Spain will cost, the answer has an ID, a price and an expiry:

```http
POST /shipping-quotes
{ "from": "DE", "to": "ES", "weight_grams": 1200 }

HTTP/1.1 201 Created
{ "id": "quo_77", "price": { "amount": "7.90", "currency": "EUR" }, "expires_at": "2026-11-14T10:15:00Z" }
```

## Prefer a sub-resource over a status PATCH for real state transitions

`PATCH /orders/ord_42 {"status": "cancelled"}` is tempting because it's one endpoint. It breaks down the moment the transition has rules. Which status values may a client set, and from which states? Where does the reason go? How does the client learn that cancelling triggered a refund? A writable status field turns your state machine into an input validation problem.

A sub-resource keeps the transition explicit. `POST /orders/ord_42/cancellation` can require a reason, return <Status code={409} /> with a precise problem type when the order has shipped, and later be read back to show who cancelled and when. Keep `status` read-only and let transitions happen through resources that describe them.

_Assumes:_ FastAPI with Pydantic v2, DRF 3.15, Hono 4 with Zod. `orders.cancel()` raises `OrderNotCancellable` for shipped orders.

Here is the endpoint. Watch the 409: the client gets a problem type it can act on, not a generic validation error.

<Tabs syncKey="stack">
<TabItem label="FastAPI">

```python
class CancellationIn(BaseModel):
    reason: Literal["customer_request", "out_of_stock", "fraud"]

@app.post("/orders/{order_id}/cancellation", status_code=201)
def cancel_order(order_id: str, body: CancellationIn, response: Response) -> Cancellation:
    try:
        cancellation = orders.cancel(order_id, reason=body.reason)
    except OrderNotCancellable as e:
        raise problem(409, "order-not-cancellable", detail=str(e))
    response.headers["Location"] = f"{BASE_URL}/orders/{order_id}/cancellation"
    return cancellation
```

</TabItem>
<TabItem label="Django">

```python
class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Order.objects.all()
    serializer_class = OrderSerializer

    @action(detail=True, methods=["post", "get"], url_path="cancellation")
    def cancellation(self, request, pk=None):
        order = self.get_object()
        if request.method == "GET":
            return Response(CancellationSerializer(get_object_or_404(Cancellation, order=order)).data)
        serializer = CancellationSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        cancellation = cancel(order, reason=serializer.validated_data["reason"], by=request.user)
        return Response(CancellationSerializer(cancellation).data, status=201)
```

</TabItem>
<TabItem label="Hono">

```ts
const CancellationIn = z.object({ reason: z.enum(["customer_request", "out_of_stock", "fraud"]) });

app.post("/orders/:id/cancellation", zValidator("json", CancellationIn), async (c) => {
  const id = c.req.param("id");
  const result = await orders.cancel(id, c.req.valid("json").reason);
  if (!result.ok) return problem(c, 409, "order-not-cancellable", result.detail);
  c.header("Location", `${BASE_URL}/orders/${id}/cancellation`);
  return c.json(result.cancellation, 201);
});
```

</TabItem>
</Tabs>

The singular `cancellation` is deliberate: an order is cancelled at most once. A repeatable action, such as partial refunds, gets a plural collection: `POST /orders/ord_42/refunds`.

Even a toggle benefits, as GitHub's stars show.

<Note kind="practice" title="GitHub stars" source="https://docs.github.com/en/rest/activity/starring">

GitHub needed a star button and resisted adding a "star" verb. Instead, `PUT /user/starred/{owner}/{repo}` stars a repository, `DELETE` removes the star, and `GET` returns <Status code={204} /> if starred or <Status code={404} /> if not. Because the star is a resource, idempotency came for free: double-clicking the button can't double-star.

</Note>

## Accept a custom method when no honest noun exists

Push this too far and you get `/emails/eml_1/sendings`, which helps nobody. Some operations genuinely resist nouns: `send` on an email draft, `translate` on a text, `reboot` on a machine. Guidelines split on this, as the table below shows. Whatever your rule, apply it consistently, use `POST`, and document the operation's idempotency.

## Use the business's words, and model the whole process

Resource names should come from the people who run the domain. `/shipments` beats `/data`, `/ledger-entries` beats `/entries`, and `/orders/ord_42/cancellation` beats `/objects/42/state`. When engineers and the business use the same nouns, a support ticket and a spec read the same way.

The happy path is the easy half. A `/payments` resource that can be created but never refunded, listed or reconciled sends consumers to back channels, and Larkspur will end up emailing a spreadsheet to your finance team every month. Before publishing, walk each resource through its full lifecycle and check that every transition a consumer needs is in the API.

Keep each API small enough to hold in your head. Guidelines suggest somewhere around four to eight resource types; past that, look for a domain boundary to split along.

<WorkedProblem kind="Design" title="Expense approvals">

Managers approve or reject expense reports, with an optional comment. A report can be approved by up to two managers, and finance needs an audit trail. Design the endpoints.

<Solution>

```http
POST /expense-reports/exp_9/approvals      { "decision": "approved", "comment": "…" }  → 201
GET  /expense-reports/exp_9/approvals                                                → 200, the audit trail
GET  /expense-reports/exp_9                                                          → "status": "pending_second_approval"
```

Approvals are records with an author, a time and a comment, and there can be several, so they form a plural sub-collection. The report's `status` is derived and read-only. A third approval attempt returns 409 with a problem type such as `approval-limit-reached`.

**Alternatives.** `POST /expense-reports/exp_9:approve` (custom method) is fine under Google's guidelines, but you'd still need somewhere to read the audit trail, which the sub-collection gives you for free.

</Solution>
</WorkedProblem>

## What to take away

When you catch yourself writing a verb, ask what record that action leaves behind; usually it's a field change, a new sub-resource or a computed result, and the record is what support will need later. Once you have the nouns, you have to spell them in URLs that stay stable for years. That's [URL design](/modelling/urls/).
