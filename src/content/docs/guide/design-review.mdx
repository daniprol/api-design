<InBrief>

- Twenty findings on a 60-line spec, which is typical for a first draft, and none of them exotic.
- Read the draft first and make your own list; then compare.
- Findings are ordered by the cost of fixing them later: what breaks clients after release comes first.

</InBrief>

The draft below was written in an afternoon by a capable team under deadline, and it would work. Most first drafts would. The point of a design review is the next five years: which of these choices will be expensive once three partners have integrated, and which are cheap to fix today. Nothing here requires new technology. Every fix is a convention described elsewhere in the Guide.

## The draft

```yaml title="orders-api.yaml (draft)"
openapi: 3.1.0
info: { title: orders, version: latest }
paths:
  /api/v1/getOrders:
    get:
      parameters:
        - { name: page, in: query, schema: { type: integer } }
        - { name: customerEmail, in: query, schema: { type: string } }
      responses:
        "200":
          content:
            application/json:
              schema: { type: array, items: { $ref: "#/components/schemas/Order" } }
  /api/v1/orders/create:
    post:
      requestBody:
        content:
          application/json:
            schema: { $ref: "#/components/schemas/Order" }
      responses:
        "200": { description: Order created }
  /api/v1/orders/{id}:
    get:
      responses:
        "200": { content: { application/json: { schema: { $ref: "#/components/schemas/Order" } } } }
    put:
      requestBody:
        { content: { application/json: { schema: { $ref: "#/components/schemas/OrderUpdate" } } } }
      responses:
        "200": { description: Updated }
  /api/v1/orders/{id}/cancel:
    get:
      responses:
        "200":
          content:
            application/json:
              schema:
                {
                  type: object,
                  properties: { success: { type: boolean }, error: { type: string } },
                }
components:
  schemas:
    Order:
      type: object
      properties:
        id: { type: integer }
        Status: { type: string, enum: [NEW, PAID, SHIPPED] }
        customerEmail: { type: string }
        total: { type: number }
        created: { type: string, example: "14/03/2026 10:26" }
        items: { type: array, items: { type: object } }
        isGift: { type: boolean, nullable: true }
        _internalNotes: { type: string }
    OrderUpdate:
      type: object
      properties:
        status: { type: string }
        total: { type: number }
```

## Findings that break clients if fixed later

1. **`version: latest` and no owner.** The contract has no version a consumer can pin, no owner to ask, and no audience to judge risk by. Use SemVer, `contact`, `x-api-id` and `x-audience`. [Specs in CI](/evolution/specs-in-ci/)

2. **Verbs in paths: `getOrders`, `orders/create`, `{id}/cancel`.** The method already says get and create. Use `GET /orders` and `POST /orders`. Model cancellation as a resource, `POST /orders/{order_id}/cancellation`, which can require a reason, answer `409` once the order has shipped, and be read back later. Keep `status` read-only. [Resources and actions](/modelling/resources/)

3. **`GET` that cancels.** A crawler, a link prefetcher or a retrying proxy will cancel orders. `GET` must be safe. [Methods](/http/methods/)

4. **A bare array at the top level.** It can't gain a `next` link or any metadata without a breaking change. Return `{ "items": [...], "next": "..." }`. [JSON conventions](/representations/json/)

5. **Page-number pagination with no limit.** `page` without `limit` returns whatever the server feels like; offset pages also skip and repeat items as orders arrive. Use an opaque cursor, a documented default and maximum `limit`, and a `next` link. [Pagination](/collections/pagination/)

6. **Integer IDs.** `id: integer` leaks volume (order 1842 tells competitors your sales), invites enumeration, and breaks JavaScript clients past 2<sup>53</sup>. Use opaque string IDs such as `ord_42`. [Data formats](/representations/data-formats/)

7. **`total: number`.** Floats can't represent 0.10 exactly, and a total without a currency is a guess. Use `{ "amount": "59.90", "currency": "EUR" }`. [Data formats](/representations/data-formats/)

8. **A homemade date format.** `14/03/2026 10:26` is ambiguous across locales and has no time zone. Use RFC 3339 with an offset, named `created_at`. [Data formats](/representations/data-formats/)

9. **Closed, uppercase enum.** `[NEW, PAID, SHIPPED]` will gain `cancelled` and `partially_shipped`, and clients that switch on a closed set will crash. Use lowercase snake_case values and document the enum as open-ended. [Compatibility](/evolution/compatibility/)

10. **Mixed casing: `Status`, `customerEmail`, `isGift`, `_internalNotes`.** Pick one case for every property and stick to it; this site uses snake_case. Renaming after release is a breaking change. [JSON conventions](/representations/json/)

11. **The same schema for input and output.** `POST` accepts `Order`, so clients can send `id`, `Status` and `_internalNotes`. That's a mass-assignment bug waiting to happen. Define `OrderCreate` with only the writable fields, and reject unknown ones. [Authentication and authorization](/security/auth/)

## Findings that hurt clients today

12. **`200` for creation, with no body.** Return `201 Created`, a `Location` header and the created order, so clients learn the ID without a second request. [Status codes](/http/status-codes/)

13. **No error responses at all.** Clients will receive whatever the framework emits, probably an HTML page. Declare `application/problem+json` for 4xx and 5xx, and `422` with per-field errors for validation. [Errors](/http/errors/)

14. **`success: false` inside a `200`.** Every generic client, proxy and monitoring tool will count failures as successes. Use status codes. [Status codes](/http/status-codes/)

15. **Retrying `POST /orders` creates two orders.** A timeout on a checkout is the most common time to retry. Accept an `Idempotency-Key`. [Idempotency and retries](/reliability/idempotency/)

16. **`PUT` with a partial body.** `OrderUpdate` has two fields, so `PUT` either wipes the rest or behaves as a merge, and clients can't tell which. Use `PATCH` with JSON Merge Patch for partial updates of the fields clients may change (a gift message, a delivery note), drop `status` from it (finding 2), and protect it with `If-Match`, because two support agents will edit the same order. [Methods](/http/methods/), [Concurrency control](/reliability/concurrency/)

17. **`total` is writable.** A client can update the price of its own order. Derive totals on the server.

## Findings about privacy and security

18. **Email in the query string.** `?customerEmail=` ends up in access logs, browser history and analytics. Filter by `customer_id`, or move sensitive searches into a `POST` search resource. [Filtering and sorting](/collections/filtering/)

19. **`_internalNotes` in a public response.** If a field is internal, it doesn't belong in the public representation, prefixed or not. [Principles](/foundations/principles/)

20. **No security scheme.** The spec doesn't say who may call what. Declare OAuth 2.0 scopes per operation, and check that the caller may see this specific order, not just orders in general. [Authentication and authorization](/security/auth/)

## The reviewed version

```yaml title="orders-api.yaml (after review, excerpt)"
openapi: 3.1.0
info:
  title: Order Management API
  version: 1.0.0
  contact: { name: Team Checkout, url: https://wiki.example.com/teams/checkout }
  x-api-id: 0f3c1e2d-7a0e-4b8e-9d2b-1f2a3b4c5d6e
  x-audience: external-partner
paths:
  /orders:
    get:
      security: [{ oauth2: [orders:read] }]
      parameters:
        - { name: customer_id, in: query, schema: { type: string } }
        - {
            name: limit,
            in: query,
            schema: { type: integer, minimum: 1, maximum: 100, default: 20 },
          }
        - { name: cursor, in: query, schema: { type: string } }
      responses:
        "200":
          { content: { application/json: { schema: { $ref: "#/components/schemas/OrderPage" } } } }
        default: { $ref: "#/components/responses/Problem" }
    post:
      security: [{ oauth2: [orders:write] }]
      parameters: [{ $ref: "#/components/parameters/IdempotencyKey" }]
      requestBody:
        { content: { application/json: { schema: { $ref: "#/components/schemas/OrderCreate" } } } }
      responses:
        "201":
          headers: { Location: { schema: { type: string, format: uri } } }
          content: { application/json: { schema: { $ref: "#/components/schemas/Order" } } }
        "422": { $ref: "#/components/responses/ValidationProblem" }
        default: { $ref: "#/components/responses/Problem" }
  /orders/{order_id}:
    patch:
      security: [{ oauth2: [orders:write] }]
      parameters: [{ $ref: "#/components/parameters/IfMatch" }]
      requestBody:
        {
          content:
            {
              application/merge-patch+json: { schema: { $ref: "#/components/schemas/OrderPatch" } },
            },
        }
      responses:
        "200": { content: { application/json: { schema: { $ref: "#/components/schemas/Order" } } } }
        "412": { $ref: "#/components/responses/Problem" }
        default: { $ref: "#/components/responses/Problem" }
components:
  schemas:
    Order:
      type: object
      required: [id, status, total, created_at]
      properties:
        id: { type: string, example: ord_42 }
        status:
          type: string
          description: "One of placed, paid, shipped, delivered, cancelled. New values may be added; treat unknown values as in progress."
          example: placed
        customer_id: { type: string, example: cus_7 }
        total: { $ref: "#/components/schemas/Money" }
        created_at: { type: string, format: date-time }
        is_gift: { type: boolean, default: false }
```

<Note kind="aside" title="Reviews scale through linters" source="https://github.com/zalando/zally">

About half of these findings (casing, verbs in paths, missing error responses, integer IDs, top-level arrays, missing metadata) are mechanical, and a Spectral or Zally ruleset catches them before a human looks. That leaves the review meeting for findings 2, 11, 15, 16 and 17, which need someone who understands orders. That division of labour is what linters like Zally are for.

</Note>
