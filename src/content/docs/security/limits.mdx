<InBrief>

- Bound every dimension of a request: page size, body size, array lengths, query complexity, execution time.
- Rate-limit per authenticated client (per IP only for anonymous traffic), and answer <Status code={429} /> with `Retry-After` and a problem body.
- Publish the quota on every response with the `RateLimit` and `RateLimit-Policy` headers, so clients slow down before they hit the wall.
- Use a token bucket for request rate and a separate concurrency limit for expensive endpoints.
- Protect business flows that bots love, such as sign-up, checkout and coupon redemption, with limits on the flow, not just the endpoint.

</InBrief>

At 3 a.m., Larkspur Logistics' cron job hits an error it has never seen and does what it was written in 2019 to do: retry immediately, forever. By the time Priya wakes, checkout is slow for every customer. Bugs, scrapers and successful partners end up here. Limits keep the service up for everyone else; good limit responses let well-behaved clients cooperate instead of guessing.

## Cap how much one request can cost

Rate limits cap how often; resource limits cap how much per request, and OWASP lists their absence as API4, unrestricted resource consumption. A `limit=1000000` does its damage in one call, well under any rate limit. Each of these needs an explicit, documented maximum:

| Dimension        | Limit                                           | Response when exceeded                         |
| ---------------- | ----------------------------------------------- | ---------------------------------------------- |
| Page size        | `limit` ≤ 100                                   | <Status code={422} /> (or clamp, documented)   |
| Request body     | e.g. 1 MB for JSON                              | <Status code={413} />                          |
| Arrays in a body | e.g. 100 items per batch                        | <Status code={422} />                          |
| String lengths   | per field                                       | <Status code={422} />                          |
| Query complexity | filter depth, `embed` depth, GraphQL cost       | <Status code={422} />                          |
| Execution time   | server-side timeout below the gateway's         | <Status code={503} /> or <Status code={504} /> |
| Upstream fan-out | e.g. outbound webhooks, emails, SMS per account | <Status code={429} />                          |

The last row is the expensive one. An endpoint that sends an SMS costs real money on every call, and without a per-account cap, an attacker can run their messaging campaign on your bill.

## Say no with 429, a time and a reason

A bare 429 leaves the client guessing, and clients guess badly. Give it a time to come back and a reason a human can read; the `RateLimit` headers are explained below.

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 30
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=0;t=30

{
  "type": "https://api.example.com/problems/rate-limit-exceeded",
  "title": "Too many requests",
  "status": 429,
  "detail": "This API key allows 100 requests per minute. Retry in 30 seconds."
}
```

`Retry-After` is what clients act on; [retry logic](/reliability/idempotency/) should honour it in preference to its own backoff. When the whole service is overloaded rather than one client being over quota, use <Status code={503} /> with `Retry-After` instead. A 429 during your database incident tells every client it misbehaved.

## Show the quota before clients hit it

A 429 is a wall the client finds by walking into it. Clients behave better when every response, not only the rejected ones, shows the wall coming. For years, every API invented its own `X-RateLimit-*` headers with incompatible semantics: GitHub's `X-RateLimit-Reset` is a Unix timestamp, others use seconds remaining. The IETF HTTPAPI working group's draft replaces them with two Structured Fields. `RateLimit-Policy` states the quota, and `RateLimit` states where this client stands against it:

```http
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=42;t=30
```

Read it as: the policy named `default` allows 100 requests (`q`) per 60-second window (`w`); this client has 42 left (`r`), and the quota resets in 30 seconds (`t`). The name ties the two headers together, which matters once you publish more than one policy, such as `"burst";q=10;w=1,"daily";q=5000;w=86400`. An optional `qu` parameter counts something other than requests (`"content-bytes"`, for example), and `pk` carries a partition key when the quota belongs to something other than the caller.

The draft has changed shape more than once, and libraries lag it. Many still emit the older `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` trio, or a single `RateLimit: limit=100, remaining=42, reset=30`; a client written against one of those can't parse the other. Emit the current syntax for new APIs, write it yourself if your library doesn't, and keep any legacy headers you've already published until their callers are gone.

## Pick the algorithm for what you're protecting

The algorithms differ mainly in how they treat bursts. The mobile app opening a screen fires six requests at once, then nothing for a minute, and the limiter must not mistake that for an attack.

- **Token bucket** refills at N tokens per second up to a burst size, and each request takes one. It allows short bursts and enforces an average, which suits most APIs. Stripe described running exactly this, in Redis, as their primary limiter.
- **Fixed window** counts per calendar minute. It's simple, but it allows twice the rate across a window edge.
- **Sliding window** weighs the previous window. It's smoother than fixed and cheap enough.
- **Concurrency limit** caps in-flight requests per client. It's the right tool for slow, expensive endpoints, where rate alone doesn't capture cost.

Key limits by the authenticated client (API key, OAuth client, account). IP-based limits get it wrong in both directions: they punish everyone behind a corporate NAT or a mobile carrier, and a botnet evades them trivially. Use them only for anonymous endpoints such as login.

_Assumes:_ Redis-backed limits shared across instances; `request.state.client_id` (FastAPI) or `c.get("clientId")` (Hono) set by authentication middleware that runs first; a `problem_response` helper as in [Errors](/http/errors/).

Here's the setup. Notice two things: the key falls back to the IP address only when there's no authenticated client, and the quota headers go on every response, with the 429 carrying `Retry-After` as well.

```python
import time
from limits import parse, storage, strategies

DEFAULT = parse("100/minute")
limiter = strategies.FixedWindowRateLimiter(storage.RedisStorage("redis://redis:6379"))

def ratelimit_headers(policy: str, quota: int, window: int, remaining: int, reset: int) -> dict:
    return {"RateLimit-Policy": f'"{policy}";q={quota};w={window}',
            "RateLimit": f'"{policy}";r={remaining};t={reset}'}

@app.middleware("http")
async def rate_limit(request: Request, call_next):
    key = getattr(request.state, "client_id", None) or request.client.host
    allowed = limiter.hit(DEFAULT, key)
    stats = limiter.get_window_stats(DEFAULT, key)
    reset = max(int(stats.reset_time - time.time()), 0)
    headers = ratelimit_headers("default", DEFAULT.amount, DEFAULT.get_expiry(), stats.remaining, reset)
    if not allowed:
        return problem_response(429, {"type": f"{PROBLEMS}/rate-limit-exceeded", "title": "Too many requests",
                                      "detail": f"Retry in {reset} seconds."},
                                headers={**headers, "Retry-After": str(reset)})
    response = await call_next(request)
    response.headers.update(headers)
    return response
```

# throttling.py: DRF throttles that remember their state, so the response can publish it
from rest_framework.throttling import AnonRateThrottle, ScopedRateThrottle, UserRateThrottle

class PublishedRateMixin:
    def allow_request(self, request, view):
        allowed = super().allow_request(request, view)
        history = getattr(self, "history", None)  # unset when this throttle didn't apply
        if history is not None:
            reset = int(self.duration - (self.now - history[-1])) if history else self.duration
            request.ratelimit = {
                "RateLimit-Policy": f'"{self.scope}";q={self.num_requests};w={self.duration}',
                "RateLimit": f'"{self.scope}";r={max(self.num_requests - len(history), 0)};t={reset}',
            }
        return allowed

class AnonThrottle(PublishedRateMixin, AnonRateThrottle): ...
class UserThrottle(PublishedRateMixin, UserRateThrottle): ...
class SmsThrottle(PublishedRateMixin, ScopedRateThrottle): ...

# views.py: every view inherits the header publishing; 429s get Retry-After from DRF
class FernhillView(APIView):
    def finalize_response(self, request, response, *args, **kwargs):
        response = super().finalize_response(request, response, *args, **kwargs)
        for name, value in getattr(request, "ratelimit", {}).items():
            response[name] = value
        return response

class PhoneVerification(FernhillView):
    throttle_classes = [SmsThrottle]
    throttle_scope = "sms"  # an expensive side effect gets its own, much lower limit

# settings.py: a shared cache backend (Redis) keeps counts consistent across instances
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": ["shop.throttling.AnonThrottle", "shop.throttling.UserThrottle"],
    "DEFAULT_THROTTLE_RATES": {"anon": "20/minute", "user": "100/minute", "sms": "5/hour"},
}

```ts
const WINDOW = 60;

// hono-rate-limiter only knows older drafts, so turn its headers off and write the current ones.
function setRateLimitHeaders(c: Context): number {
  const { limit, remaining, resetTime } = c.get("rateLimit");
  const reset = resetTime
    ? Math.max(0, Math.ceil((resetTime.getTime() - Date.now()) / 1000))
    : WINDOW;
  c.header("RateLimit-Policy", `"default";q=${limit};w=${WINDOW}`);
  c.header("RateLimit", `"default";r=${remaining};t=${reset}`);
  return reset;
}

app.use(
  "/orders/*",
  rateLimiter({
    windowMs: WINDOW * 1000,
    limit: 100,
    standardHeaders: false,
    keyGenerator: (c) => c.get("clientId") ?? c.req.header("x-forwarded-for") ?? "anon",
    store: new RedisStore({ client: redis }),
    handler: (c) => {
      c.header("Retry-After", String(setRateLimitHeaders(c)));
      return problem(c, 429, "rate-limit-exceeded", "Retry after the time in Retry-After.");
    },
  }),
  async (c, next) => {
    setRateLimitHeaders(c);
    await next();
  },
);
```

All three tabs build the strings by hand, which is safe while the values are plain integers and a quoted name. Once you add `pk` or several policies, use a Structured Fields library (`http-sf` in Python, `structured-headers` in TypeScript) rather than more string formatting.

## Limit the business flow, not only the endpoint

Some abuse stays politely within every per-endpoint limit. Fernhill releases 200 pairs of a limited-edition walking boot, and a bot with ten API keys buys all of them in four seconds. Others create thousands of accounts for sign-up bonuses, or try every coupon code. OWASP lists this separately as API6, and the defences live at the level of the flow:

- Limits per account, per payment instrument or per shipping address, not only per API key.
- Friction where it's cheap for humans and expensive for bots: email or phone verification, proof-of-work, CAPTCHA on anonymous flows.
- Device and behavioural signals, and holding suspicious orders for review instead of rejecting them outright.

<Note kind="curiosity" title="420 Enhance Your Calm" source="https://en.wikipedia.org/wiki/List_of_HTTP_status_codes#Unofficial_codes">

Before RFC 6585 registered 429 in 2012, Twitter's original API answered rate-limited clients with an unofficial 420 "Enhance Your Calm". It worked only for clients written against Twitter's docs. Generic HTTP tooling had no idea what 420 meant and treated it as an ordinary 4xx. Once a standard code exists, use it, because the tooling already knows it.

</Note>

<Rule guide="zalando" id="153" level="MUST" title="Use code 429 with headers for rate limits">

Zalando accepts either `Retry-After` or a trio of `X-RateLimit-Limit`, `-Remaining` and `-Reset` headers. This guide sends `Retry-After` on every 429 and the IETF `RateLimit` fields in place of the `X-` trio.

## What to take away

Cap what one request can cost, cap how often each client may call, and tell clients both numbers before they find out the hard way. Limits stop the clumsy and the greedy. A determined attacker goes after your logic instead, and those [attacks are best told as stories](/security/attacks/).
